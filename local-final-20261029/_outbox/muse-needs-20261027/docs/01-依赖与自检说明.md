### 2.1 白名单 2 个是哪些（清单点名要写清）

| 动作 | 判定 | 理由（`tools\freebie_allow.json` 原文） |
|---|---|---|
| `passCardAward` | ALLOW FLAG（无真扣、无记账） | 通行证档位：`passAward>=4` 判已领 + 活跃度门槛（C01 已审） |

另有 **WARN 1 条**（不阻断）：`rewardUFO` 的资格判断里用到 `p.signCode` —— 已人工确认那是防作弊签名，**不是**档位/身份/胜负，故不改。

### 2.2 拒绝码 136 / 153 / 238 的统计口径（清单要求写清）

`tools\check_reject_codes.js` 的三个数字口径不同，别混着说：

| 数字 | 名字 | 口径 |
|---|---|---|
| **136** | 动作 | **有拒绝分支的动作数**（`var H` 里出现过 `eRet` 拒绝登记的动作） |
| **153** | 条目 | 拒绝码**事实表条目数** = `reject=152` + `flow=1`（`tools\facts\reject-codes.json` 的条目，按「动作×原因码」去重计数） |
| **238** | 拒绝点 | **代码落点计数**：R5b+ 扫描 271 个 handler，命中 `noteReject(...)`/字面量 `eRet` 的**处数**（同一动作多处拒绝就多计；动态 `eRet` 规避 0 处） |

所以「动作 136 < 条目 153 < 拒绝点 238」是正常的：一个动作可以有多个原因码、一处拒绝也可能是两行叠加。

## 3. `node build-handlers.js` 的预期产物（清单点名要写清）

```powershell
cd F:\BaoZouyxt\hotfix-patch
node build-handlers.js
```

期望 stdout（节选，本机 2026-10-28 沙箱复跑原样）：

```
CATCH CODES  136 个动作已推导：...
HANDLERS OK  ver=hcce22f0f  selfCheck=1426  bytes=1639277  -> patch/live/handlers.js
FLOW     OK  bytes=17862  -> patch/live/flow.js
```

- **ver = `hcce22f0f`**、**selfCheck = 1426**、产物 **1,639,277 B**（这就是最新值，与线上 `impl` 一致）。
- 复跑注意：产物第 1 行是 `built=<ISO 时间戳>`，**每次构建都会变**（这是唯一允许的差异）。沙箱复跑时整文件 MD5 会与仓库里那份不同（时间戳行不同），**跳过第 1 行后逐字节一致**（本机已验证 `True`）。
- 顺序铁律：**改了动作 → 先 `node tools\gen_shapes.js`，再 `node build-handlers.js`**；否则 build 自检会因为「实现前形状是 `eRet:1` 空壳」拦下（报 `shape:<动作>:eRet info 2`）。

## 4. 校验 SHA256（Windows 片段）

```powershell
Get-Content SHA256SUMS.txt | ForEach-Object {
  $h,$f = $_ -split '\s+',2
  $got = (Get-FileHash -LiteralPath $f -Algorithm SHA256).Hash.ToLower()
  if ($got -ne $h) { "FAIL $f" } else { "OK   $f" }
}
```
