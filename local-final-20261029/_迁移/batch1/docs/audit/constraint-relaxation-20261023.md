# 约束放宽：允许在进程内改客户端数据层（2026-10-23 用户裁定）

> 用户原话：「可以放宽约束」。
> 上下文：R20 审阅 §4③ 把"monkey-patch `CFMgr.getItem` 去 rebase 配置表时间"判为**越界**，
> 并写明「这一条只能由用户来修改约束，它不在我的技术判断权范围之内」。用户在此明确放宽。
> 这是**约束变更**，不是一次性许可，所以单独留档。

## 1. 变更前后

| 项 | 变更前（本项目此前一直遵守的口径） | 变更后（用户 2026-10-23 裁定） |
|---|---|---|
| 允许改的东西 | 只替换**网络层**：拦住并应答客户端自己的请求 | 还可以在**游戏进程内**改客户端**数据层**的返回值（例如 `ConfigMgr.getItem(...)` 返回的行） |
| 仍然禁止 | 改/重打包 APK、改官方客户端文件、架服务器、伪造付费 | **完全不变** |
| 补丁位置 | 客户端自己的可写目录（`files/hotfix/…`） | 不变 |

## 2. 立刻解锁的事

1. **16 条配置表活动时间**（`active` 27/55、`exchange` 2200..2212、`mall` 39）：不再只能"忠实到期"，可以在进程内把 `getItem` 返回的时间列 rebase 到 now+Δ。
2. **`create.currentServerEndTime` / `serverOpenTime`**（10 位秒级，2026-12-26）：同理可改，但 R20 反例 8 警告它可能是"开服第 N 天"的依据（七日任务），一起平移会让七日活动永远停在第 1 天 ⇒ **必须分开取证、分开裁定**。
3. 其它"配置表驱动"的行为（掉落/商店/活动开关）理论上都在新边界内。

## 3. 必须随之而来的纪律（不是建议，是硬要求）

1. **每一项数据层覆盖都要有登记**：`文件:行号`（被覆盖的读点）+ 覆盖前后的值 + 关闭开关的一行常量（沿用 `REBASE_ACTIVITY_WINDOWS` 的形态）。
2. **可观测**：覆盖生效时打一条日志（沿用 `env.log`），否则"行为变了但没人知道"。
3. **不许扩大到手改玩家可见数值**：数据层覆盖只用于**时间/开关**这类"抓包快照老化"问题；凡是会改变经济口径的（掉落表、价格表、兑换成本）一律不覆盖，只登记。
4. **边界仍需顾问钉死**：放宽到"数据层"这个词的精确范围（能不能改 `BundleMgr` 的 prefab 加载？能不能改 `LangMgr` 文本？）留给下一批由顾问给判据；在拿到判据之前，**只做时间列 rebase 这一类**。

## 4. 回滚

每一项覆盖都必须是"一行常量 + 一段函数"，常量置 false 即回到原行为；
代码回滚位仍按批次的 `_backup\<时间戳>-pre-*\` 走（带 `MD5SUMS.txt`）。
