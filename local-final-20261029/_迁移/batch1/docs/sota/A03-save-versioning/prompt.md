# A03 · 存档版本演进（第 1 批 · 直接复制下面整个代码块去问）

> 用法：整段复制 → 贴给外部模型 → 把答复原文存成同目录 `answer.md` → 主审再写 `adopted.md`（只有它能改代码）。
> 红线：本文件已脱敏，**不要**在粘贴时补上游戏名、真实字段 id、密钥、表名。

```text
请帮我设计一套"单文件 JSON 存档"的版本演进方案。这是纯技术问题，我给出全部背景，不需要你猜业务。

【场景】
单机离线程序，玩家进度全部存在一个 JSON 文件里（当前约 700 字节，预期最终 20–100 KB）。
没有数据库，只有文件读写：读 = 读整个文件反序列化，写 = 序列化整个对象覆盖原文件。
运行环境会随时被杀进程（移动端/模拟器），也可能断电。
玩家数据不可接受丢失——这是玩家的全部进度，丢了就是灾难。

【已经发生过的 4 次结构调整（一周内）】
v1  { roleId, questAccepted: [qid], questDone: [qid],
      abilities: { aid: levelNumber }, inventory: { itemId: count }, xp }
v2  + equipInstances: { uid: [kind, itemId, attrs, gemIds, skinId] },
      equipSlots: { slotIndex: uid }
    （原因：装备需要"实例"概念，同一件装备可以有不同属性）
v3  abilities: { aid: [level, progressRaw, tier] }
    （原因：技能要存升级进度和突破等级，不能只存 level）
v4  + rewardedQuestIds: [qid]
    （原因：奖励要防重复发放，需要记"已发过奖励"的名单）

目前的做法很原始：读档后 if (!save.abilities) save.abilities = {}，逐字段补默认值；
没有版本号，也不写迁移函数。已出现过两次事故：① 某次改动后旧档读出来少了字段，
程序按"空"处理并把空值写回，玩家背包被清空；② 同名字段在"全量快照"和"增量同步"两个接口里
格式不同（一个是数组，一个是对象），改错一处静默失效两周没人发现。

【约束（重要）】
1. 只有一个存档文件，不能引入数据库、不能要求多进程锁。
2. 程序随时可能被杀，写文件必须在任何时候都是"要么旧内容、要么新内容"，不能写一半。
3. 迁移函数必须幂等（同一份旧档跑两遍结果一样），且必须能跳过版本直接升到最新。
4. 存档里有些集合是"增量语义"（每次同步只回变更项），有些是"全量语义"（整份替换）。
   两者混在同一个文件里，格式还不一样。
5. 玩家可能从备份恢复到某个旧版本，然后再次升级。

【我要什么（请只回答这四件事）】
1. 版本化方案：`saveVersion` 整数 + 顺序迁移函数，还是"读时补默认值"，还是两者混用？
   给出你推荐的组合，并说明为什么另一种会出问题。给出迁移函数的签名和一个最小实现骨架。
2. 原子写：在上述约束下，文件写入怎么做到"永不留半截"？（给出可移植的做法，不要依赖特定框架）
3. CI 断言：我要能在测试里拦住"改字段把老档写坏"。请给出 3–5 条断言，每条都要写成
   "给定某版本存档输入，断言输出满足 X" 的形式，能直接翻译成代码。
4. 自动备份与自愈：什么时候备份、保留几份、如何检测"这次写入写坏了"并自动回滚？
   给一张策略表（时机 / 份数 / 触发条件 / 回滚动作）。

【回答格式（严格照这个来）】
1. 结论：≤5 句。
2. 迁移签名 + 骨架代码（≤40 行，伪代码即可）。
3. 原子写做法（≤10 句，标明可移植性与失败场景）。
4. CI 断言 3–5 条（每条一句话 + 一句伪代码）。
5. 备份策略表（4 列）。
6. 边界清单：容易漏的边界条件（≤8 条，每条一句话）。
7. 反例：我这套"读时补默认值"的做法，在什么具体场景下会写坏玩家数据？
8. 假设：你这条建议依赖哪些前提？哪个前提不成立就失效。
9. 落地步骤：≤5 步，每步一句话。

不要给"建议考虑/应该注意"这类空话；每条结论要么带条件说明，要么带可执行形式。
不要假设我有数据库、消息队列、分布式锁——我只有本地文件和单线程。
```
