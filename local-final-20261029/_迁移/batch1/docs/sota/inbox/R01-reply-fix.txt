0. 先认错与数据核对
上一批 B01 的 H3（计数目标可以从 Type + Require 解析出来）已被证伪。因此 B01-2 的方式③（事件推断计数）、B01-3 的去重键、B01-4 的 taskProg.c 计数器全部作废。B01-4 的 v5 迁移只保留 legacy 标记的思路，计数字段不再引入。
数据自洽性核对：Type 3847+530+454+9 = 4840 ✓；875 = 12+66+56+0+741 ✓；1058 = 995+63 ✓。上一批材料写的是 4842 个任务，这次是 4840 个，相差 2 个，材料未提供原因。
“完成条件只有两种可观测数据”这一判断可能不完整。表里还有 Fight、ReceiveEvent、CompletionEvent、receive_action、finish_action 等列，可能也承载完成条件或发物逻辑，但这几列的取值分布材料未提供。【推断】第 3 节的验证步骤 V1 用来核实这一点。
有一个缺失信息决定了下面所有结论：交任务时 SpRequire 物品会不会被扣掉（上交），还是只需要”携带”，材料未提供。 下文用 C(t,i) 表示交任务 t 时扣除的物品 i 数量：上交型任务 C = need，携带型任务 C = 0。
1. 结论
按回执里写的形式（把差额写进存档背包、用全局 borrowed[itemId] 记账、交任务时扣回、“不得跨会话残留”），先借后还不能直接用。它有四个缺陷：上交型任务会被重复扣除；全局记账让多任务互相吃掉借款；借来的物品和自己买的物品混在一起后可以被卖掉或用掉，从而把凭空增加转移到别的科目；“不得跨会话残留”与任务本来就可以跨会话这件事矛盾。
替代做法是派生叠加：存档里的 inventory 永远只记合法获得的数量，不再写入任何借来的物品；L5 投射给客户端时，按”进行中任务的需求减去真实库存”现算一份只用于显示的叠加量 overlay = f(state)。这样什么都不用持久化，不会漂移，也不会残留。
派生叠加满足”客户端交任务前只在本地校验数量 ≥ 需求”这个前提，同时让守卫不需要任何”允许背包凭空增加”的例外。代价是：客户端如果想使用或卖出叠加出来的物品，服务端会拒绝，变成一次误拒；这类误拒必须重新投射，让客户端视图回到正确值。
如果坚持用写入存档的借贷账本，必须同时满足四条：按任务分账（loans[taskId][itemId]）；交任务时的归还量是 R = max(0, 借款 − C)；把借款当作背包上的留置额，使用或卖出不得吃进留置额；账本与背包在同一个 state’ 里原子写入。
741 种物品没有来源，最可能的解释是”任务自己在接取或剧情事件里发物”【推断】。如果 V1 证实这一点，接任务时补物品就不是凭空增加，而是配置声明的合法授予；那么正确的做法是把它实现成按配置发放的 TaskGrant 事件，而不是去”借”。
2. 逐项回答 a–e
下面每一项都对比两种做法：回执原方案（借款写进存档背包，用全局 borrowed 记账），和我推荐的派生叠加（overlay）。
a. 接任务后、交任务前，玩家自己买到了同一物品
会不会坏： 原方案在携带型任务上不会坏，在上交型任务上会坏。
坏在哪： 以需求 5、自有 2 为例。接任务时借 3，背包变成 5；然后买了 5，背包变成 10。上交型任务交付时扣 5，背包剩 5，再”归还”借款 3，背包剩 2。但玩家实际应该剩 2 + 5 − 2 = 5，被重复扣了一次。携带型任务交付时不扣，归还 3 后剩 7，这是正确的。
怎么防： 原方案必须改成 R = max(0, B − C)：上交型任务的借款由上交动作本身偿还，不再另外扣。派生叠加天然正确：买入后真实库存是 7 ≥ 5，叠加量自动变成 0；交付只扣真实库存，不需要任何特殊处理。
b. 玩家放弃任务（如果存在放弃请求）
会不会坏： 原方案会坏。放弃请求是否存在，材料未提供；Repeat 列的存在说明任务可以重复接取。
坏在哪： 放弃时没有归还的话，借来的物品就成了白送。如果”接取 → 放弃 → 再接取”可以循环，每一轮都能再借一次，背包无限膨胀。如果放弃动作还没有实现、落到了 F 降级层（旧回放逻辑），借款永远不会被清账。
怎么防： 原方案要在放弃处理里执行 repay = min(loans[t][i], inv[i])，不够还的部分记入 forgiven 审计计数，然后删除 loans[t]；放弃动作不允许落到 F 层，必须走 ROUTE 路由。派生叠加下，放弃后任务不再处于进行中，叠加量随之变成 0，不需要任何处理。但要注意：客户端本地仍然留着那些叠加物品，直到下一次投射才会修正，所以放弃的应答里必须带上背包投射。
c. 同时接了多个需要同一物品的任务
会不会坏： 原方案会坏。
坏在哪： 用全局 borrowed[i] 按”当前背包”计算差额时，任务 1 需要 5、库存 0，借 5，背包变成 5；任务 2 也需要 5，这时库存已经是 5，差额为 0，不借。交付任务 1（上交型）后背包归零，任务 2 卡死，自动补齐原本承诺的”一路能点下去”被打破。反过来，携带型任务里两个任务本来可以共用同一份物品，如果按”预留”去计算差额，又会多借。
怎么防： 差额的计算方式取决于 C：上交型任务的需求累加，need_i = Σ need(t, i)；携带型任务取最大值，need_i = max need(t, i)。账本按任务分开存。派生叠加：overlay[i] = max(0, Σ_上交型 need + max_携带型 need − inv[i])，每次投射时现算。
d. 交任务前重启游戏
会不会坏： 原方案会坏，而且是回执里自己定的断言造成的。
坏在哪： 回执要求”borrowed 不得跨会话残留”，可任务本来就会跨会话进行。要满足这条断言，加载时要么拒绝加载，要么清空账本，后者直接把借来的物品变成白送。另外，账本和背包如果不在同一次写入里落盘，进程在两次写入之间被杀，就会留下”背包里多了东西、账本里却没记”的状态。
怎么防： 原方案要删掉这条断言，改成”借款只属于进行中的任务”（见第 5 节第 3 条）；账本放进存档，通过 v6 迁移引入，并和背包在同一个 state’ 里写入。派生叠加没有任何需要持久化的东西，加载后重新计算即可。
已有存档： 过去自动补齐写进去的物品已经和真实库存混在一起，无法区分。迁移时不要猜测，把这些物品当作既成事实保留，接受这一部分历史数值已经泄漏。
e. 物品是可堆叠的消耗品，客户端只校验”数量 ≥ 需求”
会不会坏： 原方案会坏。
坏在哪： 借来的物品已经在存档背包里，玩家可以直接用掉或卖掉。用掉的话，玩家等于白白获得了消耗品的效果；交任务时客户端校验不过，任务卡住；归还时 R 大于库存，背包会变成负数，或者截断后留下一笔永远还不上的残账。卖掉的话，借来的物品变成了货币，凭空增加从背包转移到了货币，背包这一科目的守恒断言完全察觉不到。
怎么防： 原方案要加留置检查：对使用、卖出等非任务动作，断言 inv[i] - amount >= Σ_t loans[t][i]，不满足就拒绝。派生叠加下，使用或卖出时服务端只认真实库存，叠加出来的物品自然被拒绝。两种做法都会对客户端造成一次误拒（客户端显示有货，操作却失败），所以拒绝时必须重新投射背包，而且这类动作不能是纯 ACK 动作（纯 ACK 的客户端看不到应答）。此外，如果物品有堆叠上限（材料未提供），真实库存加上叠加量可能超过上限，投射时要截断到上限。

4. 来源系统补齐顺序与排序依据
排序依据：按下面的公式给每个来源系统 S 打分，从高到低实现。
score(S) = Σ_{物品 i ∈ S 能提供} |downstream(tasks_requiring(i))|      // Pre-Require 图上的传递下游任务数（只算可达任务，见 V5）
           × verifiable(S)                                              // 写入能否用闭式守恒校验：能 = 1，需要外部计数或去重 = 0.3【推断的权重】
           / newWritePoints(S)                                          // 新增写入点数量（每一个都要进 A04 白名单）
按”下游解锁数”排序，而不是按”物品种类数”排序，是因为一个卡在主线上游的物品会挡住它后面整条任务链。可校验性之所以作为乘数，是因为 B01 已经证明这个项目无法对战斗做去重，凡是依赖战斗计数的来源都会带来不可逆的风险。
按这个依据得出的初稿顺序（每一步都应以分数的实际计算结果为准）：
任务自身发放（TaskGrant）：取决于 V1 的结论。不需要新系统，也不新增写入点，只是把接任务时的补齐从”凭空增加”改为”配置声明的授予”，并用 TaskGrant 事件守恒。预期分数最高。
任务奖励链（66 种只来自奖励，另有 12 种多来源）：已经存在，只需按 Reward → drop → item 校对展开逻辑。可以闭式校验。
商店（56 种只来自商店）：新增一个写入点（买），效果是货币减少、物品增加，守恒关系清楚。前提是货币有合法来源，如果货币没有来源，商店的价值趋近于 0。
V2 和 V6 找到的其他表（合成、活动、采集）：这些表的结构材料未提供，等表找到之后再计算分数。
打怪掉落：在任务物品上的覆盖为 0（“仅打怪掉落”是 0 种），而且依赖战斗结算去重（B01 已经证明拿不到），可校验性最低，排在最后。
5. 5 条断言
说明：第 1–4 条针对”写入存档的账本”做法（如果你保留先借后还）；第 5 条两种做法都适用。
不重复借。 断言：var s1 = run(s0, accept(t)), s2 = run(s1, accept(t)); assert(eq(s2.loans, s1.loans) && eq(s2.inventory, s1.inventory))。触发场景：客户端重发 acceptTask，或者对已在进行中的任务再次接取。
借款有上限，且有留置。 断言：for (t in loans) for (i in loans[t]) assert(loans[t][i] <= need(t, i))，并且在每个非任务动作之后：for (i in inv) assert(inv[i] >= sumLoans(i))。触发场景：卖出或使用借来的物品（e），或者多任务重复计算差额（c）。
不残留（取代”不得跨会话残留”）。 断言：assert(isSubset(keys(state.loans), state.questAccepted))，每次写入前都要检查。触发场景：交付或放弃之后忘了清账，放弃动作落到了 F 层。
不超额还。 交付任务 t 时断言：for (i in need(t)) { var B = loans0[t][i] || 0, C = consume(t, i); assert(inv1[i] === inv0[i] - C - Math.max(0, B - C) && inv1[i] >= 0) } assert(!(t in loans1))。触发场景：上交型任务重复扣除（a）。
长期守恒，防漂移。 存档里持久化审计计数 ledger = {borrowed: {}, repaid: {}, forgiven: {}}，每次写入前断言：for (i in U) assert(ledger.borrowed[i] - ledger.repaid[i] - ledger.forgiven[i] === sumLoans(i))。派生叠加做法下改为断言：assert(eq(overlay(s), overlay(deepClone(s))))，并且 save.inventory 的任何增加都必须由奖励、购买或 TaskGrant 事件解释。触发场景：任何一个绕过账本修改背包的写入点，比如调试通道灌物品、F 层回放。
6. 反例：静默漂移的场景
对上交或携带的判断错了。 如果某个任务实际上由客户端在本地扣除物品，而服务端当成携带型处理，服务端存档会多出这些物品、客户端显示会少；反过来则会重复扣除。各项断言都基于同一个错误的 C 值，全部通过，漂移完全静默。
可重复任务成了刷奖励的机器。 如果某个 Repeat 任务是携带型且带 Reward，借来的物品不消耗，“接取 → 交付”可以无限循环，每一轮都拿一份奖励。背包守恒完全成立，但奖励是凭空产生的。用下面这条命令检查这类任务是否存在：python3 筛选 Repeat≠0 且 SpRequire≠0 且 Reward≠0 的行。
派生叠加的投射点漏了一个。 如果某个背包增量接口走的是 F 层回放，没有加上叠加量，客户端本地背包就会和叠加视图来回跳动。存档本身不会坏，但玩家看到的数字会漂移，直到下一次全量快照。
历史上自动补齐产生的物品。 已经写进存档、和真实库存混在一起，任何断言都无法识别，这部分永久保留。
TaskGrant 实现成按配置发放之后，发放后的物品被用掉。 如果玩家用掉了任务发的道具，然后放弃任务、重新接取，会再发一次。需要用”每个任务每次接取只发一次”的 acc 键去重（需要单调计数，B01-4 里的 seq 可以保留下来用于这个目的）。
7. 假设
H1：客户端在发送 getFinishTaskAward 之前，会用本地背包校验”数量 ≥ 需求”（即 e 的描述）。不成立时，不需要任何叠加或借贷，服务端在交付时直接不校验即可，第 1 节第 2 条失效。
H2：客户端不会把本地背包整份回传给服务端。不成立时，叠加出来的数量会被客户端当成真实库存回写，派生叠加失效。
H3：所有背包投射都经过 L5。不成立时，叠加只在部分接口里出现，会出现第 6 节第 3 条描述的漂移。
H4：上交还是携带（C 值）可以逐个任务确定（通过客户端代码或黑盒实验）。不成立时，a 和 c 的公式都没有输入。
H5：使用、卖出物品的请求不是纯 ACK 动作。不成立时，这类误拒对客户端不可见，客户端会一直显示错误的背包。
8. 落地步骤
先跑 V1、V5 和 Repeat 筛选（只读）；同时用黑盒实验确定交付时客户端是否本地扣除 SpRequire，产出每个任务的 C 值表。
V1 命中的任务改成 TaskGrant 事件（按配置发放，按 acc 去重）；其余 SpRequire 任务改成派生叠加，删除接任务时写背包的逻辑。
交付时只扣真实库存的 min(inv, C)；对使用、卖出叠加物品的请求，拒绝并重新投射。
从 A04 守卫里删掉所有”允许背包凭空增加”的例外，加入第 5 节的第 5 条断言和叠加纯函数断言。
