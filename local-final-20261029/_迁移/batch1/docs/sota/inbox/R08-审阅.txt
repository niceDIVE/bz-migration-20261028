1. 结论
D1 的修法方向对，但还缺一道防线。 现在只靠”MUTATE 非空就不写产物”，这条防线挂在一个环境变量上。如果 CI 的全局环境里残留了 BZ_MUTATE，分类器就会一声不响地什么都不写，gen_shapes.js 会照着上一轮的旧 field-classes.json 生成形状表。要补的断言：gen_shapes.js 读取分类文件时，校验文件头里的 runId（或输入三包的 md5）与本次构建一致；对不上就退出码 1。
D2 修好了确定性，却把一个语义错误冻成了常量。 GEN_NOW = 1792612412000 是 2026-10-21 12:53:32 PDT。只要某个时间字段没有 handler 产出，客户端每次收到的都是这个固定时刻。如果客户端用”当前时间减 beginTime”来算进度，这个差值会每天增长 86400 秒，表现为一开始就已完成，或者进度条溢出。
时间类字段不能用常量作形状默认值。 它们要么由 handler 在请求时取 env.now() 产出，要么在判明客户端不读之后直接剔除（见 Q2 的判别步骤）。
重新 --freeze 本身没有错，问题是这次冻结没有核对差异范围。 冻结时应该断言”基线差异恰好等于 D2 预期的 17 处时间类路径”，否则同一个 diff 里混进来的意外改值会被一起洗进基线。见 Q1 的 C10。
upgradeSkill 的取证暴露了一个比死字段更重要的事实：handler 里直接 __require(&#39;RoleBaseInfo&#39;) 写活模型，是 L3 的第二个出口。 R07 的 S3 推送计数，以及 R04 的单一投射出口假设，都漏掉了它。
把键改成 ptt，激活了一条原本不生效的路径，所以”危害为 0”还没有被证明。 它取决于 ECONOMY_CHNG 的 ptt 分支是赋值还是累加。见第 5 节。
2. Q1 答
可判定区分规则
对差异集里的每一项（动作，路径，旧值 v0，新值 v1），先计算两个值的”分支签名” σ：
function sigma(v) {
  if (v === undefined) return &#39;absent&#39;;
  if (v === null) return &#39;null&#39;;
  if (Array.isArray(v)) return v.length ? &#39;arr+&#39; : &#39;arr0&#39;;
  var t = typeof v;
  if (t === &#39;number&#39;) return v === 0 ? &#39;num0&#39; : (v < 0 ? &#39;num-&#39; : &#39;num+&#39;);
  if (t === &#39;string&#39;) return v === &#39;&#39; ? &#39;str0&#39; : &#39;str+&#39;;
  if (t === &#39;boolean&#39;) return v ? &#39;true&#39; : &#39;false&#39;;
  return Object.keys(v).length ? &#39;obj+&#39; : &#39;obj0&#39;;
}
σ 编码的是客户端所有真值判断、.length、短路运算和下标读取会看到的那一层差别。
(a) 计划内的值重写：下面三条同时成立。
签名不变：σ(v0) 等于 σ(v1)。对象类型时，要逐层递归比较子键集合，每一个叶子的 σ 都不变。
在清单里：这一项能被 golden/planned-changes.json 里某条规则的谓词匹配上，例如：
{"rule":"D2-clock","field":["beginTime","CDTime","gen"],"expect":17}
数目精确：每条规则匹配到的项数，恰好等于这条规则的 expect。
(b) 意外的放宽：上面三条只要有一条不成立，就判为 (b)。
你担心的”0 变成非空数组”属于 σ 变化：num0 变成 arr+。它在第 1 条就会被拦下，不管路径有没有变化。
另有一种特殊情况：如果这个字段是查表键（静态扫描能匹配到 getItem(X.f, "表")），那么即使 σ 不变，v1 也必须是这张表的合法主键。F1 的 getItem(0, "formula") 就是”σ 不变但值不合法”的例子。

3. Q2 答
判定条件
把动作 B 的 handler 返回值，继承给动作 A 的字段 f 作为默认值，只有下面三条同时成立时才合法：
同一读取代码：A、B 两个回调里读取 f 的代码，是同一个函数（共享具名回调），或者是同一个消费函数。
与 B 的状态无关：这个值不来自 B 的状态、时间或 id，在 C11 定义下是中性值。
σ 不变：这个值的 σ 和 A 的回调期望的 σ 相同。
但是，一个中性值根本不需要从别的动作继承，直接按类型给空值就行；而一个非中性值必然不满足第 2 条。所以合法的继承在实践中是空集，选 (a)，禁止跨动作继承。
只是给错误贴一个标签，并不能阻止 A 收到 B 的语义。BeginMeditation 拿到”钓鱼开始时刻”就是这种情况。
(a) 下的默认值来源，按顺序取第一个可用的：
A 自己 handler 的返回值；
按 A 回调里的读取类型生成中性空值；
如果这个字段既是契约，又是查表键，并且 A 没有 handler，生成器拒收，写入人工清单。中性值 0 会触发 F1 那种查表失败，不能用。
断言 C12：形状条目的 src 只能是 handler:<A>、neutral 或 promoted 之一，不允许出现 handler:<B≠A>。

4. Q3 答
收益的定义
改造收益 = 消除的潜在 F1 型风险对数 R。
一个（动作 A，字段 f）计入 R，需要下面四条同时成立：
f 在 A 的 span 内是闭合的：没有成员赋值、没有把响应对象整体外传、别名的读取全部在 span 内；
只按 span 内的读取，f 判为开关；
当前 f 被补发（47 个冲突字段目前全部被补发：契约 42、键集合契约 5）；
A 的 handler 在所有录制样本中都没有自己给出 f。如果 handler 总会给出 f，补发与否就没有影响，不计入。
闭合率只是一个辅助指标，不能作为是否改造的判据：闭合的对子里，如果 span 判出来仍然是契约，改造对这一对是零收益。

5. 对 note.eco.potential 改为 ptt 的判断
不同意”危害为 0”已经得到证明。
改动之前，note.eco.potential 是一个确定的空操作。改成 ptt 之后，ECONOMY_CHNG 的 ptt 分支被激活，这是一处行为变化。你保留顶层 potential 时用的理由是”不制造新变数”，但这次改键恰恰违背了这个理由。
判别：读 tools/index.js:64698-64725 里 case "ptt" 的那条语句。
如果是赋值（例如 potentials = value）：它与 handler 主动推送的值相同，结果冗余但无害。同意你的处置。
如果是累加（+=）：你发的是新余额，不是增量。客户端显示的潜能会变成”推送值加新余额”，大约翻倍，直到下次 LoadGame 才恢复。这时有两个改法，二选一：
eco 改成发增量，并且删掉主动推送；
或者撤掉 eco，只保留推送。
同一个判别结论也适用于 R07 的 118 行兑换修复：那里的 note.eco.ptt 同样是按新余额发的。
顶层冗余 potential：回调不读它，同意保留，危害为 0。
补一条自检：在 core/ 下 grep __require\(&#39;RoleBaseInfo&#39;\) 的写入点，把它们登记为 L3 出口，并纳入推送计数器。否则 R07 Q4 的 S3 断言”召唤期间推送增量为 0”会漏掉这条旁路。
6. 反例
固定时间戳：BeginMeditation 没有 handler，客户端收到的 beginTime 是 2026-10-21 12:53:32 PDT。如果打坐的时长小于”现在减去这个时刻”，玩家点开始就立即”完成”，紧接着发出结束请求。复现：在真机上点打坐，对照 Q2 判别第 3 步看到的差值。
σ 漏判：某个字段从 [0] 变成 [5]，σ 都是 arr+，C7 判绿。但如果客户端用 e.list[0] 去查表（5 不是合法主键），会出现 F1 型崩溃。只有当这个字段被识别进查表键集合 K 时，C9 才能抓到；如果是下标形态的查表键（getItem(e.list[0], ...)），K 的提取正则必须覆盖这种写法。
清单规则过宽：D2-clock 的谓词只匹配字段名 beginTime。如果以后另一个改动恰好把某个 beginTime 从 0 改成了 handler 的真实值，只要总数仍然是 17，C8 就会放行。所以清单规则还要写明旧值的范围（例如旧值落在某次运行的时间窗口内）。
D1 环境变量残留：CI 的 runner 复用了 shell，BZ_MUTATE 没有清掉。分类器不写产物，构建照旧走旧的 field-classes.json，C1 拿旧产物比字面量，依然判绿。第 1 节第 1 条要求的 runId 校验，就是为了抓这种情况。
eco 累加：如果 ptt 分支是累加，那么升级一次技能之后，客户端显示的潜能大约翻倍；账本是对的，所以自检 skill:ecoKey:ptt（eco 的值等于账本潜能）依然判绿。这正是 C2 教训里”断言比对的对象选错了”那一类：这条自检拿 eco 去比账本，而该比的是客户端显示。
7. 假设
H1：ECONOMY_CHNG 的分支有可能是累加，只是还没核实。如果读完确认是赋值，第 1 节第 6 条和第 5 节的风险部分作废，你的处置成立。
H2：客户端会用 beginTime 和当前时间做减法【推断】。如果 Q2 判别第 2 步发现它是死字段，第 1 节第 2 条和第 6 节反例 1 降为”无害的常量”，只需要按 C11 把它剔掉或置 0。
H3：σ 的五档（不存在、空、零、正、负）覆盖了客户端分支依赖的值特征。如果客户端有按具体值分支的代码（例如 == 2），C7 就不够，必须给这类字段建一张枚举白名单。
H4：录制样本覆盖了每个 handler 的常见路径。如果没有覆盖，Q3 的 handlerOwns 会被低估，R 会被高估，从而可能误判进入”做 span 改造”那一档。
H5：action_facts_listener.json 里存有回调的行范围。这一点材料未提供。如果没有存，Q3 第 2 步就要先实现 R07 Q3 的 span 定位，脚本的成本会从”只读统计”上升为”半个改造”。
H6：gen_shapes.js 读取的分类文件里能写进 runId。如果文件格式不允许（例如被别的工具严格校验），就改为在 shapes.json 的 __meta 里记录输入文件的 md5，再由 CI 比对这个值。
