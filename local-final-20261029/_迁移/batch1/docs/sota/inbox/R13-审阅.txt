1. 结论
isCollective 现在的实现方向反了，而且是我 R12 的规则写错了。 按 index.js:120523 的逐字逻辑，真正需要这个字段”存在且等于 0”的，恰恰是非集体练功：门派练功界面开着时选择个人练功，客户端要靠它关掉门派界面、打开普通练功界面。你现在把请求值 0 过滤掉不发，正好丢掉了这一种情形。正确规则：请求里只要有 isCollective 这个字段，就原样回声它的解析值，0 也照发；请求里没有这个字段，才不发。这是我的错，R12 的假设 A1 已经被这段源码证伪。
skillID 的改法是对的，有一个条件：s.skills[String(sid)] 和存档里技能的实际键形一致。 如果存档里 skills 是数组，或者键形不同，所有练功都会被静默拒绝（见反例 3）。
useItem 的顺序改对了。 剩下一个缺口：效果分支如果先改写了 s、再在 bagAdd 之前抛出异常，内存和磁盘仍然会不一致。效果应该先汇总成待应用的增量，再一次性应用。
D1 有实际风险。 原来的问题出在 live 场景下检查被跳过，而 id 闸门只在构建期跑，构建期 harness 总是存在，所以这个闸门永远看不到 live 里的跳过。live 场景的 selfCheck 只回一个计数，这个窟窿等于原样保留了。第 5 节给出一个不动 flow 层的补法。
D2 目前没有实际风险。 条件是 B1 到 B3 批次开工之前必须先加上闸门；能不能按时加上，只能靠排期保证，因此需要把它写进 B1 的开工检查清单。
2. Q1 答
跨动作选码的通用规则：按动作选，不取交集
eRet 的含义由每个动作自己的回调来定义。同一个 4，在 useItem 里是一条提示分支，在 BeginTraining 里根本不进入任何分支。按”全族交集”取码，等于假设所有回调共用同一套码义，这一点已经被你给出的两处证据否定了。
每个动作的拒绝码按下面的顺序，取第一个满足条件的：
第 1 档：在这个动作的回调里，以及通用网络层里，有分支、且该分支只弹提示、不改模型、不发后续请求的码。候选不止一个时，选提示文本语义最接近”无法使用、条件不满足”的那一个（提示文本的内容材料未提供，需要抄出 :64904 和 :64906 的提示键）。
第 2 档：回调里没有分支，通用网络层也不拦截的码。前提有三条：客户端发请求之前没有本地预扣；没有遗留的等待遮罩；没有半写的 UI 状态。
永远禁止：这个动作的成功码集合里的任何码。BeginTraining 的成功码是 1 和 2（回调写的是 1 == n.eRet || 2 == n.eRet），所以 2 绝对不能当拒绝码。
统一性只做为平局规则：当第 2 档有多个码可选时，取 4，便于对日志。统一性不能凌驾于第 1 档之上。
按这套规则：useItem 取 4 或 5（第 1 档，以提示文本为准）；BeginTraining 取 4（第 2 档）。
把选码理由写成断言
新增 tools/facts/reject-codes.json。这份文件由脚本从回调源码里抽取 eRet 比较式生成，人只负责填写 chosen 这一列：

CI 断言 R1 到 R5：
function assertRejectCodes(tbl, runReject, genericIntercepts, lineSha) {
  Object.keys(tbl).forEach(function (a) {
    var t = tbl[a];
    assert(t.success.indexOf(t.chosen) < 0, &#39;R1 拒绝码落在成功集 &#39; + a);
    if (t.promptOnly.length) assert(t.tier === 1 && t.promptOnly.indexOf(t.chosen) >= 0, &#39;R2 有提示分支却没用 &#39; + a);
    else assert(t.tier === 2 && t.handled.indexOf(t.chosen) < 0 && genericIntercepts.indexOf(t.chosen) < 0, &#39;R3 第 2 档码被拦截或被处理 &#39; + a);
    assert(lineSha(t.ev), &#39;R4 证据行哈希不符（客户端包变了要重抽）&#39; + a);
    var r = runReject(a);                 // 用固定的非法请求夹具运行 handler
    assert(r.resp.eRet === t.chosen && r.diskHashSame && r.bizHashSame, &#39;R5 实际拒绝码或无副作用不符 &#39; + a);
  });
}
R5 把”注释里写的码”和”handler 实际发出的码”绑在一起，这样不能只改表、不改代码。反过来，handler 里每出现一个新的拒绝 return，也必须在表里有对应条目：先按 {eRet: 字面量扫描 handler 源码，得到动作集合，这个集合必须 ⊆ 表的键集合。
3. Q2 答
先说一个关键推论
var use = Math.min(n, have)：当账本里没有某个物品时，use 等于 0，什么都不会被扣。所以只有”账本里现在就有”的物品，才可能发生损失。可获得性的意义在于预判：这个物品将来会不会进入账本。
可获得性判定式
Obtainable(i) = Ledger(i) ∨ Drop*(i) ∨ Task(i) ∨ Shelf(i) ∨ Grant*(i)

Ledger(i) : 账本中任何容器（背包、仓库等，以存档实际结构为准）里 i 的数量 > 0
Drop*(i)  : ∃ npc：i ∈ closure(BZ_NPCDROP[npc])        // 掉落组如果嵌套，要做传递闭包
Task(i)   : ∃ task ∈ BZ_TASKS：i ∈ task.Reward 的物品集   // 包括挂在 rewardPending 上的，宁宽勿窄
Shelf(i)  : i ∈ 我们实际发出的货架（BZ_NPCSHOP ∪ BZ_GESHOP ∪ BZ_ROGUESHOP），不含 mall.json
Grant*(i) : ∃ handler 的 bagAdd(s, X, +k) 能让 X = i
            （包括兑换、BuyHomeCrop.rewardArray、useItem 效果本身产出物品，比如礼包）
* 表示要做不动点：礼包 A 可获得，A 的产出 B 就可获得，B 的产出也就可获得。
允许高估，不允许低估。 判成”可获得”的结果是拒绝使用，而对一个根本拿不到的物品来说，拒绝没有任何代价；低估则会把一个真实存在的损失漏掉。
每个物品都要输出来源证据：tools/facts/obtainable.json 里每项是 {itemID: [来源…]}，来源格式比如 "drop:npc123"、"task:4567"、"grant:exchange#line"。
Grant* 无法静态判定的 handler（物品 id 是动态计算出来的），整个 handler 都按”能给出它表里的所有物品”高估处理。
账本里现有的算不算可获得：算，而且是最强的一项。 这是唯一一种当下就会真的造成损失的情形。
计数表要不要纳入 G 规则
分成两张表处理：
计数对象
性质
G 规则

“需要服务端落地”类效果被消耗的事件
缺陷登记。按照 (b′)，这类效果已经改成拒绝，所以这个计数理论上恒为 0
cap 固定为 0：只要出现一次就 FAIL，不能登记豁免

“客户端本地生效”类效果被消耗的事件
清单登记，属于正常使用
只适用 G5：按”不同 Effect 码的个数”设 cap，出现新的码就 FAIL，强制先分类

请求使用一个账本里没有的物品（have=0）
这不是损失，而是客户端模型和账本发生了分叉的信号
单独做一个计数器，cap 为 0，出现即报警，由投射问题来处理

另外要补一个分类前提：item 表里的 Effect 码如果不在客户端认识的 18 个码之内，客户端很可能根本不会为这个物品发出 useItem【推断】。这类物品直接归到”不可达”，不用纳入取证。
4. Q3 答
用什么替代”上一次提交”
用上一次验收为绿的快照来替代，也就是一个由 CI 自己推进的序号。
tools/golden/registry-history.jsonl   // 只追加；每次验收全绿后由 CI 追加一行
{ "seq":42, "ts":"…", "impl":"hcf51452f", "reg":"known-missing-handlers",
  "entries":[...ids], "cap":0, "entriesHash":"…", "prev":"<上一行的 sha256>" }
tools/golden/registry-snapshot/<reg>.json   // 等于最后一行的 entries 和 cap，作为"base"使用
推进顺序固定为：先用快照当 base 判定 G1 到 G5，全部通过之后，才追加一行并刷新快照。 顺序不能反过来，否则一次违规的变更会先污染 base，再被拿来做比较（见反例 6）。

哈希链能否替代 git
防篡改的能力，只在链头有外部锚点时才成立。 没有锚点，整条链可以被整段重写，哈希链只能抓到”改了中间某一行”这种笨拙的篡改。今天就能用的锚点是：每次验收报告都打印链头哈希，而验收报告本身被归档。CI 断言”当前链头等于上一份归档报告里打印的链头，或者恰好是它往后追加一行的结果”。
你面对的威胁模型是”自己不小心借登记转绿”，而不是有人恶意改历史。在这个威胁模型下，history 加快照加报告锚点，判定能力已经等同于 git 的 merge-base 对比。少掉的只有”任意时刻的完整代码差异”，而 G1 到 G5 本来就用不到这一项。
5. 对 eRet:4 在 BeginTraining 上”静默但无损失”的取舍判断
有条件接受，但”静默”必须变成”可观测”。 理由是这个拒绝在正常操作下几乎打不到：练功界面列出的只会是客户端模型认为已经学会的技能。所以真正触发它的场景，几乎只有一种：客户端模型和账本的技能集合发生了分叉。这种情况下玩家会反复点击、毫无反应，而根因是投射问题，不是一个合法的拒绝。
需要满足的条件，以及要补的东西：
不能留遮罩：确认 BeginTraining 不走 sendReqWithMask；如果走了，要确认网络层在收到任何应答时都会移除遮罩。这一点材料未提供。
“Begin 类同 useItem 没有本地预扣”目前是【推断】：你给出的逐字证据只覆盖了 USE_ITEM。要在 BeginTraining 的发送点上方 40 行内，再做一次同样的 grep。
每次拒绝都写一条 warn 级日志并计数，格式如 BeginTraining reject skill=<id> reason=notLearned，并纳入第 3 节”分叉信号”的那张 cap 为 0 的表。一旦出现，就去修投射，不靠拒绝码兜底。
D1 的补法（不动 flow 层）：impl 里直接读取 Cocos 自己的全局对象 cc.director.getScene().name，用它判断当前场景。这读取的是客户端运行时，不是 bootstrap 的状态，所以不新增对 bootstrap 契约的依赖。场景名是否就是 ‘gamescene’，属于【推断】，需要实测确认。另外，live 的 selfCheck 增加返回 missingRequired:[…]：impl 内部持有 required 列表，自己计算差集，只返回缺失的那几个 id，不会撑爆命令通道。验收器断言这个数组为空。
6. 反例
个人练功关不掉门派界面：玩家在门派练功界面（isSchoolLiang 为 2）里选择个人练功，请求带着 isCollective:0，你的实现不发这个字段，客户端不进入 :120523 的分支，门派界面不关闭，普通练功界面也不打开。32/32 的验收如果没有覆盖”从门派界面切换到个人练功”这一步，就测不出来。
live 里的跳过依然看不见：live 进程里 harness 缺失，clock:liveIsReal 被跳过；同一次热重载又新增了一条检查，checkedCount 依然是 1234，failed 依然为空。构建期的 id 闸门全绿，因为构建期 harness 总是存在。
技能键形不一致，导致全部练功被拒：存档里 skills 是 [{id:101,lv:3}, …] 这样的数组，s.skills["101"] 取到 undefined，所有 BeginTraining 都返回 4 并且静默。玩家看到的现象是：练功按钮点了没有任何反应。
礼包嵌套漏判：礼包 A 只能从掉落里拿到，它的效果会给出物品 B，而 B 是一个需要服务端落地的未建模物品。如果可获得性只看三张来源表、不做 Grant* 不动点，B 就会被判为”不可获得”，(b′) 不拒绝它，B 被使用时物品就丢了。
第 1 档选错了提示：useItem 选了 4，而 4 在 :64904 弹出的提示其实是”等级不足”之类的文案，玩家被误导，以为是等级问题。按 R2 的规则，第 1 档里有多个码可选时，必须按提示文本来选。
先推进快照、再判定：某一次验收全绿，但同一轮里登记表新增了一条，如果 CI 先刷新快照、再用快照做 G1 判定，那么 base 已经包含了这条新登记，G1 永远判不出来。
成功码被误用为拒绝码：如果某个 Begin 类 handler 用 eRet:2 表示拒绝，客户端会照常进入成功分支，并执行 getSTimestamp() - beginTime，而这时 beginTime 根本没有写入，结果是 NaN，或者一进去就判为已完成。
7. 假设
A1：:120523 里的 e.isSchoolLiang 来自客户端的模型或 UI 状态，而不是请求本身；集体练功的请求不需要进入这个分支。如果门派集体练功其实也依赖别的字段来关闭界面，第 1 节第 1 条的规则仍然成立（照常回声），但反例 1 的触发路径需要重新确认。
A2：存档里的 skills 以技能 id 字符串为键。如果不是，第 1 节第 2 条失效，反例 3 成为一个现存缺陷。
A3：BeginTraining 不走 sendReqWithMask，或者网络层会在收到任何应答时移除遮罩。如果不是，第 5 节的”接受第 2 档”失效，必须在 BeginTraining 的回调或网络层里找到一个能清除遮罩的码；如果找不到，拒绝时就要改成”应答 eRet:1，但不推进任何状态”的退化方案，而这需要再次评审。
A4：通用网络层不会统一拦截 eRet 4 和 5。如果会拦截，第 2 节 R3 的判定要把 genericIntercepts 加进去，BeginTraining 也许因此能有第 1 档可选。
A5：cc.director.getScene() 在 impl 运行的上下文里可以访问。如果不能访问，第 5 节第 4 条的 D1 补法失效，只能回到 R12 的 flowCheck 方案，并且需要重启。
A6：验收报告会被归档，并且可以被下一次运行读到。如果不能，第 4 节的锚点不成立，哈希链只能防止”改了中间一行”，G1 的判定基准可能被整段改写。
A7：客户端不认识的 Effect 码，不会发出 useItem。如果会发出，第 3 节”不可达”那一类必须重新纳入取证。
