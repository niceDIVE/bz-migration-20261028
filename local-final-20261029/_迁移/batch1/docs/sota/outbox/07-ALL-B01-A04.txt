===== 第三部分：材料 B01（任务进度状态机）=====

【现状】
- 配置表里 4842 个任务，字段：TaskID、Type、Require（前置）、SpRequire（完成时必须携带的物品，格式 "物品id,数量|物品id,数量"）、Reward（奖励 = 掉落表 id）。
- 客户端自己算"任务显示状态"；服务端只被问两件事：接任务（acceptTask）、交任务（getFinishTaskAward）。
- 客户端提交完成时**不会**告诉服务端"我打了多少只怪 / 采了多少个东西"，请求里只有 taskID。
- 我现在的实现是权宜之计：接任务时按 SpRequire **自动补齐所需物品**，于是"完成任务"永远成立；交任务时按 Reward→掉落表 展开发奖，并用"已发奖励名单"防重发。
- 结果：任务能一路点下去，但**任务内容没有真实进度**（没有计数器、没有"杀 N 只"、没有"到达某地"）。

【约束】
1. 客户端一行不改，它不会上报击杀/采集计数。
2. 只能从两类信息推断：客户端请求里带的参数、以及它发出的其他请求（例如打怪可能有独立的结算请求）。
3. 单玩家离线；不允许数值凭空增加；重复提交必须幂等。
4. 配置里的 Require 是 "flag,taskID,param|..." 的结构串，不是裸 id 列表。
5. 存档只有一个 JSON 文件；新增字段必须能通过版本迁移引入。

【我要你回答（B01）】
1. 在"客户端不上报计数"的前提下，任务进度有几种可行的建模方式？每种的先决条件（需要客户端发哪些其他请求）、精度、代价各是什么？给对比表。
2. 如果只能靠"打怪结算请求"和"采集/使用物品请求"去推断进度，推断逻辑应该放在 L2 还是 L3？如何保证"同一次打怪不会同时推进两个任务、也不会被重复计数"？给去重的键设计。
3. 给出"任务进度"的存档字段设计（要支撑：多任务并行、离线补算、跨版本迁移、进度回退守卫）。
4. 给 5 条可翻译成代码的断言，专拦：重复计数、跨任务串味、进度回退、已完成任务被重开。

【B01 输出格式】
B01-1 结论（≤5 句）
B01-2 建模方式对比表（方式 / 先决条件 / 精度 / 代价 / 适用任务类型）
B01-3 推断逻辑归属（L2/L3）+ 去重键的构造公式
