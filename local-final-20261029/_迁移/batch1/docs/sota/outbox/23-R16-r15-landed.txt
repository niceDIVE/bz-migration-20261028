【三、两处我反过来纠你的事实】

**A. 那条"已知红"的归因是错的 —— 它不是 useItem，是 `upgradeSkill` 缺 `skillArr` 的无效请求。**
原断言（`test\core-test-server.js` 第 62-67 行改前）：
```
// T5 upgradeSkill：skch 增量
{ … const r = s.dispatch('User', 'upgradeSkill', { skillID: 1262 });
  assert.deepStrictEqual(r['User.upgradeSkill'].note.skch['1262'], [1, 0, 0]); … }
```
请求**没有 `skillArr`** → 走 `bz-rpc-server.js:1143-1146` 的无效分支 → `eRet:1`、`note.skch = {}`、**一个字节都不落盘**。
所以 `note.skch['1262']` 恒为 undefined：不是"期望形状从 [1,0,0] 变成 [lv,0,1]"，而是**这条请求根本不会建技能**。
你给的两条依据（1262 已在 skills、useItem 已学会回 5 不带 note）本身都对，但对这条测试不适用。
处置：把断言改成"无效请求不写技能、不落盘"的等价校验（`eRet===1` + `note.skch` 为 `{}` + 账本无 1262 + `readSave(SAVE_KEY)===null`），
**没有**删断言、**没有**改成永真、**没有**动请求。正向"skch 增量"覆盖在 `upgrade-skill-target`（`[15,0,1]/[17,2,1]/[5,6,1]` 真写）与 `r06-medicine-scholar`（已学会 eRet:5 不扣）里。
⇒ 结论：把它定性为"期望过时"是对的，但"过时"的原因是**请求无效**，不是形状变更。

**B. "毫秒时间戳"这条不能对整份产物做 —— 会误杀配置数据。**
实测产物里有 **214 个** 13 位毫秒字面量、43 个不同值（`1792572970629`、`1739116799000`…），全部是活动的起止时间，
是**真值**，不是生成时刻。照"只许 GEN_NOW"一刀切，会逼着人去改这些数据（把真值改坏）。
所以我把断言收在元数据行上：`BZ_SHAPES.__meta` 那行 + 头部注释。`__meta.gen` 现在是 `new Date(GEN_NOW).toISOString()`
（`2026-10-22T…` 固定值），两次构建 `ver` 相同（实测 `hf54b63bc` 连跑两次一致）。
