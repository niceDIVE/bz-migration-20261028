## D1 目标与完成定义

**结论**

"全部内容"必须先变成一个能算出来的集合，否则"还原完了"判不了。定义如下（可执行）：

```
U = 动作宇宙 ∪ 效果族宇宙 ∪ 任务/成就条目宇宙
动作宇宙   = { a | a ∈ HttpConst ∪ HttpConst3 ∪ (其它 HttpConstN)，且 send(a)=1 ∧ on(a)=1 }
            // 目前可数部分：M1 中 send∧on = 711（0110:634 + 1110:62 + 1111:15）【复算】，与全量 §十三 的 711 一致；
            // HttpConst3 的 128 个键的 send 列材料未提供
效果族宇宙 = 76 族中 SEND ∪ GATED = 43 族（全量 §九）
条目宇宙   = 任务表行 ∪ 成就表行（成就 2113，全量 §十一 #4；任务表行数材料未提供）

每个 u ∈ U 恰好落入一类：
  GEN     客户端代码 + 客户端表足以决定应答与状态变化 → 由生成器产出
  RULE    规则数据在客户端表里，但要一行声明式规则把表接到账本 → 规则表一行
  CAPTURE 规则数据不在客户端（例：Effect 13 礼包内容，全量 §九 0 命中）→ 只能来自原服应答样本
  OUT     项目边界排除：付费（PAY_ACTION_RE → eRet:4，全量 §二）；
          需要其他真人玩家的内容【推断】（例：USER_PVP 读 o.EnemyData，M2 第 15802-15810 行；FriendList/rankList 同理）

完成(u) :=  (class(u) ∈ {GEN,RULE}   ∧ contractPass(u) ∧ ledgerPass(u))
         ∨ (class(u) = CAPTURE       ∧ (hasCapture(u) ? replayPass(u) : registeredHonestReject(u)))
         ∨ (class(u) = OUT           ∧ registeredHonestReject(u))
全部完成 := ∀u∈U: 完成(u)  ∧  |{u | class(u)=UNKNOWN}| = 0
还原率   := |{u | class∈{GEN,RULE} ∧ 完成}| + |{u | CAPTURE ∧ replayPass}|   除以   |U − OUT|
```

在"不架服务器、不伪造付费"（全量 §二）之下，"完全还原"的上界是 `|U − OUT − 无样本的CAPTURE|`，不是 `|U|`。这是边界本身决定的，不是工程问题。

假设：(H1) 分类只依赖客户端代码、442 张表、`templates.json` 与已有抓包；H1 不成立（例如还能连原服抓新样本）时，CAPTURE 类能继续转成完成，上界随之上移。(H2) "其他真人玩家内容"判 OUT 是【推断】；用户若把"单机假数据（空好友、只有自己的排行）"也算还原，这部分改判 GEN，上界上移。

**判据**

```js

assert(registry.every(r => r.class==='UNKNOWN' || r.evidence.length > 0));        // 无证据不许入类
assert(setEq(registry.filter(r=>r.kind==='action').map(r=>r.id), enumerateActionUniverse())); // 分母封闭
assert(count(registry, r=>r.class==='UNKNOWN') <= cap('unknown'));                  // 棘轮，只许降
```

**反例**

- 某动作 send=1 只在死代码里（例如入口被 `Map=0` 挡住，全量 §十一 #8），它进了 U 却永远测不到 → 还原率分母被虚高。需要把"入口可达"加进 `send` 判定，材料未提供可达性分析。
- 同一个动作在 rogue 模式和正常模式下读不同字段（M4 §3：rogue 的 `eco` 只认 `coins`），按动作计一行会把两种完成态混在一起。需要按（动作 × 模式）计。

**材料缺失**

`HttpConst3`（及是否还有 `HttpConst2` 等）的定义块位置与 send 列；任务表的行数。这两项都能在 D5 的 S1 里由执行方机械得到，不需要再送一轮。

## D2 架构分层

**结论**

当前策略层是"每个动作一个手写 handler、每个 handler 自己拼 `note`"（M4 §1–§5：ivch 有 10 个手写写者、eqch 9 个、eco 8 个）。这种结构下，边际成本 = 一个 handler + 一组 test + 一批 freeze 登记，与剩余量线性相关。支撑 D5 的目标分层是把它拆成四块，其中三块是生成物：

| 层 | 产物 | 由谁决定 | 手写？ |
|---|---|---|---|
| L1 契约 | `contracts.generated.json`：每动作 {必读字段, 开关字段(hasOwnProperty), 类型提示, 外键表} | 客户端代码（M2 升级版） | 否 |
| L2 账本 + 投射 | handler 只改 `s`；`note` 由 `project(diff(before,after))` 统一产出 | 存档模型 + M4 的映射 | 投射器写一次 |
| L3 规则表 | `rules.generated.json`：GEN/RULE 动作的 {前置, 扣, 给, 写标志} | 客户端表 + 客户端前置校验代码 | 否（RULE 行可人工补，但不写代码） |
| L4 分类登记 | `registry.json`（D1） | L1–L3 的产出 + 抓包 | 否 |

剩下的手写代码只有：信封层（已有）、投射器（一次）、规则解释器（一次）、CAPTURE 类里有抓包样本的个别动作的回放器。

假设：(H3) 客户端的应答消费都经过 `MessageCenter.on` 或 `g[I]` 直读（全量 §七 59325/59332），没有绕开 MessageCenter 的第二条消费路径。不成立时 L1 抽不全，契约漏字段。注意矛盾 4 已经证明存在"回调里直接读 `note.gemch`"这种路径，它仍在 MessageCenter 回调里，所以 H3 目前没被推翻。

**反例**

## D4 验证体系

**结论**

现有体系（K1–K3、K-cap、G3、G5、`approved-narrowing.json` 逐字段登记，全量 §十）对"防回退"是对的，但它把**每一次生成物的变化都变成一次人工登记**：形状一由契约生成，`check_shape_freeze` 看到的"发→不发"就会成批出现，每个都要手填 `escape:"closed"` + 客户端行号。这会把 D5 的边际成本打回逐项。因此：

1. **冻结对象从"产物字段"改成"生成器输入 + 生成器代码"**：冻结 `sha(M2 抽取结果) + sha(gen 代码) + sha(442 表)`；产物变化若能由输入变化解释，则自动放行。
2. **`approved-narrowing` 的证据由契约自动填**：一条"发→不发"如果对应字段在契约里是 hasOwnProperty 开关、且有客户端行号，就自动生成登记行；只有契约里找不到依据的才落到人工。
3. **加一个运行时检查**：MessageCenter 吞异常（全量 §十二 `npcArr` 例），所以"设备上不报错"不是证据。在进程内包一层监听器记录异常，作为每个动作的硬判据。
4. 本轮"未验证"的三项（自检 1242、验收 38/38、freeze 退出码 0，全量 §十三）是 D5 S0 的第一个判定，不跑就没有基线。

以上做法与"消费者驱动契约"同构：客户端是 consumer，只声明它读的那部分应答，provider（我们）对照验证。`[检索 2026-10-23] docs.pact.io/getting_started/how_pact_works（页面日期 2024-12-23）`：每个 interaction 描述"A minimal expected response - describing the parts of the response the consumer wants"。变形：我们没有 consumer 的测试代码，契约要从客户端源码抽，不是由 consumer 团队手写。

假设：(H5) 生成器的输入是确定性的（同输入同输出）。不成立时（例如生成器依赖目录遍历顺序或时间戳——`__meta.gen` 字段就是时间戳，全量 §十五 #4），输入哈希相同而产物不同，自动放行会放进真变化。

**判据**

```js
assert(sha(genOutput(inputs)) === sha(genOutput(inputs)));                  // 生成确定性，__meta.gen 排除在哈希外
assert(freeze.inputsHash === sha([m2Extract, genCode, cfgDump]));            // 冻结的是输入
assert(narrowings.filter(n => !n.autoEvidence).length <= cap('manualNarrowing')); // 人工登记只许降
// 运行时：进程内包 MessageCenter
const errs = []; wrapMessageCenter(e => errs.push(e));
for (const a of genActions) dispatchSynthetic(a);
assert(errs.length === 0, JSON.stringify(errs.slice(0,5)));
```

**反例**

- 契约判"字段不读"而客户端实际在 callee 里读（矛盾 6，`LoadGame`）。自动放行会把"该发的字段不发"当合法收窄放过去，freeze 体系反而为错误背书。所以第 2 条只在 S2（跨函数抽取）完成后启用。
- `dispatchSynthetic` 只证明"监听器不抛"，不证明"界面状态对"。例如 `ivch` 发了增量，监听器不抛，背包数量错（全量 §七"能反复卖"）。所以运行时检查要和 D3 的模型等价断言一起用，不能单独当完成判据。

**材料缺失**

无。上面的检查都只依赖现有工具链和材料里已有的文件。

## D5 工作量与路径

**结论**

**①(a) 有没有一种重构，能把边际成本压到与剩余量无关？**
部分有，部分没有，边界由"规则数据在不在客户端里"这一条事实决定：

- **有（GEN / RULE 类）**：「契约生成（L1）+ 账本差分投射（L2）+ 表驱动规则（L3）+ 机械分类（L4）」。生成器和解释器是一次性成本；之后每多还原一个动作 / 一族效果 / 一张表，代价是"生成器多吃一行输入"，不随剩余量增长。
- **没有（CAPTURE 类）**：规则和数据只在原服（例 Effect 13：442 表与客户端资源全文 0 命中，全量 §九）。这类的边际成本由"取证"决定，每条要一个原服样本，与工程方法无关。同类工程的情况一样：`[检索 2026-10-23] talk.trinitycore.org/t/making-of-tc/31747（2018-07-25）`：客户端数据库含 spells、skills、items 等静态信息，"Other data for example quests, loot … are not available"；`[检索 2026-10-23] talk.trinitycore.org/t/how-does-trinity-code-work/28762（2012-12-07）`：掉落模板靠"look at a lot of sniffs"。变形：TrinityCore 能持续抓包，因为原服在线；我们能不能抓新样本，材料未提供（见 ②）。
- **排除（OUT 类）**：付费、多人内容【推断】，由项目边界决定。

现有数据能先给出规模（【复算】，M1.tsv × M2）：客户端 send∧on 但我方无 handler 的 **634** 个动作里，**326** 个有内联字段读取（契约现在就能生成），**182** 个只有命名处理器（要展开 520 个函数体），**124** 个内联但 0 读取（**不能**直接当"只要 ACK"，见矛盾 6），2 个混合。另有 `HttpConst3` 128 个未计入。

**①(b) 判定条件（可执行判据）**

```js

     contract[a].closed                                   // 跨函数抽取完成：无未展开命名处理器、无动态键读取 o[k]
  && contract[a].fields.every(f => provenance(a,f) !== null);
// provenance(a,f) ∈ { 'req.p.<x>', 's.<key>', 'cfg.<table>.<col>', 'const@<file:line>', 'time.now' }，找不到即 null

// 动作级：可规则化（RULE）

  && contract[a].closed
  && stateDelta(a).every(op => op.source.startsWith('cfg.') || op.source.startsWith('clientPrecheck@'));
// clientPrecheck@file:line = 客户端发请求前做的本地校验/扣费显示代码（例：货架价 price: s.BuyPrice，scripts2.js:46443）

// 效果族级：族 F 可生成 ⇔ 存在 USE_ITEM 的开关字段 f 及其 getItem 表 T，和 Data 列 c，使族内所有物品的 Data_c 都是 T 的键
const famGEN = F => switchFieldsWithTable('USE_ITEM').some(({field, table}) =>
  ['Data1','Data2','Data3','Data4','Data5'].some(c =>
    items.filter(i => i.Type===2 && i.Effect===F).every(i => keys(cfg[table]).has(String(i[c])))));
// 可用的 (字段,表) 对已在 M2 USE_ITEM 条目里：formulaID→"formula"(64794)、taskID→"tasknew"(64789)、
// dogid→"npc"(64817)、weaponSkinId→"weaponskin"(64878)；titleID→成就数据(64812)

// 条目级（任务/成就进度）：条目 e 可生成 ⇔ 其条件类型列的取值有一个已登记的领域事件源
const condGEN = e => eventSources.has(condType(e));      // condType 的列名材料未提供
```

**①(c)** 不适用于 GEN/RULE 类（①(a) 已判"有"）。对 CAPTURE 类，卡在一条事实上：**规则数据不在客户端里**（Effect 13 已实测 0 命中）。这条事实本身不需要更多材料就能判"无"。

**①(d) 反例：这条路径在哪些场景下退回逐项**

1. **动态读字段**：客户端用 `o[key]`、`for..in` 遍历或把应答对象传进通用组件（例：`addShowRewardUI1(a.rewardArray, 0, a.equipObj, …)`，M2 USE_ITEM 64768）。契约只能得到"对象被消费"，得不到字段集 → 该动作 `closed=false` → 退回人工读代码。
2. **同字段多语义**：`ivch` 在 64675 / 64914、`eqch` 在 64685 / 64917（D2 反例）。投射器需要按动作加例外，每个例外是一条人工。
3. **规则在客户端但不在表里**：客户端前置校验写死在代码分支里（例：Effect 15 的 `numDeaths==0` 判断，`index.js:64423-64428`），`provenance` 落到 `const@file:line`，能生成；但如果原服规则**比**客户端前置更严（客户端只做一部分校验），生成结果比原版宽松，契约检查发现不了。
4. **随机性**：开宝箱、钓鱼、洗练（`washAdditionalArr`）的结果分布在原服。客户端表最多给出候选集，给不出权重 → 落 CAPTURE。
5. **跨动作状态**：任务进度、成就、七日活动依赖"之前做过什么"。`condType` 列不能一对一映射到事件时（例如"累计在线时长"），每种条件类型要手写一个事件源。

假设：(H6) 442 张表就是客户端在运行时用到的全部配置；若运行时还从网络下发配置（例 `activityResource`，全量 §八 `scripts2.js:31067-31086`），这部分表不在 dump 里，`provenance` 会误判为 null，GEN 被低估。(H7) M2 的抽取在内联体内是完整的；矛盾 6 已经说明跨函数不完整，S2 就是为此存在。

## D6 工作流程

**结论**

执行方不做路线判断（全量 §一），所以"下一步做什么"必须由 `registry.json` 机械给出，不靠人选：

```

  next = registry.filter(r => r.class==='UNKNOWN')
                 .sortBy(r => -unlocks(r))       // unlocks = 该行转类后能连带完成的条目数（例：族的件数、条件类型下的条目数）
                 [0]
  只改生成器 / 解释器 / 投射器 / 分类器，绝不直接改 generated 产物
  一次提交 = 源码改动 + 重新生成的全部产物 + registry diff

  推设备 = 只在门禁过后；推完校验 bz_ready.impl === 产物版本串，否则回滚到上一个版本串
```
