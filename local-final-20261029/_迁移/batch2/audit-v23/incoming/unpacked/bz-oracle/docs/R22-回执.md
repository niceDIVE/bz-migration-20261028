3. **HttpConst3 的键数对不上。** R21 矛盾 #5（复算自 M2）是 131 处 `on` 注册、128 个不同键。R22 的定义块是 145 键，构成为 116 个 `User.*`、11 个 CTS_、17 个 STC_、1 个数据对象。

   ```

## D1 目标与完成定义

**改动：一个动作"完成"的定义加入拒绝分支。**

```
DONE(a) ⇔ 成功分支 PASS
        ∧ ∀ 拒绝理由 r ∈ Reasons(a): (存在真服样本 ∨ rules.json 有带 source 的规则)
                                     ∧ 我方回 {errorCode:code(r)} 且存档不变

- 当前只有 `User.saleItem` 有已证的拒绝理由：非法 uid、无此物品、已穿戴装备，三者都回 errorCode=1。
- 其余动作的 `Reasons(a)` 未知。按 R21 D1 的口径，这些动作只能算"成功分支完成"，不能算 DONE。

## D2 架构分层

拒绝形态成为第二种应答形态，从协议层一直贯通到裁判层。v2.3 已落地，各层的改动和断言如下：

| 层 | 改动 | 断言（selftest 第 23 步） |
|---|---|---|
| 投射器 | handler 返回 `{errorCode}` 时原样裸发；夹带字段或改了存档都会抛错 | 三条 |
| DSL | `guard.reject:"errorCode"`，并支持 `pre:true`（在参数校验之前判断） | uid=90001 → `{"errorCode":1}` |
| 回放服务器 | 拒绝形态不套信封 | 第 9 步不误杀 |

**反例**：如果某个动作的拒绝在真服上**不是**裸形态（比如回 `{"code":200,"MsgData":{"eRet":0}}`），v2.3 的 `rejectForms` 识别不到它，会按成功契约去检查，可能误报 L1.REQUIRED。`rejectForms` 目前只登记了一条，依据只有 saleItem 的 3 个场景。

## D3 协议与状态

1. **两种应答形态**：成功 = `{"code":200,"MsgData":…}`；拒绝 = 裸 `{"errorCode":N}`。
2. 【推断】三种不同的拒绝理由都回 errorCode=1，所以**客户端按 errorCode 区分不了拒绝理由**。我方 handler 只需要正确判断"拒或不拒"，不需要还原具体理由。
   - **失效条件**：只要有任何一个真服样本回出 errorCode ≠ 1，这条推断就作废，`Reasons(a)` 必须逐条带上 code。
3. **存档语义**：拒绝时存档不变。真服上无法直接观察存档，只能观察"拒绝之后 LoadGame 全量和拒绝之前一致"。
   - 判定命令（设备侧）：`LoadGame` → 发拒绝请求 → `LoadGame`，然后 diff 两次 MsgData。diff 必须为空，`volatileKeyRe` 匹配到的键除外。
4. **DNS 分裂**（R22 §一）：bzgf 域名在 PC 上解析到已失效的 IP，在设备上能通。条件：所有抓包和真服请求都从设备侧发起，或者 PC 侧手工 pin 到设备解析出的 IP。har2cases 的 `--url-re` 要同时匹配域名和 IP 两种形态。

**反例**：如果真服在连续收到非法请求之后触发风控（封号、限流、静默丢包），第 3 条的"拒绝前后 LoadGame 一致"可能因为账号状态被服务端改动而失败，并被误判成"拒绝改了存档"。材料没有提供原服的风控行为。

## D5 工作量与路径

1. **CAPTURE 类重新定价**（原服可达）。按"能不能安全、重复地取样"再分三档：

   | 子类 | 判据 | 处置 |
   |---|---|---|
   | CAPTURE-R（可重复） | 在真账号上能反复触发，而且不消耗稀缺资源或一次性资格 | 进入 GEN，L4 模板直接从 HAR 取 |
   | CAPTURE-1（一次性） | 首充、新手、限时活动、一次性奖励这类，同一账号只能触发一次 | 每个账号只有一个样本；L4 只能对照这一个样本，L3 的分支覆盖做不到 |
   | CAPTURE-X（不可取） | 付费、已下线的活动、依赖其他玩家状态 | 维持 OUT |

   - 还原率上界 = `(|GEN| + |RULE| + |CAPTURE-R| + |CAPTURE-1|) / |U_action|`。【推断】在 R22 给出的材料里，这三档各有多少个，**材料未提供**，所以"上界上移多少"现在判不了，只能说"上移，幅度 ≤ |CAPTURE|"。

   - CTS_ 的 11 个键对应的线上动作名，材料没有给。如果其中有和 M1 里 value 重名的，并集会少于 1125 + 145。
3. **HttpConst3 的 116 个动作进入注册表**：当前状态是 NO-CONTRACT（L1 判 FAIL）。下一步是把 scripts3 的 `on` 注册纳入 `build-contracts.js`。前提是 ⓪.3 的逐键表已经出来。在那之前，这 116 个动作一律不能进 GEN。

## D6 工作流程

**真服操作的红线**（用户已授权抓包和真机 L2，以下是授权之下的执行约束，不是新的规则建议）：

1. **只读和必拒请求**（LoadGame，以及参数非法、已穿戴装备这类注定被拒的请求）可以在真账号上直接做。
2. **会改状态的请求**（卖出、购买、收功）每次执行前后都各做一次 LoadGame 快照，并且完整录入 HAR。做不到前后快照的，不执行。
3. 每个动作一个会话，单个会话内的请求速率 ≤ 客户端正常操作的速率。【推断】原服风控行为材料没有提供，取保守值。
4. **CAPTURE-1 类动作禁止在主账号上"试一下"**，因为一试资格就没了。必须先在 registry 里登记，再执行，样本存档备份。

**下一步顺序**（每一步都有可机械检查的完成判据）：

1. 跑 v2.3 的 selftest，23 步全部通过。之后 saleItem 重新判级（⓪.6）。
2. 在设备侧做 saleItem 三项（D4.3）。完成判据：M09 被击杀，击杀率 131/131。
3. 拒绝用例的 L0 观察（D4.2）。完成判据：`toastTexts` 或拒绝期望已登记。
4. 出 HttpConst3 的逐键 send/on/通道表（⓪.3），按 ⓪.4 做 M2 字段级断言。完成判据：两处矛盾都有定论。
5. 补 CompletionEvent 的取值集合（D5.4）。完成判据：condGEN 的可行率出了数字。

**反例**（针对整套做法）：如果原服的版本和设备上的三包不是同一个版本（R22 只核对了"tools 三包 ≡ 设备生效代码"，没有核对服务端版本），那么真服样本反映的是**新服务端**的行为。我方按这些样本写 handler，旧客户端可能不认（比如字段新增或重命名）。判定方法：拿 L1 对每个真服样本做检查。如果出现 `UNKNOWN_FIELD` 或 `REQUIRED` 缺失，说明服务端和客户端已经分叉，该样本不能直接当 L4 模板用。
