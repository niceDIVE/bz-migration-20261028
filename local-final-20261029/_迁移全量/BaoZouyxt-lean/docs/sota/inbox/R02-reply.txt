硬伤候选三：出售截断之后，铜钱必须按截断后的数量计算。 如果按请求数量计算，叠加出来的物品就会被变现成真钱。补一条断言 A7：coinDelta === price(id) × min(req, realBag(id))。
2. Q1：C = 0 在什么条件下会错，以及判别检查
会错的条件（任意一条成立，原版的 C 就可能是 need）：

网络分发层存在一个通用的应答钩子，会对任何接口应答里的物品字段做增减（例如 itemObj、delItem、costItem 这类字段），原版服务端借此在 getFinishTaskAward 的应答里下发了扣减。

Type 12 或 13 在 updateTaskData 里有自己的分支，并且这个分支会扣物品；你只给出了 case 2（空分支）和 case 3 的代码。

Type 2/12/13 任务的 finish_action 或 CompletionEvent 配置了非 0 的值，而客户端对这些值的处理函数里包含扣物品的逻辑。
判别检查（只读源码和配置，可以直接执行）：

3. Q2：叠加的误拒最小化
(a) 截断 vs 拒绝

截断并返回成功（现状）
拒绝（eRet≠1）
玩家看到什么
“操作成功”，数量却不变；对于使用后有效果的物品（药品、礼包），如果效果是客户端按成功应答在本地结算的，玩家会白拿一次效果
客户端走它自己的错误分支；如果分支只是弹一条提示，玩家明白操作失败了，状态也不会变
风险
成功的应答如果触发了客户端本地的效果，或者本地扣减，就会产生凭空的价值，或者让视图分叉
如果错误分支处理得不好（卡住界面、弹”网络错误”、或者自动重试），体验比截断更差
哪个更小：当使用和出售回调里 eRet≠1 的分支只弹提示、不改任何状态时，拒绝的后果更小，因为它不会制造”假成功”，也就不存在白拿效果的问题。如果错误分支会卡住界面或者自动重试，就保留截断，同时把截断后的效果量也截到 0。判定方法：读 useItem 和 saleItem 回调里的 eRet 分支（只读源码即可）。
(b) 最不伤玩家的三种处理（按顺序）
在应答里携带纠正值。 前提是使用、出售回调（或者网络通用钩子，见 Q1 第 1 步）会消费应答中的物品字段。如果会，就在应答里直接下发该物品的投射数量（真实库存加叠加量），这样不需要推送通道，也不会绕开应答路径。同一个机制也能修好硬伤候选二：如果 acceptTask 的回调会消费物品字段，就在它的应答里带上叠加量。
拒绝，并使用客户端已有的”数量不足”错误码。 在客户端的错误码表或提示文本里搜 数量不足、不足、not enough，复用一个已经存在的码，让玩家看到的是一条有意义的提示。
截断并返回成功（现状），加日志。 只有在前两种都不可行时才用，而且效果量必须同步截断。
(c) 选”进程内直接改客户端模型”的两条代价
出现了第二条写入路径。 服务端代码直接改客户端状态后，A01 的契约测试只比对应答，再也看不见这部分副作用；自检或沙盒实例只要拿得到同一个 window，就能改到活客户端的模型，从而污染它。
耦合到客户端的私有结构和时序。 模块路径和字段名一旦随客户端热更新变化，推送就会静默失效；如果在客户端自己处理应答的过程中插入修改，客户端后续的处理会覆盖或者重复应用这次修改，产生竞态。
4. Q3：Repeat 刷奖励（66 个任务）
(a) 要不要堵：要堵。判据是：一个循环的净资源消耗为 0、而奖励大于 0，这不可能是设计上的循环【推断】。原版里只要满足下面两条中的任意一条，循环就不是零成本的：要么每轮都要消耗物品（Q1 判出 C = need），要么有次数或周期上限（由 Repeat 的取值语义决定）。 先查一个现状问题：你现在用来”防重发”的已发奖励名单，对 Repeat 任务是怎么处理的？如果名单会挡住第二次领奖，那么循环其实已经被堵住了，但正常的重复任务同样被误伤。如果名单在重新接取时会被清掉，那么循环就是开着的。这一点材料未提供，请先读一下自己的实现。
(b) 不误伤正常重复任务的堵法：叠加只帮第一次，之后的循环必须用真实库存。
// 投射：Repeat 任务一旦领过一次奖励，就不再为它计算叠加
function overlayNeed(t, st) {
  if (t.Repeat !== &#39;0&#39; && hasRewardedOnce(st, t.TaskID)) return 0;
  return need(t);
}
// 交任务断言（只对 Repeat 任务的第二次及以后生效）
assert(!(t.Repeat !== &#39;0&#39; && hasRewardedOnce(before, t.TaskID)) ||
       all(items(t), function (i) { return realBag(before, i.id) >= i.n; }));
为什么不会误伤：手里有真实物品的玩家照常可以重复做任务；没有物品的玩家只会失去零成本的循环，而这本来就是要堵的。实现上需要一个领奖次数记录，比如 repeatCount[taskId]。如果现有存档里没有这个字段，就通过 v5 迁移引入，初值统一设为 0，不根据历史去推算。
(c) 去客户端源码里搜什么：
字段读取：.Repeat、["Repeat"]、Repeat==、Repeat>
可接取判定：在 judgeTaskFinishRequire（134394）前后 5000 行内找”已完成任务集合”的成员判断，例如 finishTask、doneTask、finishTaskObj、hasOwnProperty(taskID) 出现在 accept 相关函数里的位置
周期和次数：daily、resetTask、refreshTask、todayCount、repeatCount、times，以及中文的 每日、次数、今日
链式任务：.Chain，用来区分”可重复”和”链式循环”
判定规则：客户端如果允许对已完成任务再次显示接取入口，而且这个入口受 Repeat 控制，那么原版就允许重复领奖；如果找到了次数或日期相关的变量，以它的值作为上限。
5. Q4：359 种无来源物品
(a) 没有配置声明时，TaskGrant 和凭空发放有没有区别：没有区别。判据是：一次发放之所以合法，是因为能够从配置或代码里重新算出 (触发点, 物品, 数量)。既然 40 个非 SpRequire 列里都没有语义性的声明，所谓 TaskGrant 只是给凭空发放起了一个名字，事后无法审计，也无法和真实获得区分开。
(b) 语义保守性排序：只显示、不落库的叠加，比按配置发放并落库更保守。排序依据有两条，按优先级：
可逆性：把叠加代码删掉，存档就回到真实状态；而落库之后无法撤回。
可区分性：叠加不会制造 Q7 所说的”不可区分”状态；落库则会。
需要说明的是，叠加的保守性只对物品成立。它让任务能够交付，而交付之后发出的奖励是落库的，所以叠加并不是零副作用。这正是 Q3 必须单独去堵的原因。
(c) 第一个可落地的来源系统：建议优先做”物品开启型”，也就是使用某个物品时展开一张掉落表（宝箱、礼包）。前提是 item 表里有一列引用 drop 表的 id，这一点材料未提供。
为什么它比其他三个都省事：
它复用了已经存在的 useItem 请求和已经写好的”截断到真实库存”逻辑，不需要新增接口。
守恒关系是闭式的：消耗 1 个物品，展开 1 次掉落表。
天然幂等：请求重发时，物品已经扣掉了，第二次会被截断成 0，不需要去重键。
对比之下：打怪掉落依赖战斗结算去重，B01 已经证明拿不到这个条件；任务奖励链能覆盖的 74 种已经用完了；商店表没有导出。
验证命令：在 item 表的每一列里统计取值落在 drop 表 id 集合中的比例，找出取值大部分命中 drop id 的列。再拿 Fact D 同样的对照组方法排除数字巧合。

6. Q5：fightTaskObj 的重启保真
选择：② 加 ③，也就是不持久化、接受重启后需要重打，服务端在交任务时不做校验（维持现状）。
理由：三个 bundle 里没有任何应答字段会给 fightTaskObj 赋值（事实 E），这说明原版服务端同样无法在重启后恢复这个标记。所以”重启后要重打”大概率就是原版行为【推断，依据是客户端没有接收这个标记的代码路径】。
选 ① 会不会破坏原则：会。 原因有两个。第一，客户端没有任何从应答接收这个标记的入口，要让它生效只能在进程内直接修改客户端模型，这超出了”只回投射”的范围。第二，这等于给游戏增加了一项原版没有的行为。
如果仍然选 ①，写在哪一层：
不能写进 L5 的投射函数。投射函数必须保持纯函数，自检和沙盒都会调用它。
应该写在网络层替换的”活连接出口”：真实的 XHR 回调把 LoadGame 应答交给客户端之后，在同一个调用链里执行，并且用 ctx.live === true 做门控。自检和沙盒实例构造的 ctx 里没有活客户端的句柄，所以不会触发推送。
持久化的形状是 fightDone: {taskId: npcId}，按任务存而不是按 npcId 存，这样任务完成时才能对应清除（客户端是按 SpRequire 删除的）。需要通过 v5 迁移引入，初值设为 {}。
7. Q6：2629 个死任务
(a) 要不要把死任务的 SpRequire 从叠加里排除：不要。判据是：叠加只针对进行中的任务计算，一个真正的死任务根本不可能出现在 questAccepted 里，排除它不会改变任何结果；反过来，被误判为死的任务一旦被排除，就会少给叠加，造成误拒。 可以加一条监控代替排除：if (questAccepted 中出现被标为死的任务) log(&#39;reachability-gap&#39;, taskId)。这条日志本身就是可达性定义有漏洞的证据。
(b) 最可能漏掉的一类入口：由其他任务的事件列直接下发的任务。也就是完成或接取某个任务时，通过 Chain、CompletionEvent、finish_action、receive_action、transfer 这些列自动接取的后续任务。这类任务在你的图里没有对应的边。
验证检查：对每个死任务的 id，统计它在可达任务的上述各列中作为数字 token 出现的比例。再按 Fact D 的做法设对照组：用随机抽取的、不存在的任务 id 去跑同样的统计，以排除数字巧合。命中率显著高于对照组的列，就是漏掉的入口列。

另外，定义本身还有一个漏洞需要顺手检查：你把 Pre-Require 里用 | 分隔的多个前置当成了”全部满足（与）“还是”满足其一（或）“？如果实际语义是”或”，而你按”与”来算，死任务的数量会被严重高估。检查方法：读客户端里解析 Pre-Require 的循环，看它是在遇到第一个不满足时就返回 false，还是在遇到第一个满足时就返回 true。

9. 反例：派生叠加 + C=0 会静默出错的场景
局中接任务后交不了。 前提是 acceptTask 的应答回调不处理物品字段（硬伤候选二）。玩家接下一个 Type 2 任务，客户端本地背包里没有叠加，NPC 就不给”完成”入口。不会报错、也没有日志，玩家只会觉得任务坏了，直到重启。
Type 2/12/13 的需求物品是装备。 叠加跳过了 item.Type = 1 的物品，而客户端的 judgeItemRequire 走的是 getItemNum。如果 getItemNum 对装备返回的是 PlayerEquip 里的数量，那么这类任务在 08 号之前靠自动补齐能交，现在会永久卡住。检查方法：统计 700 条真物品需求里 item.Type = 1 的条数，以及 getItemNum 对装备 id 的实际返回路径。
Repeat 任务的奖励落库。 在 Q3 的堵法上线之前，66 个任务的零成本循环会持续把奖励写进存档。背包守恒、md5 检查、A1–A5 全部通过，没有任何守卫能察觉到。
NPC id 和物品 id 撞号产生幽灵物品。 前提是没有按 Type 过滤（硬伤候选一）。进行中的 Type 3 任务会给客户端叠加一个同号物品，玩家去使用或出售时被截断。
原版其实是 C = need。 前提是 Q1 的第 1、2 步找到了通用钩子。那么 Type 2 任务的道具永远不会被消耗，一份道具就能满足所有共用它的任务；这本身不报错，但改变了游戏的资源流。
10. 假设
H1：getItemNum 对非货币、非装备的物品只读本地背包模型。不成立时，叠加写进 itemObj 不起作用，A2、A3 通过了也没有意义。
H2：客户端不会把本地背包回传给服务端。不成立时，叠加的数量会被当成真实库存回写，Q7 的硬规则会被破坏。
H3：Q1 的三项检查全部为否。不成立时，C = 0 失效，Q3(a) 的判据要改成”原版每轮都消耗物品”，第 9 节第 5 条成为现实。
H4：Repeat 的取值能从客户端源码里读出语义。不成立时，Q3(b) 只能使用”叠加只帮第一次”这一种保守堵法，无法实现按周期放行。
H5：item 表里有引用 drop 表的列。不成立时，Q4(c) 的首选来源失效，第一个来源要改成”商店”，而商店需要先导出商店表。
H6：可达性的唯一漏洞是事件列入口加上或/与语义。不成立时（例如存在由等级或地图触发的任务入口），Q6(a) 的监控日志会持续报出 reachability-gap，需要继续补充入口类型。
