1. 结论
最明显的错位是 (f) 的后半句被放进了 L4，排在最后。 第 3 项修复上线后，出售时服务端已经真正移除了物品，但不结算铜钱。也就是说，玩家每卖一次东西，价值就被不可逆地销毁一次，这是正在发生的数据损失，必须放到第 0 位止血，不能当作 L4 的守恒完善来处理。修复用 R02 的公式：coinDelta = price(id) * min(requested, real(id))。
观测 (g) 应该排在 L2 前面，而不是并列放进缺陷清单。 L2 先做哪个动作，取决于”哪些动作真被调用”，日志统计失真时，排序本身就是猜的。
装备属性很可能不是”补属性”，而是”补穿戴状态的投射”。 第 4 项只修了记账，但 newApplyBonuses 遍历的是哪个字段里的已穿戴装备、这个字段有没有出现在 LoadGame 的应答里，材料未提供。见 Q1。
L4 先做不会拖累 L2，前提是先上”观察模式”（只记录、不拒绝），再逐个动作切换到强制。 见 Q5。
材料里有两处数字不一致： 配置表在第五节写 442 张，在 (a) 写 454 张；第三节第 1 项说叠加只在 LoadGame/sync 的投射里出现，但第 5 项和 R03 的 B 项已经在接任务和交任务时推送叠加。请在下一批里统一口径。
2. Q1：装备属性
只读检查步骤（不需要试玩）
读汇总入口：从 newApplyBonuses（143297）往下读，找到它遍历装备的那个循环，记下两件事。
循环的数据源是哪个字段，例如 RoleBaseInfo.xxx、roleObj.equip、每个槽位上的 uid 等。
对每件装备调用了哪个函数取属性。
读取属性函数：读 equipAttruteNum 和 equipStateAttruteMult（143320-143328）的函数体，用你已有的读表索引核对它们调用了哪些 getItem(x,"表名")，以及读的是哪一列（Property1..5/Data1..5、equip，或者 PlayerEquip 里的 data[2] attrs）。 判定规则：
只读 item 或 equip 表的列 → 基础属性来自配置。
读了 data[2] → 附加属性来自存档。
两者都读 → 基础属性来自配置，附加属性来自存档。
核对 equip 列是不是外键：如果第 2 步读的是 getItem(item.equip, "某表")，就对 item 表 equip 列的非零值做主键命中统计，同时用”每个值加 7”作为对照组跑一遍。这一步要先去掉零值，避免重犯 decompose 那次的错误。
读 parseEq 中 type==1 的分支：确认 type==1 时客户端是把 attrs 当作空，还是从配置里补全 attrs。
读穿戴状态的来源：用 grep -n "equipWeapon" 找到客户端在 equipWeapon 的回调里写了哪个字段，再看 LoadGame 的解析函数是否读取同一个字段。这个字段就是我们必须持久化并投射回去的东西。
如果 type==1 的属性全部来自 item 表，还要补什么
属性值本身不用补，但还有三件事要补：
穿戴关系：存档里需要有一个 equipped: {角色或槽位: uid}，并按第 5 步找到的字段投射到 LoadGame 的应答里。如果存档格式还是 v4，就要走迁移，初值从当前客户端视图里读不出来，只能是空的。
强化或等级状态：如果第 2 步发现 equipStateAttruteMult 读的是某个强化等级，就要找出这个等级存在哪个字段，否则倍率永远是 1。这一点材料未提供。
断言：每件已穿戴的装备都必须是持有中的装备，同一件装备穿戴的件数不能超过持有数量。
for (var s in save.equipped) { var u = save.equipped[s]; assert(save.PlayerEquip[u] && cnt(save.equipped, u) <= save.PlayerEquip[u][1]); }
如果第 2 步的结论是属性来自 data[2]，那 type==1 的”无附加属性”就是正确的，基础属性同样只需要上面的穿戴投射。只有在 type≠1 时才需要生成 attrs，而生成规则材料未提供，所以不要自己编数值。
3. Q2：活动面板内容
反推 dataArr 元素结构的方法
以读取方为准，不以写入方为准。 在 HomeActiveUI 里查 this.actDataMap 的所有读取点：
grep -nE "actDataMap(\[|\.)" scripts2.js
记下用来取元素的 key：如果是 actDataMap[r.number] 这类写法，key 就是 active_order.number；如果是下标，dataArr 就是按 tab 顺序排的数组。再记下取出元素后交给了哪个子 UI 的 setData。
读子 UI 的 setData 和它引用的成员。 读 DailyMissionUI.setData、SevendayActiveUI.setData 以及它们后续的方法，把每一个 e.xxx/this.data.xxx 的读取点整理成一张字段表，并按用法推断每个字段的类型：
.length 或 forEach → 数组
for in 或 hasOwnProperty → 对象
和数字比较或做算术 → 数字
拿去 getItem(x,"表") → 某张表的 id
用配置做旁证。 如果字段被拿去查 active 表，它的值域就应该在 active 的主键范围内；这一步同样要去零、加对照组。
标出每个字段有没有防护。 被 hasOwnProperty、|| [] 或 if (x) 包住的字段，返回空值是安全的；没有防护的字段，返回 undefined 就会抛 TypeError。
“先只让 tab 出来、内容留空”是否可行
可行，但需要同时满足三个条件，缺一个就可能再次卡住：
getActiveState 读到的每个字段都必须带上，并且类型正确：schoolActivityOpen、schoolArenaOpen、activeShowList、activeObj。如果 activeShowList 缺失，indexOf 就会抛错，整条回调中断。
允许出现零个 tab：如果 getActiveState 对全部活动都返回 false，onLoad 里不能出现 tabs[0].xxx 这类没有防护的读取。检查方法是 grep 出 getActiveSortData( 调用之后的 20 行，看里面有没有 [0]。
对第 2 步字段表里所有没有防护的字段，都返回空值，但类型要对：数组字段给 []，对象字段给 {}，数字字段给 0。时间字段给 0 时要特别检查：如果倒计时代码是用 endTime - serverTime 来判断是否结束，值是 0 时可能显示负数，或者立即触发”已结束”的回调【推断】。
通用排查（上次卡死的根源）：在这条链路的每个回调里，找出 if (e.hasOwnProperty("X")) 的 else 分支既不打开也不关闭弹窗的写法，把它们列成清单，每个 X 都必须由应答提供：
grep -nE "hasOwnProperty\(\"[A-Za-z]+\"\)" scripts2.js index.js
然后人工检查这条活动链路里命中的那些位置。
4. Q3：774 个 Reward
下一步最省事的判定动作
一条命令：
grep -nE "\.Reward\b|\[\"Reward\"\]" index.js scripts*.js
判读方式：
0 个命中，或者只出现在显示或发送的位置：客户端从不解引用 Reward，说明奖励表只在原版服务端存在。到此停止找表，结论是这些奖励从客户端无法恢复。
有命中，并且被拿去 getItem(x,"T")：T 就是要找的表。接下来读 CFMgr.getItem 的实现，看它是否在查表前对 key 做了变换（取模、拼前缀、查二级索引）。按主键找不到的原因就在这个变换里。
有命中，但被拿去做运算（比如 Math.floor(x/100)）：说明是复合编码，按运算式把这 774 个 id 解码之后，再去主键里找。
在此之前：跳过还是挂起
非 Repeat 任务挂起，Repeat 任务跳过，与 R03 一致。
另外有一处可以简化：挂起集合不需要存档新字段，它可以随时从现有数据算出来，即 pending = rewarded ∩ {Reward 无法解析的任务} − RepeatIds。这样就不用为了 rewardPending 把存档从 v4 迁移到 v5。等真相查明以后，补发时用 bzPatch 加上任务 id 作为幂等键即可。
这个推导成立的前提是配置不变。只要官方 APK 一更新，配置就可能变化，那时必须先把当时的 pending 集合落盘，再升级。
5. Q4：日志上限的轻量替代
// 只放在内存里计数，不额外触发写盘；跟着下一次业务写入一起落盘
var STAT_CAP = 400;   // 337 个已知动作 + 未知动作的余量
function countAction(save, name, now) {
  try {
    var m = save.meta || (save.meta = {});
    var s = m.actionStats || (m.actionStats = { v: 1, since: now, c: {}, n: 0 });
    var k = SHAPES[name] ? name : &#39;?&#39; + name;            // 未知动作加前缀，最有价值
    if (!s.c[k]) { if (s.n >= STAT_CAP) k = &#39;?overflow&#39;; else s.n++; }
    var e = s.c[k] || (s.c[k] = [0, 0]);
    e[0]++; e[1] = now;                                   // [次数, 最后一次调用时间]
  } catch (err) { /* 统计失败不能影响应答 */ }
}
接入规则（全部可以写成断言）：
调用时机：在应答已经构造完成之后再调用，并包在 try/catch 里。断言：一个请求在打开计数和关闭计数两种情况下，返回的应答字节必须相同。
不额外写盘：计数只修改内存里的 save.meta，跟着下一次业务写入一起落盘。进程崩溃时丢掉的只是上次写入之后的计数，这对频次统计可以接受。
守卫豁免：meta 不参与写前守卫的比较、A04 的守恒比较和 Q5 的背包守恒比较。断言：diffKeys(before, after) 只出现在 meta 里时，写入算作纯元数据写入，跳过业务守卫。
自检口径：自检和热重载时检查”存档 md5 未变”的那条断言，要改成”去掉 meta 之后的 md5 未变”，否则计数一更新，这条断言就会误报。
沙盒：env.sandbox 下不计数，否则自检的 1117 项会把统计污染掉。
存档格式：meta 是可选字段，旧的加载代码遇到它时会忽略，不需要迁移；新的加载代码要容忍它缺失。

L4 逐个动作切换到强制
一个动作在观察模式下累计 N 次调用、无法解释的差额为 0，才切换到强制

先做 L4，会不会让 L2 更难： 取决于 L4 是哪种模式。
强制模式先上，会。 每接一个新动作，都得先声明事件，否则一写入就被拒绝、被回滚，施工会一直被打断。
观察模式先上，不会，反而更容易。 对还没声明事件的动作，守卫会自动记下它的实际差额，比如”saleItem：背包 1001 −3，铜钱 0”，这正是该给它声明的事件，也正好暴露出第 0 项那类漏洞。
切换条件写成可执行的形式：
ENFORCE[name] = stats[name].calls >= 20 && stats[name].unexplained === 0;
7. 反例
装备属性：如果 newApplyBonuses 对 type==1 的装备也读 data[2]，并且客户端在 parseEq 里把配置属性写进 attrs，再由服务端回传，那么 attrs 就必须由服务端生成，Q1 里”只补穿戴投射”的结论就是错的。
空内容的 tab：即使三个条件都满足，子 UI 也可能在 onEnable 时启动 schedule，每帧读取 this.data.list[i]。空数组不会抛错，但如果代码用的是”为空就请求刷新”，就会每帧发一次请求，这是一种静默的高频请求循环【推断】。这时 Q4 的计数器会表现为某个动作的计数暴涨，是可以发现的。
观察模式的守卫：如果一直不切换到强制，它就永远只是一张日志表，L4 名存实亡。
推导出来的 pending：如果某个任务的 Reward 在当时能解析、后来因为配置变化而无法解析，推导就会把它误判成”没发过”，从而重复补发。
把出售放在第 0 位：如果客户端会在本地先加铜钱，而 LoadGame 又把铜钱回滚，玩家就会看到”卖了能拿钱、重启之后钱没了”。损失虽然一样不可逆，但表现得更晚。只有修好服务端的结算，这两种表现才会一起消失。
8. 假设
H1：客户端的穿戴状态来自 LoadGame 应答里的某个字段，而不是只存在于客户端内存。不成立时，Q1 的”补穿戴投射”无法实现，重启后装备会全部卸下，这就和 fightTaskObj 一样，只能接受。
H2：getActiveState 只读取材料里列出的四个字段。不成立时，Q2 的条件 1 不完整，需要先用 grep 补全字段清单。
H3：官方 APK 和配置不会变。不成立时，Q3 的推导式 pending 失效，必须改为落盘。
H4：业务写入足够频繁，计数能及时跟着落盘。不成立时（比如长时间只有只读请求），Q4 会丢掉较多计数，需要再加一条规则：“每满 10 分钟，在下一次请求时补写一次纯元数据写入”。
H5：出售价格就是 item 表的 SellPrice 或同类字段（具体列名材料未提供）。不成立时，第 0 项要先确认客户端出售界面显示的价格是从哪一列读的，再实现结算。
