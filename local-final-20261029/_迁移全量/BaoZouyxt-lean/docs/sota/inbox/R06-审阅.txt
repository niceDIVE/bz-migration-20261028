1. 结论
F1 的”不补回”现在还不能定论，它依赖一个没有核实的前提：秘籍（Effect==11）对已经学会的技能，原版效果是什么。 你的证据只证明了 41 级不是秘籍给的（因为 useItem 从不写 skills），但如果原版语义是”已学会时，技能等级 +1”或者”增加经验”，那秘籍本该产生的效果就确实丢了，按”可推导就补回”的原则应该补。最省事的判别是只读配置：读 item 3626 的描述列（列名材料未提供），看写的是”学会 X”还是”X 等级 +1”；同时在客户端的物品使用流程里 grep Effect 等于 11 的分支，看有没有”已学会，不能使用”的拦截。
描述是”学会”，并且客户端没有拦截 → 原版语义多半是”已学会也照样消耗”【推断】，不补回成立。
描述是”+1 级”或”经验” → 应该补回 1 级（[41]→[42]），用 bzPatch 并写入审计。
秘籍类只做”大声失败”是错位的。 现在每用一本秘籍，物品就被消耗、效果却不落地，这和 R04 里”卖东西白扔”是同一族问题：正在发生的、不可逆的损失。在学技能的语义实现之前，useItem 遇到 BZ_ITEMSCH 里的物品应该拒绝、不扣物品，而且拒绝码必须落在客户端有提示的分支里，这是你自己 Q3 第⑤步得出的教训。
分类器很可能是按字段名在全局归类，而不是按”（动作，字段）“归类。 它扫的是 356 个字段名和全部 33 万行代码，没有限定在某个回调的范围内。这样 data、type、list、id 这类常用名，会因为别的回调里有解引用而被判成契约。F1 那一族问题会在 formulaID 以外的字段上复发，而 6 条标注集抓不到这种污染。判别：统计同时出现在两个以上回调里、并且各回调标签互相冲突的字段名有多少个。如果大于 0，就要把扫描窗口限定在回调函数的行范围内（从 send 的 cb 定义开始，用括号计数找到函数结束，不需要语法树）。
crop 采用”保留容器、剔叶子”的动机有问题。 那 6 条 absent 报错是校验器的规则错误（父字段不存在时，子路径应该视为不适用，而不是缺失），不能成为保留空壳的理由。见 Q1。
校验器的”开关必须缺席”写得太绝对了。 handler 用合法值显式给出开关字段（比如以后实现了配方的 useItem），也会被判为 FAIL。应该改成：“开关字段要么缺席，要么出现在 handler 的产出里、并且值通过合法性检查。”
F2 的上限优先级反了。 上限是客户端按属性计算的（43132），属性一涨上限就涨，而 save.hungerMax 是某一次学到的值，会过期。读上限时应该先看本次请求自带的 hglmt，再看活模型，最后才用账本里的值；而账本里的值只能作为下限保护，不能作为截断依据。见 Q3。
2. Q1：开关 × 容器重叠的可判定规则
记 P 为既是开关、又是父容器的字段（比如 crop），C 为 P 的子字段读取点集合。对每个子字段读取点 P.c，判断它落在哪个位置：
在 hasOwnProperty("P") 的真分支内，并且没有自己的防护 → IN
在这个开关判断之外，并且没有防护 → OUT
自己有防护（P.hasOwnProperty("c")、真值判断、或运算默认值） → GUARDED
判定
条件
处理

R1 不发
C 里只有 IN 和 GUARDED，并且 handler 给不出全部 IN 子字段的合法值
整个 P 缺席

R2 发完整对象
C 里只有 IN 和 GUARDED，并且 handler 能给出全部 IN 子字段的合法值
发 P，P 里包含全部 IN 子字段

R3 发契约空壳
C 里出现 OUT
发 P，P 里包含全部 OUT 子字段；IN 子字段如果给不出合法值，判为冲突，写入人工清单，生成器拒收

R4 不发
C 里只有 GUARDED
缺席（缺席时副作用最小）

永远不发一个空对象 {} 作为默认值。 只有在 C 为空，并且开关真分支里除了读子字段之外没有其他语句时，{} 才等价于缺席。这种情况直接按 R4 处理。
防止子字段被误判为”已存在”的两条判定：
校验器判断子路径时，必须逐层检查真实应答对象里有没有这一层的 key，不能因为父字段存在就推定子字段存在。
父字段缺席时，子路径的结果是”不适用”，不能报 FAIL。

crop 的具体做法：先读 changeSate 回调里 hasOwnProperty("crop") 的真分支，确定 crop.b、crop.m 属于 IN 还是 OUT。如果都属于 IN，并且 handler 没有真实的种植数据，就按 R1 处理，crop 整个不发。
3. Q2：“必需且非空”的静态实现和元素可用性
静态实现（不需要语法树，只用一个跳过字符串和正则字面量的最小分词器加括号计数）
找循环：用 /for\s*\([^;]*;\s*(\w+)\s*<\s*([\w$.\[\]]+)\.length/ 捕获下标 i 和集合 P。再用括号计数确定循环体的范围；循环体是单条语句时，范围到第一个顶层的 ; 为止。只有当 P 经过别名表能解析到某个应答字段路径（比如 this.data.FashionArr ← e.FashionArr）时才继续。
找候选变量：在循环体里收集赋值左值（this.v = … 或局部的 v = …，要排除 ==）。同时记录每个赋值点外层、仍在循环体内的条件表达式文本，称为”可用性谓词”。
检查是否所有赋值都在循环里：
局部变量在它所在的函数范围内收集全部赋值点；this.v 在整个类的范围内收集（从 cc.Class({ 开始，用括号计数找到结束）。
赋值为哨兵值（null、void 0、-1、undefined）的点不算有效赋值。
判定条件：所有非哨兵赋值都落在第 1 步找到的循环范围内。
检查有没有无防护的读取：找 v 在循环之外的读取点（排除赋值左值）。满足下面任意一条就算有防护：
所在行的 if (…)、三元条件、与运算短路里出现了 v
外层某个 if 块的条件里出现了 v（通过括号范围判断）
出现了 typeof v 只要有一处读取点不满足上述任何一条，就给 P 打上 契约-非空 标签，并记下可用性谓词。
加入标注集：GetFashionList.FashionArr 必须判为契约-非空（证据是 curSelectType）；getActivityCounts.dataArr 必须判为契约，但不要求非空，否则说明判据写错了。
避免”存在但不可用”的元素
元素可用的定义：能让第 2 步记录的可用性谓词为真。也就是说，生成的元素必须满足循环体里通向赋值点的所有条件。只在 item 表里存在是不够的。
把谓词里的项映射到配置列：比如 1 == this.curSelectType、f.Type == 8、page == x，每一项要么能映射到元素的某个配置列，要么属于客户端运行时状态。
只从配置里挑选能让所有可映射项都为真的行作为元素。挑不出来，或者谓词里含有无法映射的运行时状态（比如子页白名单是在运行时动态生成的），就写入人工清单，生成器拒收，不要随便填一个看起来合法的 id。§7.1 那次误判就属于后一种情况。
在活进程里做只读验证（ctx.live === true，测试时运行）：发出应答、UI 完成初始化之后，读取 UI 组件上的 v，要求它不为 undefined。断言：
assert(comp.curSelectType !== undefined)
这一步只读不写，不构成第二条写入路径。沙盒里没有客户端，所以这条断言只能在真机的 CI 阶段运行。
4. Q3：只做结算应答带 hg 是否自洽
结论：有条件地自洽。 这取决于消耗是客户端在本地扣的，还是原版服务端在结算时算的。请求里带了 speed，这本身就说明原版服务端可能参与计算【推断】。
判别步骤（只读）
客户端在挂机期间有没有本地扣减：在挂机相关的 schedule 或 update 回调里，grep -nE "hunger[^=]*(-=|=\s*[^=].*-)"，找对 hunger 的递减写入。如果有，请求里的 hg 就是已经扣过之后的值，直接回声是自洽的。
回调怎么使用应答里的 hg：如果回调用”请求时的 hg 减去应答里的 hg”来显示”消耗了 X 饱食度”，或者以此判断”饥饿导致收益减半”，那就说明客户端期待服务端来算消耗；这时直接回声会表现为”0 消耗”，也就是免费挂机，不自洽。
客户端自己有没有消耗公式：搜索 speed 在挂机 UI 里的用法，比如”预计消耗”的显示。
如果客户端自己算过 speed × 时长，就复用这条客户端公式。这不算发明规则：输入都来自同一个请求，公式也来自客户端。
如果客户端从来不算，就不实现消耗，只回声。
跨重启的影响：LoadGame 不返回 hunger，客户端重启时会按属性重新计算饱食度，很可能直接回满【推断】。所以任何服务端的消耗模拟，玩家重启一次就能绕过，经济上没有意义。这一条决定了：不要把 hunger 持久化，也不要模拟消耗，除非第 2 步证明不这么做会改变收益结算。
无论走哪条分支都要做的
截断时用同一个请求里的 hglmt：hg_out = clamp(hg, 0, req.hglmt)。这是最新鲜的上限，比 save.hungerMax 和活模型都更可靠。
save.hungerMax 只在请求没有带 hglmt 的路径（比如 useItem）上作为后备。并且一旦它小于活模型的 hunger.limit，就用活模型的值覆盖它，避免过期的上限把饱食度截得过低。

6. Q5：H4 的判定阈值与是否对调
统计口径（按成就条目数计，不按条件类型数计）
先回答一个问题：成就进度是谁算的？
第一步：读客户端成就 UI 显示进度的代码。如果进度是客户端用本地模型算出来的（比如直接读 RoleBaseInfo.level），这类条目服务端只需要实现领奖接口，算作 D0（零成本）。
剩下的条目，按条件类型分成三类：
类别
判定

D1 状态可推导
进度是当前存档的纯函数，并且这个量是单调的，比如等级、技能等级、已完成任务数

D2 状态可推导但非单调
进度依赖当前持有量（物品数、金币数）；如果成就的语义是”曾经达到”，那就只能近似

E 需事件累计
存档里没有对应的量，比如击杀总数、使用次数、登录天数、消费总额

定义可推导占比 D = (D0 + D1) / 总条目数。D2 不计入 D：它在语义上只能近似，只有被单独确认后才能计入。
是否对调的分界
条件
处理

D ≥ 0.6
不对调，成就排第一，先做 D0 和 D1 两类

0.4 ≤ D < 0.6
不对调，但成就这一项只做 D0 和 D1，E 类条目推迟到每日任务链做完计数基础设施之后再做

D < 0.4
对调，每日任务链排第一

强制对调
不管 D 是多少，只要 E 类条目所需的计数器里，有一半以上和每日任务链的 18 项需要的计数器相同（比如击杀数），就对调，因为计数器先在每日任务链里做出来，可以两边复用

0.6 和 0.4 这两个阈值是决策取值【推断】，不是数据结论。它们的依据是：可推导部分超过六成时，先做成就，在不建任何计数器的前提下，玩家可感知的条目最多。
7. 反例
字段名全局归类造成污染：useItem 的应答里如果有一个叫 type 的开关字段，而别的界面里有 e.type.xxx 的解引用，分类器会把 type 判成契约，于是生成器补上 type: 0，客户端走进错误的分支。6 条标注集全部通过，自检也全部是绿的。
F1 不补回：如果 3626 的描述是”技能等级 +1”，玩家就是实际丢了一级，而现在的结论把这笔损失判成了”不存在”。
hungerMax 过期：玩家属性提升之后，上限从 540 涨到 600，但 save.hungerMax 仍然是 540。吃食物时饱食度被截到 540，客户端显示不满，玩家却找不到原因，日志里也没有 OBS 记录。
直接回声 hg：如果判别第 2 步的结果是”客户端期待服务端算消耗”，直接回声就等于无限免费挂机。这个漏洞不会报错，只会表现为收益偏高。
测试包装没有还原：S13 如果漏写了 finally，测试中途抛出异常后，InventoryModel.setItem 会一直保持包装状态。生产环境里每一次推送都会经过测试计数器；功能上无害，但热重载之后会层层嵌套，最后导致栈越来越深。
R4 默认缺席：如果开关真分支里有”关闭某个旧状态”的副作用（比如 crop 一出现就清除旧作物的显示），那么缺席会让旧显示一直残留。这属于表现层的错误。
8. 假设
H1：只有 upgradeSkill 会写 skills。不成立时，41 级的来源需要重新排查，第 1 节第 1 条的论证要重做。
H2：L3 推送只有 pushItemsToClient 这一个出口。不成立时，S3 会漏计，必须改为只依靠 S4 包装客户端的 setter。
H3：客户端在 LoadGame 之后会按属性重新计算饱食度，很可能是回满。不成立时（比如保留上一次进程内的值），Q3 第 4 步”消耗模拟没有经济意义”的论证就失效了。
H4：成就的条件类型能从配置里的某一列读出来。不成立时，Q5 的统计口径要改为逐条阅读客户端的进度显示代码。
H5：回调的函数体可以从 send 调用点用括号计数界定出来。不成立时（匿名监听器、按 key 分发），第 1 节第 3 条的范围限定就需要为分发表单独建模。
H6：changeSate 里 crop 的子字段全部读取于开关的真分支之内。不成立时，crop 应按 R3 发空壳，而不是 R1 的整体缺席。
