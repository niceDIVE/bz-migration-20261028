1. 结论
H1 作废，ptt 部分的结论我收回。 ECONOMY_CHNG 的六个分支全部是赋值，所以 R08 §1 第 6 条、§5 的风险分析、§6 反例 5 都作废，把键改成 ptt 的处置成立。不受影响、仍然成立的是 R08 §1 第 5 条：handler 里用 __require(&#39;RoleBaseInfo&#39;) 直接写活模型，是 L3 的第二个出口。
H2 不是被推翻，而是被证实了，材料在这里把方向写反了。 R08 的 H2 原话是”客户端会用 beginTime 减当前时间【推断】“，失效条件是”它是死字段”。你逐字取到的 scripts2.js:47303 和 58268 证明它确实被拿去做减法。所以 R08 §1 第 2 条和反例 1 从推断升级为事实，不需要作废。
我的 C11（时间类默认值必须是 0 或不发）对被减数字段是错的，这是我的错误。 把 beginTime 设成 0，getSTimestamp() - 0 只会更大，打坐和练功仍然是”一进去就已完成”。如果不发，startTimestamp 会变成 undefined，减法结果是 NaN，两种做法都不安全。所以这一轮的”止血”实际上没有止住。
BeginTraining 的情况更严重。 120515-120523 这几行会执行 E.TimeMgr.sserverT = n.beginTime。如果 getSTimestamp() 是按 sserverT 加上本地经过时间算出来的【推断】，那么 beginTime 等于 0，就会把整个客户端的服务器时钟拨回 1970 年，所有依赖服务器时间的冷却、buff 和每日重置都会一起错，直到下次重新校时。判别方法：grep getSTimestamp 的定义和所有 sserverT = 赋值点。如果成立，M1 中的 BeginTraining 就是当前最高优先级的缺陷。
E2 的”冻结模式下零匹配就当过期归档”是一个漏洞。 冻结成功时已经会原子地归档规则，所以此后清单里还留着的规则，如果零匹配，只可能是计划的改动丢了，或者被别的修改回滚了。这时应该 FAIL，不能悄悄归档。
C9 还没实现，这直接卡住了 204 项继承的清理。 被继承的字段里有查表键，例如 BeginTraining.skillID。把它中性化成 0，会走到 F1 那种 getItem(0, …) 返回 null 而崩溃的路径。所以 Q2 里涉及查表键的批次，必须等 C9 实现并通过之后才能做。
2. Q1 答
(a) 编码断言（tools/check_encoding.js，作为 CI 的第一道闸门，跑在所有 node 测试之前）
判据：
BOM：三个目录一律禁止。JSON.parse 遇到 BOM 会报错；jsb 引擎加载带 BOM 的 core/*.js 会怎样，材料未提供，所以统一禁止最安全。
U+FFFD：数量必须为 0。如果某个文件原本就合法地含有 U+FFFD，就在 golden/encoding-allow.json 里登记这个文件的确切数量。
换行符：同一个文件里不许出现混合换行，也不许出现单独的 CR。每个文件的换行风格以 golden/eol.json 里登记的为准，改了风格就 FAIL。这样在 Windows 上，git 的 autocrlf 转换不会被误判为内容改动。
语法：.js 必须通过 node --check，.json 必须能被 JSON.parse 解析。
var fs = require(&#39;fs&#39;), cp = require(&#39;child_process&#39;);

function toCp1252Bytes(s) {             // 无法映射就返回 null
  var out = [];
  for (var i = 0; i < s.length; i++) { var c = s.charCodeAt(i);
    if (c < 0x100) out.push(c); else if (CP1252[c] !== undefined) out.push(CP1252[c]); else return null; }
  return Buffer.from(out);
}
function utf8Strict(b) { return new TextDecoder(&#39;utf-8&#39;, { fatal: true }).decode(b); }
function checkFile(p, allow, eol) {
  var b = fs.readFileSync(p), errs = [], s;
  if (b[0] === 0xEF && b[1] === 0xBB && b[2] === 0xBF) errs.push(&#39;BOM&#39;);
  try { s = utf8Strict(b); } catch (e) { errs.push(&#39;invalid-utf8&#39;); return errs; }
  var fffd = (s.match(/\uFFFD/g) || []).length;
  if (fffd !== (allow[p] || 0)) errs.push(&#39;U+FFFD=&#39; + fffd);
  var crlf = (s.match(/\r\n/g) || []).length, cr = (s.match(/\r(?!\n)/g) || []).length;
  var lf = (s.match(/\n/g) || []).length - crlf;
  if (cr) errs.push(&#39;bare-CR&#39;);
  if (crlf && lf) errs.push(&#39;mixed-EOL&#39;);
  var style = crlf ? &#39;crlf&#39; : &#39;lf&#39;;
  if (eol[p] && eol[p] !== style) errs.push(&#39;EOL &#39; + eol[p] + &#39;->&#39; + style);
  // 双重编码：UTF-8 被当成 cp1252 读进来再写回 UTF-8，结果是合法的 UTF-8，不会出现 U+FFFD
  var back = toCp1252Bytes(s);
  if (back && /[^\x00-\x7F]/.test(s)) { try { if (/[\u4E00-\u9FFF]/.test(utf8Strict(back))) errs.push(&#39;double-encoded&#39;); } catch (e) {} }
  if (/\.js$/.test(p) && cp.spawnSync(process.execPath, [&#39;--check&#39;, p]).status !== 0) errs.push(&#39;syntax&#39;);
  if (/\.json$/.test(p)) { try { JSON.parse(s); } catch (e) { errs.push(&#39;json&#39;); } }
  return errs;
}
// 遍历 tools/*.js、hotfix-patch/core/*.js、tools/golden/*.json；只要有一个文件 errs 非空，就退出码 1
为什么光查”合法 UTF-8、没有 U+FFFD”不够： E3 那类破坏最常见的形态是双重编码，Windows PowerShell 用 ANSI 代码页读 UTF-8，再写回 UTF-8。这样产生的乱码是合法 UTF-8，而且一个 U+FFFD 都没有。所以 double-encoded 这一项不能省。
另一种形态是代码页无法表示中文时，把中文替换成 ?。这样的文件是纯 ASCII，上面的所有检查都会判绿；如果 ? 落在字符串或注释里，node --check 也能通过。这一种只能用 (b) 的方法抓。
(b) “内容被改”与”仅编码被改坏”能不能区分
能，但前提是拿得到改动之前的原始字节（git HEAD 或备份）。没有原件时，就做不到，我不给启发式。
判定方法：准备一个有限的变换集合 F：
加 BOM；
LF 与 CRLF 互转；
UTF-8 → GBK；
UTF-8 → 按 cp1252 双重编码；
不可表示的字符替换为 ?（分别对 cp1252 和 cp936 各做一次）。
规则如下：
对 F 中的每个 f，如果 f(旧字节) 与新字节逐字节相等，判为”仅编码被改坏（f）“。这是确定性的结论。
如果没有任何一个 f 能做到相等，判为”内容被改”（可能同时还叠加了编码问题）。
对于可逆的 f（加 BOM、换行互转、GBK、双重编码），可以再算 f⁻¹(新字节)，与旧字节做文本 diff，把真正的内容改动单独分离出来。
对于不可逆的替换 ?，无法分离”内容改动”和”编码破坏”，我明说做不到。

排序：只做 Begin 的 M1 先做；M2 不占用施工顺序，可以随时并行跑，因为它只读、不写产物。 End 两个动作先只读取证，用来判断两件事：结束请求里有没有带上时长，结算的应答是否依赖服务端记录的 beginTime。
M1 里还有一个待查的字段：hyTime。它会被乘以 1e3 并传给 setBufferCostStartTime，它的来源材料未提供。动手前先查清它的含义：如果它能从配置推导出来，就由 handler 给出；推导不出来，这一项进人工清单，不能编一个数，也不能填 0，因为填 0 是否安全，同样取决于它的读取形态。
R ≤ 10 时 M1 是否自动升为第一
M1 现在就已经是第一，不是靠 M2 的结论才升上来的。两件事作用的对象不同：M1 改的是 handler，M2 关系到的是分类器，所以 M2 的结论不会改变 M1 的分数。
M2 的结论只决定 span 改造要不要进入队列：
R ≤ 10：不做 span 改造，用覆盖表处理。
R > 10：只有当 R 里有已经在真机上触发过的项（actionStats 计数大于 0），并且这些项有崩溃或分支走错的证据时，它们才算作已知缺陷，计入 K，再按上表与 M1 比较。
5. 对 E1 与 E2 的判断
E1：这说明 C7 抓得住真实问题，它不是纸面条款。但修法只是把正则收紧，时间字段的判定仍然靠名字。用名字判定会漏掉不按这个规律命名的时间字段，比如 st、endTs，也可能再次误伤别的字段。
改法：C11 的字段集合 = 名字正则命中的字段 ∪ 静态证据命中的字段。静态证据指：这个字段（或它被赋值到的成员）出现在 getSTimestamp() - 或 Date.now() - 形态的减法里。只靠名字命中、没有证据的字段，只报告，不处理。
另外，sigmaChangeAllowed:true 放在规则层面太宽了。应该改成逐项列出允许 σ 变化的（动作，路径）。否则同一条规则下多匹配到一个误伤项，只能依靠 C8 的计数来兜底。
E2：归档机制本身是对的，但”冻结模式下零匹配就算过期”要删掉。冻结成功会原子地归档规则，在这之后，清单里只要还有零匹配的规则，就一律 FAIL，原因写成”计划改动未生效或已被回滚”。真正过期的规则只能由人工移动到 archive 目录，并在提交里说明原因。
6. 反例
C11 把时间字段压成 0 带来的全局时钟问题：玩家进入练功，sserverT 被设成 0。之后所有依赖服务器时间的冷却和 buff 都按 1970 年来计算，表现成”冷却永远好了”或者”buff 永远过期”，而且错误发生在练功以外的界面，很难联想到练功。复现：真机点练功之后，读取 TimeMgr.getSTimestamp() 的值（只读）。
B0 合法化了错误的值：BuyMarketItem.userGold 改成”来自自身动作的抓包值”之后，C12 判它合法，棘轮计数也减少了，但客户端收到的钱包余额仍然是抓包那一刻的值。(c) 里的例外条款就是为了防这一点；如果 S 的识别漏掉了某个状态字段，这个问题仍然会发生。
? 替换：在 cp1252 代码页下用 Set-Content 改了一个文件，中文日志串全部变成 ?。(a) 的所有检查都判绿，只有当 CI 拿得到旧字节，并跑了 (b) 的变换集比对时，才能发现。
E2 的过期漏洞：某条计划规则匹配的改动被后来的另一处修改覆盖掉了。冻结模式把它当作”过期”归档，计划的改动从此没有落地，也没有人知道。
P6 冒烟覆盖不到异步读取：动作确实被触发了，计数也加 1，但出错的读取发生在 scheduleOnce 延迟之后才打开的子界面里。冒烟期间 err=0，并不能证明这个子界面安全。
只做 Begin 的 M1 与 End 结算不一致：Begin 返回了真实的当前时间，但 End 的应答如果仍然靠形状补出一个结算时间（常量或 0），客户端算出来的时长就是负数，或者大得离谱，从而可能把收益放大到异常。所以 M1 在上线之前，至少要完成 End 两个动作的只读取证。
7. 假设
A1：getSTimestamp() 按 sserverT 加上本地经过时间计算【推断】。不成立时，第 1 节第 4 条和反例 1 作废，M1 的 K 取 2，两个 Begin 动作之间不再分先后。
A2：这两个动作目前的形状默认 eRet 落在 1 或 2，所以客户端会进入写 beginTime 的分支。不成立时，现象就不是”一进去就已完成”，而是”点了没有反应”，但缺陷依然存在，M1 的排序不变。
A3：CI 的 Node 版本自带 TextDecoder，并支持 fatal 参数。不成立时，§2(a) 改用”按 UTF-8 解码再编码，与原字节逐字节比较”作为 UTF-8 合法性判断，其余检查不变。
A4：每次改动都能拿到旧字节（git 或备份）。不成立时，§2(b) 整体失效，只能保留 (a)。
A5：分类器的 facts 里保存了每个（动作，字段）的读取形态。不成立时，§3 的 P2 无法自动判定，B1 到 B3 都要先补出读取形态才能切批。
A6：actionStats 在内存里按动作实时累加，不必等到写盘。不成立时，P6 改为按真机日志里各动作的请求条数来计数。
