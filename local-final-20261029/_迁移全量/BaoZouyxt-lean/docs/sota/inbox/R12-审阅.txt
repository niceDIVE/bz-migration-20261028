1. 结论
isCollective 只在单人练功的情形下判对了。 它是开关字段，这一点没错；但请求里本身就带着 isCollective。如果玩家发起的是门派集体练功（请求里 isCollective 为真），而客户端恰好要靠 hasOwnProperty("isCollective") 这条分支，在集体练功成功后关闭门派界面，那么”绝不发”会让这个界面一直关不掉。
正确的规则是按请求回声存在性：请求里 isCollective 为真时发出，否则不发。
判别方法：读这个分支的真分支，看它是”成功进入集体练功”的路径，还是”错误、关闭界面”的路径。
skillID 改成回声请求，方向是对的，但 ||0 这个兜底是错的。 skillID 几乎一定会被拿去 getItem(…, "skill") 查表【推断】，兜底成 0 会复现 F1 那种查表返回 null 后崩溃的问题。
改法：当 p.skillID 在账本的 skills 里，并且也在 skill 表里时才回声；否则返回一个客户端有处理的拒绝码，不写入 beginTime，也不发 skillID。
这里还有一个合法性问题：原来的写法会让玩家用一门自己没学过的技能练功。
choose 显式给 0，是一次 σ 可能变化的值改写，需要单独核实。 beginPlayGame.choose 原来继承自 getFinishTaskAward 的抓包值，改成 0 之后，如果原值不是 0，σ 就变了。请确认它走了 allowSigma 逐项放行，并且有读取形态的证据；如果它在客户端被当作分支键或查表键，0 也不一定是安全值。
判绿只看 failed 是否为空，会被静默跳过的检查绕过。 本批 passed 从 1234 变成了 1233，failed 依然为空。少掉的那一条，很可能正是带条件跳过的 clock:liveIsReal 这类检查。
断言要改成：已执行的检查 id 集合 ⊇ golden/required-checks.json（必需检查 id 集合）。按检查 id 比对，而不是比计数。这样”会随数据变化的数字”就不再需要人去解释了。
useItem 先扣物品、先持久化，再去分发效果，顺序是反的。 效果分支里只要抛出一次异常，物品就丢了，而且已经写进了存档。应该先校验、先算出效果，再在同一处一并完成扣除、生效和持久化。这一条和 Q2 的定性无关，现在就该改。
其余处置没有错位。 固定时钟查出了第三个常量并改成登记制，C9a 承认只是下界，缺口如实保留并写明了理由。
2. Q1 答
断言该放哪层的判据
一条断言放在”在求值那一刻，拥有它全部输入”的那一层。 不允许为了让断言能求值，把别的层的状态引入进来。
scene 和 __BZ_HARNESS__ 都属于 bootstrap 或 flow 层，所以这条断言放在 flow 层。
impl 里的 clock:liveIsReal 保留它现在的条件判断不变；“这条检查必须被执行到”这件事，由下面的 Q1-3 来保证。
flow 层怎么让失败可见
编号
做法

Q1-1
flow 层新增一个只读函数 flowCheck()，返回 {passed:[id…], failed:[{id,msg}…]}，格式与 impl 的 selfCheck 一致。首批放两条检查：flow:harnessInGame（scene === &#39;gamescene&#39; 时，__BZ_HARNESS__.impl 必须存在）和 flow:implLoaded（implErr === null）

Q1-2
验收器已经在调用 ver 或 selfCheck 这个出口。在这个出口上把两层的结果合并：verdict = {impl: selfCheck(), flow: flowCheck()}，只有两边的 failed 都为空时才判绿

Q1-3
验收器断言：两层已执行的检查 id 的并集 ⊇ required-checks.json。这样 impl 里因为条件不满足而跳过的 clock:liveIsReal 会以”缺少必需检查”的形式变红，而不是悄悄不见

Q1-4
如果 flow 层的改动必须重启才能生效（是否必须重启，材料未提供），Q1-1 就攒到下一次计划内的重启时一起上线。在此之前，先只在验收器一侧实现 Q1-3：当前 live 进程里只要缺少 clock:liveIsReal 这个 id，验收就判红

4. Q3 答
先把登记表分成两类
缺陷登记：登记的是一个正在发生、或者潜在的问题，比如 known-missing-handlers 和 ceiling。
清单登记：登记的是合法存在、可以长期保留的事物，比如 C13 的固定时钟。
两类适用的退化判据不同。
可判定的退化规则
任何一条成立，就判定这张登记表已经退化成豁免表。
编号
规则
适用

G1 借登记转绿
在同一次提交里，用旧的登记表（merge-base 版本）跑检查是红的，用新的登记表跑检查变绿了。也就是说，这次提交是靠新增登记才让检查通过的
两类都适用

G2 净流入
最近 k 次冻结里，新增的条目数大于移除的条目数（k 取 5，是决策值【推断】）
缺陷登记

G3 滞留
有 live:true 的条目，从登记起已经超过 M 次冻结仍未移除（M 取 3，是决策值【推断】）
缺陷登记

G4 出口不可执行
有条目缺少可以在 CI 里运行的 exitCheck，或者在登记那一刻 exitCheck 已经能通过（说明登记的根本不是一个真问题）
缺陷登记

G5 无上限
条目总数超过 cap；或者 cap 比 merge-base 版本更大，却没有对应的 approved-widening 行，或者这次提交里还夹带了别的改动
两类都适用；清单登记的 cap 就是现在的条目数，比如固定时钟的 cap 是 2

写成断言的形态
// 每个登记条目：{id, kind:&#39;defect&#39;|&#39;inventory&#39;, addedAt:<冻结序号>, evidence:[&#39;bundle:line#sha8&#39;], exitCheck:&#39;<检查id>&#39;, live:true|false}
function registryHealth(reg, base, history, runCheck) {
  var fails = [];
  // G1：用 base 登记表跑会红、用 head 登记表跑变绿的检查
  reg.guards.forEach(function (chk) {
    if (!runCheck(chk, base.entries) && runCheck(chk, reg.entries)) fails.push(&#39;G1 &#39; + chk);
  });
  if (reg.kind === &#39;defect&#39;) {
    var w = history.slice(-5), add = 0, rem = 0;
    w.forEach(function (h) { add += h.added.length; rem += h.removed.length; });
    if (add > rem) fails.push(&#39;G2 net+&#39; + (add - rem));
    reg.entries.forEach(function (e) {
      if (e.live && reg.freezeSeq - e.addedAt > 3) fails.push(&#39;G3 &#39; + e.id);
      if (!e.exitCheck) fails.push(&#39;G4 noExit &#39; + e.id);
      else if (e.addedAt === reg.freezeSeq && runCheck(e.exitCheck)) fails.push(&#39;G4 exitAlreadyPasses &#39; + e.id);
    });
  }
  if (reg.entries.length > reg.cap) fails.push(&#39;G5 overCap&#39;);
  if (reg.cap > base.cap && !approved(reg.capChange)) fails.push(&#39;G5 capRaised&#39;);
  return fails;   // 结果为空才算通过；验收器把它并入 Q1-2 的总判定
}
对 C11b 来说：现在它的登记是 0 项。G5 让 cap 直接取 0，此后每新增一条，都必须单独一次提交，带上 approved-widening 并给出证据。这样就不可能”一条条登记到全绿”。
5. 对 C9a 保持”下界”状态的判断
有条件同意。 C9a 目前唯一的使用者是 204 项（现在是 203 项）的分批清理，而 B1 到 B3 的中性化批次还没开始，所以暂时不补别名和下标的回溯，不会造成实际损害。条件是要把这个状态变成一道闸门，不能只写在交接文档里：
lookup-keys.json 里加一个字段 complete:false；
中性化批次的工具一旦读到 complete === false，就拒绝运行任何会改变值的批次（B1 到 B3），只允许运行 B0（只改标签）和分桶统计；
退一步的方案：如果要在补全之前先做某一批，就对这一批里的每个字段，在三包里单独 grep 一遍别名和下标两种查表形态（R11 反例 1 的那条命令），命中数为 0 才放行。这只是批内的局部检查，代价很低。
6. 反例
集体练功卡界面：玩家在门派里发起集体练功，请求里 isCollective=1，应答里没有这个字段，客户端不进入关闭门派界面的分支，练功界面和门派界面叠在一起。复现：在门派场景里点集体练功。
skillID 兜底崩溃：请求里的 skillID 是字符串 "abc"，或者缺失，parseInt 得到 NaN，于是兜底成 0，客户端执行 getItem(0, "skill") 返回 null，之后读 .name 崩溃。
按效果码一刀切拒绝：某个 Effect 的效果本来是客户端在本地生效的（比如打开某个界面、播放某段剧情）。(a) 把它也一并拒绝，这个物品就从”能用”变成”不能用”，而且日志里看起来只是一个正常的拒绝。
计数掩盖跳过：live 进程缺少 harness，clock:liveIsReal 被跳过，同一轮里又新增了一条别的检查，passed 数不变，failed 为空，一切看起来是绿的。只有 Q1-3 按检查 id 比对，才抓得到这种情况。
先扣再生效时抛异常：食物分支里，饱食度的上限读取抛出了异常（例如活模型还没有初始化），物品已经被扣除并持久化，而效果没有生效。复现：在场景加载过程中立即使用一个食物。
G1 的误判：某次提交修好了问题，同时按规定删除了对应的登记。G1 会把”用旧登记表跑”那一侧判红、“用新登记表跑”那一侧判绿，看起来像是”借登记转绿”。所以 G1 只应该统计新增的登记条目，删除条目引起的变化不计入。
7. 假设
A1：isCollective 的 presence 分支对应的是集体练功的成功路径【推断】。如果它只是错误或关闭路径，第 1 节第 1 条作废，“绝不发”是对的，反例 1 也随之作废。
A2：skillID 在客户端会被用作查表键【推断】。如果不会，||0 只是不严谨，不会崩溃，第 1 节第 2 条降为”只需要做合法性校验”，反例 2 作废。
A3：客户端不会在发出 useItem 请求之前本地预扣物品。如果会，Q2 选码规则就必须走第 3 档，你倾向的第 2 档失效。
A4：验收器能读到 merge-base 版本的登记表和冻结历史。如果读不到，Q3 的 G1、G2、G5 就要改用 R10 T5 那种哈希链历史。
A5：impl 和 flow 两层都能通过验收器已经在调用的出口一起读到。如果 flow 层没有任何可调用的出口，Q1-2 就要在 bootstrap 里新增一个只读出口，而这需要重启才能生效。
A6：Effect 23 的 3 条物品里，至少有一条是可获得的。如果都不可获得，那么 (b′) 的 K 实际为 0，Q2 的排序就变成 (c) 第一：先只计数，等它们变成可获得时再改行为。
