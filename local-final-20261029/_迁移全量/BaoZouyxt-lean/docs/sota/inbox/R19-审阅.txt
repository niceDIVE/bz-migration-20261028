2. Q1 答
先定性：原版服务端怎么答，客户端证据判不出来
64754-64911 里没有任何分支专门针对 Effect 11，原版的应答拿不到抓包。下面的规则是从客户端流程反推出来的设计判定，不是还原原版【推断】。判据只有一条：一本书在每一种用户路径下，都只扣一次，而且只在真的获得了效果时才扣。
① useItem 侧：不扣书，不发 skch，只回 {eRet:1}
理由（都有行号）：
不论学没学会，ConsultUI 都会弹出（64413），而且”学会 1 级”本身就是 13904 里的 sendUpgradeReq(i, {lv:1, pgr:0, brlv:1}) 发出的。如果 useItem 侧也去学或升级，会和 ConsultUI 的那一步重复执行。
useItem 先发，响应也先到。如果它把 1112 写进技能，ConsultUI 里的 onLearnSkill（13872）判断 isSkillLearned 时就会走错分支。
如果 useItem 就扣书，而玩家随后关掉 ConsultUI、没有点确认，就是”有损失、没收益”，违背上面那条判据。
回 {eRet:1} 时，成功回调里的三支（skch、rewardArray、titleID）都不会命中，客户端什么也不显示，这是安全的。
这条规则同样适用于未学会的情形：你们现有 ITEMSCH 的”未学会就写 1 级并扣书”要一起改掉。这是对已裁定行为的变更，列入第 8 节的重新裁定清单。
② upgradeSkill 侧：一本书对应一次 upgradeSkill（flag=1）
项
规则

识别
flag === 1 并且 NPCID 是一件 Effect 11 的书，同时 master_book[NPCID] 存在

匹配
BZ_ITEMSCH[NPCID] === skillID，即书对应的技能 id 必须等于请求的 skillID，否则拒绝

库存
书的数量 ≥ 1，否则拒绝，不改任何东西

等级
服务端自己算：未学会时新等级 = 1；已学会时新等级 = 当前等级 + 1。不采用 skillArr[0]

进度
已学会时，要求服务端存的 pgr ≥ c，新 pgr = pgr - c。c 按 level 表和 getQualitySkillCoefficient 计算（需要先 dump level 表）。不采用 skillArr[1]

封顶
服务端重做 14045（maxSkillLevel）和 14054（getSkillTopLevel）的检查，超过上限就拒绝

落地
写技能、扣 1 本书、note.skch 和 note.ivch（写绝对值），一次 persist() 完成

为什么选”一本书对应一次 upgradeSkill”，而不是”一本书对应一次 ConsultUI 会话”：后者需要服务端记住”这一本书打开了哪一次会话”，这是内存里的状态，重启就丢，而且同一本书的会话里可以连续点出多次升级。前者是无状态的，最坏情况是玩家点一次确认就少一本书，不会出现”无限升级”。这一项是设计选择【推断】，原版的做法材料未提供。
③ NPCID 和 flag：必须读；只读 skillArr，会有三个可观测的漏洞
客户端随便报等级：现在 1225 是 lv = max(curLv, reqLv)，等级相当于由客户端上报。只要构造一个 skillArr，就能一次把技能拉到任意等级。这违反了”不能让客户端上报服务端才有的数据”。
书不扣：handler 不认识 NPCID，书就永远不会扣，一本书可以无限次打开 ConsultUI 去升级。
张冠李戴：不核对”书对应的技能 = skillID”，那么 3626（对应 1112）可以用来升级任意技能。
改动范围：只新增 flag === 1 这一个分支。flag 为其他值的现有路径（NPC 请教、潜能升级）本批不动，但第 1 条那个漏洞对它们同样存在，单独登记。

6. 反例
模板缓存被污染：如果 base 指向的是 templates.json 解析之后缓存在内存里的对象，tObj[tk] = … 就会直接改掉缓存。之后同一进程里的每一次 create 和 LoadGame 都会带上这些称号键，即使存档被换成一个新角色也一样。测试 T2”空档只有 e”如果每次都在新进程里跑，就发现不了这个问题。
已过期的限时称号被投射出去：将来出现限时称号时，s.titles[k] 存的是一个已经过去的到期时间（> 1），会被原样投射。673 的 checkTitleBuff 用 value - now 得到负的剩余时长，表现是什么，材料未提供。投射时应当过滤掉 value <= now 的项。
exitCheck 被整个数组赋值绕过：某个保存属性的 handler 写了 s.baseValueAy = req.baseValueAy。字面下标的 grep 是 0 命中，exitCheck 仍然是绿的，但从这一刻起，客户端上传的 numDeaths 就进了存档。3020 会悄悄变得可达，并且走”照扣无效果”。
升级请求里的等级由客户端说了算：只读 skillArr 的现状下，一个 upgradeSkill{skillID:1112, skillArr:[99,0,1], NPCID:3626, flag:1} 就能把技能 1112 从 41 级直接写到 99 级，书也不会扣。
useItem 学一次，ConsultUI 又学一次：在 Q1 的改动落地之前，玩家对一个未学会的技能用书。useItem 写入 1 级、扣掉书，随后 ConsultUI 弹出（列表里还是 lv 0）。玩家点确认，客户端这时 isSkillLearned 为真，走进升级分支；pgr 不够就提示失败，够的话又升到 2 级。也就是一本书产出了两级，或者让玩家看到一个莫名其妙的失败提示。
配置表里的活动集体过期：213 个没有筛查的毫秒字面量里，只要有某张活动配置的结束时间早于当前时间，或者在未来 30 天内，客户端拿它和真实的 serverTime 比较，就会关闭这个活动入口。这和 activityResource 的平移无关，现有的平移修不到它。
Effect 13 被误登记为 unreachable：如果按 Q2② 的原提议登记，而行为仍然走”照扣无效果”，一个以”不可达”自证正确的条目，会在玩家每一次打开礼包时吞掉礼包。G4 的 exitCheck 也无从写起，因为根本没有本地拦截这个条件可以断言。

8. Q4 答
① 端上实测（用掉 3626）：不该做
这不是”静态证据够不够”的问题，是实测拿到的东西不对。端上跑的时候，答应答的是我们自己的服务端，实测能看到的只有”请求的到达顺序和字段”，而这一点 §3.3 和 §3.4 已经静态闭合了。原版服务端怎么答，实测拿不到。
所以，用掉一件不可再生的道具，换来的是零增量信息。Effect 11 按 Q1 的设计判定来实现，不用消耗玩家任何东西。
真正有判定力的只有一种证据：原版服务端对 upgradeSkill{flag:1} 或 Effect 11 useItem 的抓包。去 decrypted/ 和 templates.json 里 grep "flag":1 和 NPCID。查到了，就以抓包为准修订 Q1；查不到，就是”材料未提供”，Q1 的设计判定就是终态。
② 全表探针：该做，但差集为空不能当作终局证据
差集为空只能证明”ConfigMgr 当前已经加载的表里没有礼包表”。要成为终局证据，还缺三样东西，都可以在不出网、不改客户端的条件下拿到：
P1：这 1780 件物品自己的 Data2..5 和 Property1..5 里不含物品 id；
P3：所有 bundle 的资源里 grep 不到以 7105、7106、7226 为键的数据（覆盖那些按需加载、探针时还没加载的分包配置）；
探针在进入过礼包、背包、商城等界面之后再跑一次，表名集合不再增加。
这三项都为空，再加上差集为空，才能定论”客户端不含礼包内容”，Effect 13 就是”原样不可实现”，按 Q2 ② 处置。
