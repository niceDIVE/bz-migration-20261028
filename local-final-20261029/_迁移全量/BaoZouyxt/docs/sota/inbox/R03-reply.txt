1. 结论
打怪掉落里的”同一 npc + 5 秒窗口”是硬伤。 它会同时犯两种错：正常的快速连打会被挡掉；超过 5 秒的重发会被放过。而且你用它防的威胁很可能根本不存在：网络层已经被你在进程内替换掉，传输层的重发不会发生，能产生重发的只有客户端自己的业务代码。见 Q1。
D 和”rewarded 一次封顶”放在一起是硬伤。 第一，Repeat 任务进了 rewarded 却没有进 done，违反了 A04 里那条 E 断言 rewarded ⊆ questDone。这条断言要么已经在报错，要么已经被你放宽了；如果是整体放宽，E 类事故（奖励名单丢失）就重新失去了保护。必须改成只对 Repeat 任务豁免：rewarded ⊆ questDone ∪ RepeatIds。第二，见 Q4：一次封顶很可能让本该反复领奖的任务形同残废。
B（进程内推送）没有规定和客户端回调之间的先后顺序。 推送如果早于客户端处理 rewardArray，奖励物品会被显示两次。见 Q3(b)。
推送通道和掉落路径不一致。 推送通道已经有了，掉落却既不回 rewardArray、也不推送，结果玩家看不到战利品，本地背包要等到下一次同步才有这些物品。只要 CheckBattleResult 的回调会消费 rewardArray（只读源码就能确认），就应该走应答，其次才是推送。
C 的修复和 4015/4016 的补回都成立。 补回的数量可以从配置和 rewarded 名单重新算出来，不属于”不可区分”的增加，符合上一批 Q7 的硬规则。还有一项材料未提供：saleItem 修好之后，铜钱是按截断后的数量计算的吗？这一点要用 R02 的 A7 断言确认。
2. Q1：战斗去重
“同一 npc + 5 秒窗口”能不能用：不能。 它没有对应任何真实存在的重发机制，5 秒这个数也没有依据：
误挡：开了自动战斗、扫荡或者跳过战斗时，连续打同一只怪的间隔可能小于 5 秒（实际间隔材料未提供），第二场的掉落会被吞掉。
漏挡：如果客户端确实有重发逻辑（比如回到前台后补发），重发间隔一旦超过 5 秒就会被放过，造成重复入账。
跨进程：lastBattle.t 用的是进程时钟，系统时间被回拨时，窗口判断会失真。
替代方案（按优先级选第一个成立的）：
先确认重发是否存在。 只读检查：
grep -nE "CheckBattleResult" bundle*.js        # 发送点有几处，各自在哪个事件里
grep -nE "retry|resend|reSend|timeout|onTimeout|reconnect" bundle*.js   # 找 HTTP 封装里的重发逻辑
判定规则：发送点只有一处，位于”战斗结束”事件里，而且 HTTP 封装没有重发逻辑（或者重发逻辑只在超时时才触发，而进程内替换后的应答是同步返回的，永远不会超时）。满足这些条件，就说明重复结算不会发生，正确做法是不去重：每个 win 为真的结算请求都入账一次。
如果存在重发，看请求信封里有没有客户端生成的序号或时间戳（比如 seq、t、ts、sign；有没有材料未提供）。有的话，用 save.lastBattleEnv = 信封序号 做水位线去重：同一个请求被重发时信封完全相同，被挡掉；连续两场真实战斗的信封不同，不会被误挡。
如果有重发、信封里也没有任何区分字段，看有没有开战请求。 有的话，用 B01-3 的设计：开战时由服务端分配一个单调序号，结算时消费它，每个序号只能消费一次。存档里只需要 {seq, pendingStart, battleWatermark} 三个数。
以上都不成立时，用物理下限代替 5 秒。 先从运行日志里统计相邻两次结算的真实间隔，取其中最短的真实间隔的一半作为下限 MIN_GAP；只挡掉间隔小于 MIN_GAP 的请求，并且不区分 npc（同一时刻不可能结算两场战斗）。
会不会误挡连续打同一只怪：方案 1、2、3 都不会，因为它们不依赖时间。方案 4 只会挡掉比任何一场真实战斗都快的请求；这一点依赖下限统计足够准确，统计的样本不够时，会出现误挡。
3. Q2：774 个指不到表的 Reward
(a) 三种可判别的解释
这是一张只在原版服务端存在的表。 客户端只需要显示服务端下发的 rewardArray，从来不需要自己解引用 Reward，所以这张表根本不在客户端里。 只读检查：grep -nE "\.Reward\b|\[\"Reward\"\]" bundle*.js。如果客户端从来不把 Reward 当作 key 去查任何 CFMgr.dic.*（只用来显示，或者完全不读），这个解释就成立。成立时，这 774 个奖励无法从客户端恢复。
这是一个复合编码，不是主键。 比如 100507 = 表或组号 1005 加上序号 07，或者 组 × 1000 + 档位 这类编码。 只读检查：对 774 个 id 按前 3、4 位分组，看分组后的前缀是否落在 drop 表或某张表的主键集合里；同时用随机 6 位数作为对照组，比较两边的命中率。如果命中率显著高于对照组，说明是复合编码。
这是某张表的非主键列。 比如 drop 表或奖励组表里的”组 id”列，多行共用同一个组号，所以按主键是找不到的。 只读检查：把搜索范围从”454 张表的主键”扩大到”454 张表的所有列”，统计每一列里有多少个值命中这 774 个 id；同时用”把这 774 个 id 各加 7”作为对照组跑同样的统计，排除数字巧合。命中率显著高于对照组的列，就是 Reward 实际引用的列。
(b) 跳过还是挂起
判据：如果日后查明真相，需要按”任务 → 应发奖励”补发，而且这次补发必须能被确定地、只做一次，那就挂起；否则跳过。
非 Repeat 任务：挂起。 交任务照常成功，rewarded 照常写入，应答返回空的 rewardArray；另外把任务 id 记入 rewardPending: [taskId]，这个字段通过迁移引入，初值是 []。等真相查明后，按 rewardPending 补发，每补一个就移除一个，用任务 id 本身作为幂等键。
Repeat 任务：跳过。 Repeat 任务没有可以确定的”这是第几次”，挂起之后没法确定该补发几份，这样的挂起是不可审计的。
任何情况下都不能先发一个”猜测的”奖励，否则就违反了 Q7 的硬规则。
4. Q3：第二条写入路径的护栏
(a) 除了”沙盒跳过”之外必须有的两条断言
推送的内容必须等于投射。 推送不能携带投射以外的任何信息。
for (var id in pushed) assert(pushed[id] === project(stateAfter).itemObj[id]);
这样一来，只比对应答和投射的契约测试，在逻辑上就已经覆盖了推送的内容。
推送的范围必须受本次请求约束，并且被记录下来。
assert(isSubset(keys(pushed), affectedIds(events)) &&
       keys(pushed).every(function (id) { return !isCurrency(id) && !isEquip(id); }));
ctx.trace.push({ kind: &#39;push&#39;, items: pushed });   // 契约测试改为断言 response 加上 trace.push
(b) 一条具体时序
前提：getFinishTaskAward 发放了物品 4015×1，而且推送在客户端回调之前执行。
服务端结算完成，真实库存 4015 = 1；在网络层里同步调用 setItem(4015, 1)，客户端模型 4015 = 1。
应答交给客户端，finishTaskCallBack 处理 rewardArray 里的 4015×1。如果客户端的处理方式是在本地加数量（getItemNum + n），客户端模型 4015 就变成 2。
玩家看到 2 个，服务端只有 1 个。玩家拿第 2 个去出售或使用时会被截断，看起来就是”操作了但数量没变”。
防法：推送必须排在客户端回调之后，比如挂在回调完成之后的下一个 tick。或者推送时排除本次 rewardArray 里已经包含的物品 id：assert(intersect(keys(pushed), rewardIds(resp)).length === 0)。到底需不需要防，取决于 finishTaskCallBack 是在本地累加数量还是读取绝对值，只读源码就能确定。
5. Q4：Repeat 的奖励上限
(a) 会不会变成残废：会
客户端对 Repeat≠0 的任务故意不记完成，目的就是让玩家反复接取【推断：没有别的理由会写这个分支】。如果奖励只发一次，从第二次开始玩家照样做任务，却什么都拿不到，任务就失去了意义。 只有一种情况例外：这些重复任务本身就是零奖励的循环（比如只用来推进剧情或解锁），可以统计 66 个任务里 Reward≠0 的比例来判断。
(b) 不引入新配置的替代上限（按优先级）
用 Chain 列做周期。 如果 Chain 把重复任务和链上的其他任务串成了一个环，那么每走完一轮链只发一次奖励，去重键是 rep:<taskId>:<该链的轮次>；轮次在链首任务被接取时加 1。 检查：读客户端里 .Chain 的使用位置，确认它是不是”完成后接取下一个”的指针；同时统计 66 个任务的 Chain 值是否能连成环。
对有物品需求的重复任务，从第二次开始按 C = need 扣真实库存，扣完通过推送同步到客户端。 这样每一轮的成本等于需求数量，奖励的总量就被物品来源的总量限制住了。注意，这是有意偏离”C = 0”：之所以只对 Repeat 任务这么做，是因为 C = 0 会让这类任务变成零成本的循环；这一偏离必须在 A04 的白名单里单独登记一行。
对没有物品需求的重复任务（零成本），每个任务每个服务器日最多发一次奖励。 去重键是 rep:<taskId>:<YYYY-MM-DD>，按哪个时区计算日期，材料未提供。这是一个代码常量，不属于新配置，但它是策略推断【推断】，不能当作原版行为。
6. Q5：Q7 硬规则的落地（20 行内）
var CREDIT = { TaskReward: 1, Drop: 1, Buy: 1, Maint: 1 }, DEBIT = { Sell: 1, Use: 1, Buy: 1, Maint: 1 };
function checkBag(before, after, events, ctx) {
  var exp = {}, i, k, n, e;
  for (i = 0; i < events.length; i++) {
    e = events[i];
    if (e.src === &#39;Maint&#39; && !(ctx.route === &#39;debug&#39; && ctx.backupVerified && e.reason && ctx.audit))
      throw new Error(&#39;maint outside debug route&#39;);
    for (k in e.items) {
      n = e.items[k];                                           // 正数为入账，负数为出账
      if (n > 0 && !CREDIT[e.src]) throw new Error(&#39;credit not allowed: &#39; + e.src);
      if (n < 0 && !DEBIT[e.src]) throw new Error(&#39;debit not allowed: &#39; + e.src);
      exp[k] = (exp[k] || 0) + n;
    }
  }
  var seen = {};
  for (k in before.bag) seen[k] = 1; for (k in after.bag) seen[k] = 1; for (k in exp) seen[k] = 1;
  for (k in seen) if ((after.bag[k] || 0) - (before.bag[k] || 0) !== (exp[k] || 0))
    throw new Error(&#39;bag &#39; + k + &#39; unexplained delta&#39;);
  if (ctx.route === &#39;debug&#39;) ctx.audit.push({ diff: exp, reason: events[0] && events[0].reason });
}
维护动作为什么豁免了却不会失控，靠的是四个条件同时成立：
只有 debug 路由才能产出 Maint 事件，正常路由产出的 Maint 事件会直接抛错。
写入前必须验证过备份。
必须写明原因。
本次差额必须写进审计记录。
另外，维护动作同样要经过逐键守恒的检查：它只能改动它自己声明过的物品数量。
7. Q6：入口枚举
最省事的办法：从 acceptTask 的发送点反推，而不是从配置列正推。 客户端每一次接任务，都必须调用发送 acceptTask 的那个函数，所以它的所有调用点，就是”任务从哪来”的完整清单。
grep -nE "[\"&#39;]acceptTask[\"&#39;]" bundle*.js     # 找到发送函数
# 再查这个发送函数的全部调用点；对每个调用点，追踪传进去的 taskID 变量是从哪个配置列或哪个应答字段取来的
预期会出现的来源类别，以及每类该查什么（以调用点的追踪结果为准）：
来源类别
查哪一列或哪个函数
NPC 对话
ReceiveNpc 列；客户端里构建 NPC 任务列表的函数（grep ReceiveNpc），它会对每个任务调用 judgeTaskCondition 做门控
完成后自动接取
finishTaskCallBack 和 updateTaskData 里读取的 Chain、CompletionEvent、finish_action、clear_task 列
地图触发
应答字段 triggerBoxs（getTaskCallBack 和 finishTaskCallBack 都会读它），以及 transfer、map_guide 列
接取时附带
ReceiveEvent、receive_action 列
物品或系统触发
调用点落在背包、物品使用或活动模块里的那些
用对照组排除数字巧合：只有同时满足以下两条，才能把某一列认定为入口列。
有代码证据：上面的调用点追踪确实把这一列的值当作 taskID 传给了 acceptTask。
统计显著：任务 id 在这一列里的命中率，显著高于两个对照组的命中率。对照组一是把任务 id 各加 7 之后的值，对照组二是从任务 id 的取值范围内随机抽取、但不属于任务表的 id。
需要注意，Pre-Require 不是入口，它只是门控：任务能不能被接取，由入口决定是否出现，再由 Pre-Require 判断是否放行。可达性图应该从”入口集合”出发，用阈值语义做门控，而不是把 Pre-Require 当作边来用。
8. 反例：静默出错的场景
快速连打同一只怪。 开了自动战斗或者跳过战斗，两场结算的间隔小于 5 秒，第二场的掉落被窗口吞掉。不报错、也没有日志，而且因为掉落不回 rewardArray，玩家本来就看不到获得界面，所以连”少了一次”都察觉不到。
推送早于回调。 按 Q3(b) 的时序，奖励物品在客户端被显示两次。存档本身是对的，玩家看到的数量是错的，直到下一次同步。
Repeat 任务的奖励被一次封顶。 66 个重复任务从第二次开始都不发奖励，客户端显示一个空的奖励界面，所有守卫和断言都通过，因为这一切都是”设计”出来的结果。
rewarded ⊆ questDone 被整体放宽。 如果为了让 D 能通过而去掉了这条断言，下一次奖励名单丢失或缩水（E 类事故）就不会再被拦截。
掉落掷点与自检的确定性冲突。 掉落用的是 Math.random()，自检和外部测试只要覆盖到概率掉落，结果就不可复现。如果为了让测试稳定而在测试里把概率当成必得，测试就不再代表真实路径。正确的做法是把随机数源注入进去：生产环境用 Math.random，测试用固定种子。
9. 假设
H1：客户端的 HTTP 封装不会对 CheckBattleResult 做业务层重发。不成立时，Q1 的方案 1（不去重）失效，要改用方案 2、3、4 里第一个成立的。
H2：finishTaskCallBack 对 rewardArray 是在本地累加数量。不成立时（它读取的是绝对值），Q3(b) 的时序不会出问题，第 8 节第 2 条也不成立。
H3：Repeat≠0 的任务在设计上就是要反复领奖。不成立时（它们只是零奖励的剧情循环），Q4(a) 的”会残废”不成立，一次封顶可以保留。
H4：Chain 列是”下一个任务”的指针。不成立时，Q4(b) 的第 1 条失效，只能使用第 2、3 条。
H5：客户端里所有的接任务行为都经过同一个发送函数。不成立时（比如有多个不同的接口名都能接任务），Q6 必须对每一个接口名分别执行一遍。
H6：774 个 Reward 对应的奖励数据确实存在于某处。不成立时（它们就是无效值），rewardPending 会一直挂着，这种情况下应在确认之后批量清空，并写入审计记录。
