【角色】
你是一位负责"离线游戏服务端/任务系统"的资深架构师。材料是脱敏后的技术描述，不含商业信息。
请只回答我列出的四件事，不要扩展到我没问的范围。

【背景（与上一批同一项目，已按你的建议定了分层）】
这是一个单机离线场景：客户端是现成的（Cocos Creator 2.x 手游，HTTP 请求/应答式 RPC），我不能改客户端，
只能在自己的进程里拦截请求并生成应答。玩家的全部进度存在一个 JSON 文件里（1–100 KB），无数据库，进程随时可能被杀。

我们已经按"动作路由 + 领域决策 + 结算 + 持久化 + 投射"分了层：
- L0 路由（默认走 replay）、L1 请求→意图、L2 领域决策（纯函数，产出事件或拒绝）、
  L3 结算（唯一改状态的地方）、L4 持久化（校验→写→回读）、L5 投射（快照/增量）。
- 未实现的动作落到 F 降级层（旧回放逻辑），它的 replace 集合必须取状态投射，不许回空。
- 持久化链：顺序迁移 + 写前校验 + 写后回读 + 缩水守卫（技能等级下降/已完成任务减少/背包清空 → 拒写）。

【任务系统的现状】
- 配置表里 4842 个任务，字段：TaskID、Type、Require（前置）、SpRequire（完成时必须携带的物品，格式 "物品id,数量|物品id,数量"）、Reward（奖励=掉落表 id）。
- 客户端自己算"任务显示状态"，服务端只被问两件事：接任务（acceptTask）、交任务（getFinishTaskAward）。
- 客户端提交完成时**不会**告诉服务端"我打了多少只怪/采了多少个东西"，请求里只有 taskID。
- 我现在的实现是权宜之计：接任务时按 SpRequire **自动补齐所需物品**，于是"完成任务"永远成立；
  交任务时按 Reward→掉落表 展开发奖，并用"已发奖励名单"防重发。
- 结果：任务能一路点下去，但**任务内容没有真实进度**（没有计数器、没有"杀 N 只"、没有"到达某地"）。

【约束】
1. 客户端一行不改，它不会上报击杀/采集计数。
2. 只能从这两类信息里推：客户端请求里带的参数，以及它自己的其他请求（例如打怪时会有独立的结算请求）。
3. 单玩家离线；不允许数值凭空增加；重复提交必须幂等。
4. 配置文件里的 Require 是"flag,taskID,param|..."的结构串，不是裸 id 列表。
5. 存档只有一个 JSON 文件；新增字段必须能通过版本迁移引入。

【我要你回答的四件事】
1. 在"客户端不上报计数"的前提下，任务进度有几种可行的建模方式？
   每种的先决条件（需要客户端发哪些其他请求）、精度、代价各是什么？给一张对比表。
2. 如果只能靠"打怪结算请求"和"采集/使用物品请求"去推断进度，推断逻辑应该放在 L2 还是 L3？
   如何保证"同一次打怪不会同时推进两个任务、也不会被重复计数"？给出去重的键设计。
3. 给出"任务进度"的存档字段设计（要能支撑：多任务并行、离线补算、跨版本迁移、以及"进度回退"守卫）。
4. 给 5 条可翻译成代码的断言，专拦：重复计数、跨任务串味、进度回退、已完成任务被重开。

【回答格式（严格照这个来）】
