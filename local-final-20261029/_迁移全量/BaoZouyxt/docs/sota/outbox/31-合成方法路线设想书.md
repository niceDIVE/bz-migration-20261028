## 一、转向的背景与理由（如实陈述）

1. **成本事实**：bz-oracle 线自 v2.1 起 2 天内出了 5 个版本，每版配 changelog、审计、验收报告、回执与回执的回执；同期注册表 DONE 从 0 增至 6。验证流程的消耗与内容还原的产出之间比例失衡，用户明确裁定转向。
2. **信息基础已经具备**：真三包版本核对通过（M2 行号锚点 2336/2336、字段级断言 1796/1796，见 R22 执行第一轮）；442 张表在库；请求/应答形状可从客户端源码与已有捕获直接取得。批量实现所需的信息在仓内是齐的。
3. **执行体成本结构**：环境手术类工作（设备操作、会话管理）错误率高且消耗大；批量代码生成类工作信息完备、错误率低。方法应向后者倾斜。
4. **真服抽样的角色变化**：从"每个动作的判定依据"降级为"每个原型抓 1-3 个代表做行为校准"。理由：试错成本从 317 次摊薄到 ~8 次；且 R22 执行中实测出会话窗口与双重登录限制（见《R22执行报告-第一轮》附录），逐动作真服采样在操作上不可扩展。

## 二、对象拆解（实测）

GEN-READY 共 317 个，按契约字段签名归类：

| 原型 | 数量 | 例 | 服务端行为 |
|---|---:|---|---|
| 确认型 | 63 | changePlayWooksState、BeginRollDice | 校验后回 eRet:1（+已知状态钩子） |
| 条件领奖型 | 66 | LeaveCopy、getSnowAward | 查条件 → 发奖 → 登记 done |
| 表服务型 | 13+ | boosRankList、GetHouseShopData | 从 442 表取行集返回 |
| 社交依赖型 | 7 | ChallengePVP、getFriendHomeList | 离线降级：合法空数据/拒绝 |
| 状态查询型 | 5 | getVigor、GetWhoreData | 存档状态投影 |
| 时间窗型 | 3+ | EndMeditation、EndRecoverMP | Begin/End 对结算（f(时长, 表)） |
| 待归型 | 160 | getCopyData、wearFasion、BuyHouseShop、upgradeBed | 按动作名预判大部落入领奖/表服务/购买/升级/穿戴，写时定型 |

## 三、方法设想

1. **~10 个原型模板，而非 317 个独立 handler**。每个模板封装该类行为的共性：应答形状、账本投射（ivch/eco/eqch/skch/attrch）、persist、日志。
2. **每个动作 = 一行配置**：`{原型, 数据源表, 货币, 奖励引用, 状态键}`。配置错改配置，不动模板。
3. **归型三依据**：应答字段签名 + 动作名 + M2 读点；归不进的进"手工件"队列，按玩家主线优先。
4. **代表抽样**：每原型选 1-3 个代表，一次探针会话内完成（登录后早期窗口，R22 执行已实测窗口边界与双重登录限制）。代表选择标准：只读优先、可安全触发、避开 CAPTURE-1/一次性动作。拟选：确认型=setOnHookWookState（已有半个样本）；表服务型=GetHouseShopData / getFasionShop / boosRankList；状态查询型=getVigor；时间窗型=BeginRollDice。领奖型暂缺可触发代表（条件未满足），以客户端读点定形 + 合成值标注（沿 06b 先例，source:"合成"）。
5. **正确性口径的转变（本文请 SOTA 裁定的核心）**：DONE(a) 的判定从 R22 D1 的"每种拒绝理由须有真服样本或带 source 规则"，放宽为——**实现完成 + 每条推断标注来源（index.js 行号/表列/"合成"）+ 冒烟绿 + 玩家实测无异议**。玩家实测即最终验证；实测发现行为不对，改配置不动模板。
6. **回归门槛**：selfcheck（1242 项）+ acceptance（38 项）每批必跑，绿即过批。裁判系统保留但降级为冒烟过滤器；不再逐动作出具判定文书。
7. **产出节奏**：每批 20-30 动作，批批冒烟；汇报只报数字（覆盖数、冒烟结果）。

## 五、风险与失效条件（主动列出）

1. **原型归纳错误**：代表样本行为不能代表同型动作。缓解：每型 2-3 代表、玩家实测兜底、错误修正走配置层。
2. **完成口径放宽的代价**：DONE 数会快速上升，但其含义已从"真服验证过"变为"实现+标注+实测无异议"。还原率的统计口径需 SOTA 重定义（建议在 registry 里分列"verified"与"implemented-annotated"两档，不混计）。
3. **形状表冲突**：fillShape 会给应答补默认字段，handler 与形状表不一致时会出现"写了的被改回"（saleItem 前科）。缓解：每批抽验形状补全行为。
4. **待归型 160 的预判错误**：动作名预判可能归错型，写时人工定型即可，但若某子类规模超预期（如 30+ 个同属一个未见过的原型），则模板数 +1，成本模型按此更新。
5. **会话窗口的不稳定性**：窗口时长不固定（实测同一会话早期可用、后期双重登录），代表抽样可能需要多次登录尝试。此为操作成本，不影响方法成立。
