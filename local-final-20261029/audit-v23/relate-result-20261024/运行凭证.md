§4 第 3 步的 N 为什么只有 5 —— 这是「遇到问题」第一条，按约定交回代码

结论：N 小不是协议名写法不同，而是**分派表的形态不同**。本工程的服务端不写
`'User.useItem'` 这种字符串字面量，它把 handler 挂在一个以**裸动作名**为键的对象上，
`User.` 前缀是在运行时拼出来的（`'dispatch User.' + action`、`res['User.' + action]`）。
于是 PROTO 那条正则全文件只命中 8 处、5 个动作。

证据（同一正则跑 bz-rpc-server.js，148377 字符）：
  字面量命中 8 处 → User.getFinishTaskAward ×3、User.ReqSelfBattleInfo ×2、
  User.CheckBattleResult、User.useItem、User.equipWeapon
  分段长度（extract_rw.py 的「到下一个协议名」+ 末位 20000 字窗口）：
    22 / 79 / 14250 / 366 / 1888 / 33976 / 26385 / 15566 字符（前两段 22、79 也属
    getFinishTaskAward，可以忽略；真正吃到别人代码的是 14250 / 33976 / 26385 / 15566 这四段）
  → 一个「动作」的段落跨了 350～800 行别人的代码，所以这 5 条连内容也不可信：
    例如 rw.json 里 User.useItem 的 writes 是 coins/contribution/gold/playerEquip，
    那不是 useItem 干的（它写的是 bag）。
  也就是说：这轮的 rw.json 可以算「空信号」，relations.md 里 rw:bag 那几条边不要当真。

handler 的花括号块切段，再套原来的 ACC 规则即可 —— 本文件 87 个 handler 一个不漏。
