1. 结论
最大的错位是 F1 暴露出来的”自检恒真”，它不只是一个故障，而是整个验证体系的问题。 dispatch 的顺序是先跑 handler、再跑 fillShape，所以”形状字段必须在应答里”这条断言检查的其实是 fillShape 自己的产出，永远为绿。它掩盖了 F1，也同样可能掩盖 F3–F6 这一类故障。这条断言必须改为检查”handler 的产出加上来源标记”，见 Q1。
L4 观察守卫有两处错位。
它检查的是”账本差额有没有出现在应答里”，这是 L3 的投射一致性，不是 L4 的”差额有合法来源”。两者都需要，但不能混在一起叫守恒。
它豁免了带 rewardArray 的动作，而这些动作恰恰是重复发奖和吞奖最容易发生的地方。rewardArray 本身就是事件声明，这类动作应该改为检查”差额必须等于 rewardArray”，而不是豁免。
F1 的善后材料未提供。 3626 被消耗时，服务端扣了没有？技能写入了没有？如果扣了物品、没有写入效果，就是一笔可以从日志确定的损失，应该按”可推导就补回”的原则用 bzPatch 补回。只读判别：在 JSONL 里查那次 useItem 的 ivch/skch。
F2 用客户端上报的 hg 作为基准值，这一点材料没有说明边界。 服务端存档里有没有 hunger，上限是多少，材料都未提供。如果 LoadGame 不从存档返回 hunger，那么重启之后饱食度的来源也是材料未提供。至少要做到两点：给 hunger 加上上限截断（上限值从配置读取）；如果 hg 超出合法范围，就不发 attrch。
F3 的 [物品id, 0] 中，第二个元素的含义材料未提供（可能是”是否已拥有”，也可能是价格或状态）。如果它表示”已拥有”，现在等于把 266 件时装全部白送了；如果它表示状态码，0 的含义也必须先读 showItem 确认。
2. Q1：形状表边界
判别法（可以写成脚本：用 acorn 解析 ES5，输入是客户端源码和形状表）
建立”动作 → 回调”的映射：对每一个 send("User.xxx", data, cb) 调用点，解析出 cb 对应的函数体。如果 cb 是成员方法引用，就去解析对应的类方法。
跟踪别名：在回调函数体里，把应答参数 e 的别名都找出来，比如 var t = e、this.data = e、n = e.data，最多跟进一层同类方法调用。另外，对于按 key 逐个分发的写法（比如 59325 处的 note 逐键 dispatch），要按分发表把每个 key 映射到它的处理函数，否则 F2 这类字段会被扫描漏掉。
对每个字段的每个读取点打标签：
标签
读取模式

存在开关
带引号字段名的 hasOwnProperty 判断、in 判断、与 undefined 比较

真值开关
if 中只判断字段、与运算短路、三元条件

有默认值
或运算给默认值

契约
判断之外的解引用：取子字段、下标、取 length、作为参数传给会解引用的函数

键集合契约
对字段本身调用 hasOwnProperty 判断键名，见 F5

合并成一个字段的最终分类，规则依次判断：
只要有一处读取点是在判断外解引用 → 契约。
否则，如果有存在开关 → 开关。
否则，只有真值开关或默认值 → 惰性可缺。
完全没有读取点 → 惰性。
别名没有解析出来 → 未定，输出到人工清单，不自动处理。
用已知故障当标注集，跑回归：分类器必须正确判出以下结果，否则不能上线。
useItem.formulaID → 开关
GetFashionList.FashionArr → 契约
getFriendPartner.notFriendPartnerData → 契约
groupPoints → 键集合契约
getActivityCounts.dataArr → 契约，而且类型是数组
getSevenTaskList.taskObj → 见下文”开关升格”
生成器的最小规则
开关字段默认不填：fillShape 只补”契约”类字段。开关字段只有在 handler 显式给出值时才出现在应答里。
开关升格：如果一个存在开关的 else 分支既不关闭也不打开界面，或者为空，而 if 分支里包含关闭弹窗、移除节点之类的收尾动作，那么这个字段要升格为契约，必须发送，否则就会重现 getSevenTaskList 那次卡死。
值合法性：如果开关的 if 分支里，拿字段值去调用 getItem(值, "表")，那么 handler 给出的值必须是这张表里存在的主键，否则就不发这个字段，这样可以防住 F1 这类问题。
顺序与墓碑：执行顺序改为”先 fillShape 生成默认值，再交给 handler 覆盖”；或者保留现在的顺序，但允许 handler 写入 OMIT 墓碑，由 fillShape 跳过。
把自检改成检查来源：
function fillShape(resp, shape, prov) {
  for (var f in shape.contract) if (!resp.hasOwnProperty(f) && resp[f] !== OMIT) { resp[f] = clone(shape.contract[f]); prov[f] = &#39;fill&#39;; }
  for (var g in resp) if (resp[g] === OMIT) delete resp[g];
}
// 自检：被 fill 补出来的字段，不能是开关字段
for (var f in prov) assert(!(prov[f] === &#39;fill&#39; && SWITCH[action][f]), action + &#39;.&#39; + f + &#39; filled switch&#39;);
3. Q2：隐式内联数据
扫描思路
找入口：对每一个 cc.Class，收集它的 setData 和其他赋值点（this.data = t、this.x = t.y），再收集生命周期方法 onLoad、start、onEnable、update，以及从这些方法同步调用到的同类方法（最多一层）。
把 UI 和动作连起来：如果某个动作的回调里调用了 X.setData(e…)，或者实例化了 X 的 prefab 并传入 e，就把 X 的需求挂到这个动作的应答字段上。
按访问路径打标签，例如 this.data.FashionArr[u][0]，并从用法推断类型：
取 .length 或数字下标 → 数组
[i][0] → 二维数组
for in 或 hasOwnProperty → 对象
做算术或比较 → 数字 F6 就是类型推断的反面教材：默认值给了 {}，客户端却把它当数组用。所以形状默认值的类型必须来自这里推断出的类型。
区分”无条件必需”和”有默认值可缺”
分类
判别条件

必需且非空
某个变量只在”遍历数据的循环体”里被赋值，而在循环之外（或其他方法里）被无防护地使用；F3 里的 curSelectType 就是这种情况

必需且每帧
在 update 或 schedule 回调里被无防护地解引用；F4 就是这种情况，一旦缺失会每帧报错

必需（类型对即可，可为空）
只作为循环边界，或者只做遍历，循环之外不依赖它

有默认值可缺
外层有 if、与运算短路、或运算默认值、try 包裹

惰性
只被赋值，从未被读取

“必需且非空”类别的判别是机械的：变量 v 的所有赋值点都在 for (…; i < P.length; …) 的循环体内，同时 v 至少有一处读取点不在任何以 v 为条件的判断里。凡是命中这一条的路径 P，形状默认值都必须至少包含一个合法元素（元素从配置表生成），不能是空数组。
4. Q3：权威数据缺失（转世拒绝）
只读判别步骤
发送前的修改：在 isCycleLife、cycleLife、specialCycleLife 的每个发送点，读它前面 40 行，列出所有赋值和调用，重点看三类：
写入模型：RoleBaseInfo、RoleOtherInfo、InventoryModel 的 setter
清档或切场景：killRoleClear、loadScene
写本地存储：cc.sys.localStorage.setItem 只要有任何一项出现在发送之前，拒绝之后它就会留下来。
回调的 else 分支：对 eRet≠1 的分支，检查三件事：
发送前设置的遮罩、加载圈、按钮禁用、isRequesting 一类标志，在 else 分支里有没有被复原。
如果没有复原，按钮会一直失效，直到重启。这不是存档损坏，但会让玩家觉得”卡住了”。
是否 switch(eRet) 对 2/9/4 都有分支；落进 default 的话会做什么。
通用网络层对 eRet 的特殊处理（这是最大的风险点）：在 HTTP 封装或通用分发里 grep -nE "eRet\s*==+\s*[0-9]"，确认 2、9、4 有没有被全局截获，比如很多游戏里 2 代表”会话过期，踢回登录”。一旦被全局截获，拒绝就会变成踢下线或重新登录。
提示文本：如果客户端用 getItem(eRet, "errorcode") 之类的方式取提示，就要确认 2、9、4 在表里存在；不存在的话会得到 null，再取 .name 就崩溃，和 F1 是同一个形态。
服务端断言：拒绝分支不能写盘。
assert(md5(saveBefore) === md5(saveAfter))
会不会留下坏状态
存档层面：不会，前提是第 5 步的断言成立。
客户端内存层面：取决于第 1、2 步的结果。如果发送之前就改了模型，或者 else 分支不复原标志，会留下坏状态，但重启可以恢复。
本地存储层面：如果第 1 步发现发送前写了 localStorage，坏状态会跨重启保留，这是唯一真正持久的风险。
通用层层面：如果第 3 步发现 2、9、4 被全局截获，必须换成没有被截获、并且提示文本存在的错误码。
5. Q4：不可达入口的边界
可以伪造的（纯表现层，不进账本）：
拉起 UI 本身，以及 UI 需要的 npc 上下文（npc id、对白），前提是只调用 UI 打开函数。
从配置可以完整推导出来的展示数据，比如 BZ_EXCHANGE 的货架和价格。
一旦伪造就会破坏一致性的：
直接写模型或账本：召唤通道只允许调用 UI 打开函数，绝不能调用 setItem、updateEq、属性 setter。召唤之后发生的兑换请求，必须走正常的 handler 和 L4 守恒（扣代价、加商品）。断言：召唤通道执行期间，推送计数增量为 0，存档的 md5 不变。
位置和场景状态：如果召唤是通过传送实现的，存档里的坐标或地图会被写成 Map=0，下一次加载时进入一个不存在的地图，造成软锁。所以只能拉起 UI，不能移动玩家。
服务端独有的规则：转世的重置规则不在客户端，江湖（Type117）的进度和排名数据也材料未提供。凡是要服务端给出结果、而规则又推导不出来的入口，都不能召唤，否则等于把伪造搬到了 UI 之后。
付费边界：只要某一行兑换的代价是付费货币（4001–4003 是不是付费货币，材料未提供），这一行就要从召唤后的货架里排除，否则就违反了”不实现支付”。
距离校验：如果客户端在提交兑换之前检查玩家离 npc 的距离，召唤之后这一步会失败，或者被绕过。服务端的 handler 本来就不应该依赖距离，这一点必须保持。
召唤通道本身的护栏：只能在 debug 路由里触发；必须满足 ctx.live === true；每次触发都写入 meta.actionStats 和审计记录。
另外，Map=0 也可能是有意隐藏的（活动专用、功能已下线、付费功能）【推断】。做召唤之前，先查这些 npc 在别的表里有没有被引用（活动表、剧情 transfer 列）；如果有被引用，入口就应该从那条链路接上，而不是召唤。

7. 反例
开关升格的规则漏判：如果 else 分支里只有 cc.log，规则会把它当作”else 为空”并升格成契约，强制发送这个字段；而如果 if 分支里有 getItem(值)，强制发送的值不合法就会重现 F1。所以当升格规则和值合法性规则同时命中时，必须从配置里选一个合法的值；配置里也没有合法值时，转入人工清单。
静态扫描的盲区：动态字段名（e[k]）、跨类的事件派发（cc.systemEvent.emit 把 e 传给别的 UI）、setTimeout 延迟读取，静态扫描都看不到。分类器会把这类字段判为”惰性”，实际上却是契约。F2 那条按 key 分发的链路就是这种情况，必须把分发表单独建模。
F2 用 hg 做基准：如果客户端的 hg 是在本地计时扣减之后的值，而服务端又从来没有保存 hunger，那么重启之后饱食度的来源就是未知的，attrch 给出的值可能和 LoadGame 给出的值互相打架。
把 eRet 2 当作”入口提示”：如果通用网络层把 2 定义为会话过期，玩家一点转世就会被踢回登录界面。这不会损坏存档，但会形成”一点就退出”的静默体验问题。
观察守卫的豁免：掉落和任务奖励这类带 rewardArray 的动作，如果出现重复入账，观察日志里一条记录都不会有，因为它们恰好在豁免范围内。
8. 假设
H1：客户端的回调都是通过 send(name, data, cb) 这种可以静态解析的形式注册的。不成立时，Q1 的第 1 步要改成”在运行时拦截回调注册”（也就是在进程内记录 cb 的 toString 位置）。
H2：所有 UI 都是在 setData 和生命周期方法里同步读取数据的。不成立时，Q2 的扫描会漏掉异步读取，需要把 scheduleOnce 和 setTimeout 的回调也纳入调用图。
H3：2、9、4 没有被通用网络层截获。不成立时，Q3 的拒绝码必须更换。
H4：成就的条件大部分能从存档推导出来。不成立时，Q5 的第 1 位和第 2 位对调。
H5：兑换的代价物品里没有付费货币。不成立时，Q4 的付费边界要排除相应的行；如果全部被排除，Q5 的第 3 项降到最后。
H6：[物品id, 0] 里的 0 不表示”已拥有”。不成立时，F3 的修复等于把全部时装白送，需要改为按存档里的真实持有情况生成这个值。
