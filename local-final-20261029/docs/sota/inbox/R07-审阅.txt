1. 结论
按第 2 节的判据，下一步先修契约层（②），但理由要换。 不能用”只有②改错是静默的”来论证：策略层（④）出错同样会静默，这一轮的 118 行就是证据。成立的理由是：在四层里，只有②既有已知、尚未关闭的缺陷，暴露面又能从材料数字算出来，是 337 个形状动作中的 184 到 303 个。
第四节那张表里，判错的是④（连带③）的后果。 那 118 行属于策略层的错误：exchangeItem 用了共享的 grantItem 来发奖，配置导出链本身没有出错。这个错误同时影响 118 行，客户端不报错，旧的检查器还判绿。所以”④改错只影响单个动作、秒级就能抓住”这一判断不成立。
①写的”游戏起不来”只说中了一半：报错会很明显的那一半。 编解码层也可能只在部分数据上出错（例如大整数、多字节字符），这种错误同样是静默的。三包里有没有这类数据，材料未提供。
改分类器之前，先把第 5 节的冻结断言放进 CI。 否则改分类器这件事本身，就会成为一个新的静默故障源。
材料里有两处矛盾，需要先指出。
本批写自检”原 1224 项”，上一批写的是 1124 项，相差 100。
F4 说”只要任何地方 presence 读过，就一律判成开关”，但 F3 写明合并顺序是硬编码的 deref 优先于 presence。按 F3，47 个冲突字段目前全部被判为契约或键集合契约。所以当前真正的风险方向是”某个动作的开关字段被全局补发”（F1 型崩溃），而不是”契约字段被剔掉”。
补充里的 upgradeSkill 应该排在②之前处理。 它只需要只读一个回调，几分钟就能完成，而且是一个在用的动作上正在发生的账本与客户端分叉。见第 8 节。

3. Q2 答
(a) 合并规则
运行时不做跨动作合并。对每一个（动作 A，字段 f），按下面顺序取第一个成立的规则：
f 在 A 的升格表 PROMOTED 或 SHAPE_OMIT 里：按表执行。
A 的回调范围（span）内有 f 的读取，并且这些读取没有通过别名或成员赋值逃逸出 span：只用 span 内的读取来定类。如果 span 内同时有 presence 和 deref，按 R06 Q1 的规则处理：
deref 全部落在 presence 判断的真分支里：判为开关。
有 deref 落在 presence 判断之外：判为契约，而且必须给出合法值。
给不出合法值：写进人工清单，生成器拒收。
f 有逃逸（例如 this.x = e.f，或者别名被 span 之外的代码读取）：沿逃逸链找到外面的读取点再定类。如果找不到：
冻结：沿用当前线上的发出行为（发还是不发、默认值是多少）保持不变，标记为”未定”，进入人工清单。
全局的字段分类只是构建期的中间产物。它可以给规则 4 提供”线上现状”作参照，但不能单独决定任何一个（A，f）发还是不发。
(b) 会不会复现 F1 崩溃
按 (a) 的规则，useItem.formulaID 由 useItem 自己 span 内的 presence 判定为开关，全局的 deref 不会参与，所以 F1 不会复现。
但风险方向反过来了。现在这 47 个字段全部是”补发”。改成按 span 判定之后，可能出现”补发改成不发”的变化，这会复现 F4 型崩溃。notFriendPartnerData 就是典型：它在 span 内只有一次成员赋值，真正的 hasOwnProperty 读取要隔两跳，发生在 PartnerNewModel 里。
所以要加一条硬约束：任何一项从”发”变成”不发”，都必须附带证据证明没有逃逸（见第 5 节的 C3）；拿不出证据就走规则 4，保持冻结。
(c) 形状表的结构
选择：运行时只保留一套动作级的表，在每一项上加上来源和作用域；字段级的全局分类留在 tools 里，不随运行时发布。

  scope: &#39;span&#39; / &#39;escape&#39; / &#39;frozen&#39; / &#39;promoted&#39; / &#39;omit&#39;,

}

断言：在 core/ 下 grep __switch[ 的每一处用法，键都必须是（动作，路径）对，不能只用字段名。
什么时候才需要第二套运行时数据：handler 自己产出了形状里没有的字段，而运行时又需要判断这个字段该不该发。材料没有提到存在这种情况，所以目前不需要。
4. Q3 答：没有 AST 时怎么做到动作级 span
前提断言：三包里箭头函数 => 的出现次数为 0，with ( 的出现次数为 0。任何一项不为 0，本节方法对相应文件失效。
第 0 步：最小分词器。 逐字符扫描，维护当前状态：代码、单引号字符串、双引号字符串、行注释、块注释、正则字面量。判断一个 / 是不是正则的开头，看它前面的记号是否属于 ( , = : [ ! & ? { } ; return typeof，或者逻辑或运算符。输出每个位置的括号深度。
第 1 步：函数树。 遇到 function 关键字，就记录 {名字，形参表，函数体起点，函数体终点（用括号配平找到），父函数}。同时记录每个函数体里在自身深度声明的 var x（不算嵌套函数里的声明；ES5 的 var 会提升到函数顶部），以及 catch (x) 绑定的变量和它所在块的范围。
(i) 匿名回调：用下面的正则在代码状态下匹配，匹配位置紧跟着的那个 function 就是回调，它的函数体就是 span。
/MessageCenter\.on\(\s*([\w$.]+)\s*,\s*function\s*\(/
响应对象是第几个形参，要去网络层的 emit 调用点对照位置。材料未提供；function(t, e) 里 e 是响应对象只是【推断】。
(ii) 具名回调：匹配 MessageCenter.on(CMD, this.foo, this) 或 this.foo.bind(this)。
先找到注册语句所在的 cc.Class({ ... }) 范围，在这个范围里、类字面量深度加 1 的位置找 foo: function(。
找不到，就沿 extends: 去父类里找；还找不到，归入”未解析”。
foo 被多个 CMD 共用时，span 同时归属于所有这些 CMD。如果函数体里有 if 块的条件把某个形参和 HttpConst.X 作比较，这个块只归属于 X；块外的读取归属于所有 CMD。
(iii) 嵌套函数复用同名形参：对 span 内每一次出现的标识符 e，从包含它的最内层函数开始向外找，第一个在形参、var 声明或 catch 中绑定了 e 的函数，就是 e 的绑定者。只有绑定者正是回调函数本身时，e.xxx 才计入响应字段。
对 e.list.forEach(function(e){ ... e.id ... })：内层 e 的绑定者是内层函数，所以不计入顶层 id。如果这个内层函数恰好是 .forEach / .map / .filter / .some / .every 的第一个参数，而接收者能解析到响应路径 list，就把它记为元素字段 list[].id。
别名：在回调里出现的 var t = e.list，把 t 绑定为 list 的别名。嵌套函数读取 t 时，同样按上面的规则查绑定者。
必然失效的形态：响应对象被整体交给 span 之外的代码，之后的读取全部发生在另一个函数或另一个类里。这是 notFriendPartnerData 那种两跳的形态，span 内的分析本质上看不到。可以在三包里 grep 出来：
grep -nE "this\.[A-Za-z_$][\w$]*\s*=\s*e\s*[;,]" index.js scripts2.js scripts3.js
grep -nE "\.setData\(\s*e\s*\)" index.js scripts2.js scripts3.js
grep -nE "MessageCenter\.on\([^,]*\[" index.js scripts2.js scripts3.js
grep -nE "MessageCenter\.on\([^,]+,\s*(this|[A-Za-z_$][\w$]*)\[" index.js scripts2.js scripts3.js
grep -nE "var e = e\." index.js scripts2.js scripts3.js
第一、二条：响应对象整体外传，必然失效，只能靠规则 3、4 处理。
第三条：CMD 是计算出来的，必然无法归属。
第四条：回调函数是计算出来的，必然无法定位 span。
第五条：重新声明响应变量本身，会让 (iii) 把 data.list 误记成顶层的 list。

7. Q6 答
(a) 反例与复现路径
成员赋值逃逸导致 F4 复现。路径：tools/classify_fields.js 改成按 span 判定之后，getFriendPartner.notFriendPartnerData 在 span 内只有一次成员赋值，如果逃逸追踪没做，就会被判为惰性，不再发出，PartnerNewModel 每一帧都会崩溃。C1 会抓住这个问题，前提是 C1 比对的是字面量，而不是”测试通过”。
共享具名回调的分支识别失败。同一个 foo 被 X、Y 两个 CMD 共用，函数体里用 switch(t) 或者用变量间接比较来区分，而不是用 if (t == HttpConst.X) 的形态，那么只属于 X 的读取会被归到 Y 头上，Y 会被补发它其实当作开关的字段。复现：在三包里 grep MessageCenter.on([^,]+, this\.(\w+)，按捕获到的名字分组，取出现两次以上的组，再人工核对函数体。
var e = e.data 重新声明。按 Q3(iii) 的规则，e 的绑定者是回调自己（var 会提升），于是 e.list 被记成顶层 list，而真实路径是 data.list。复现：用第 4 节的第五条 grep。
基线发出矩阵只跑空产出时会漏。fillShape 补缺但不覆盖，handler 自己给出的字段会掩盖形状的变化。所以 C2 必须同时跑真实样本那一遍；如果没有某个动作的录制样本（是否有录制样本，材料未提供），这个动作的 C2 只能算半覆盖。
兜底拒绝码也可能落进客户端没有的分支。exchangeItem 对 4002 回 eRet:4，客户端兑换回调有没有处理 4，材料未提供。这和 CYCLE_LIFE 静默丢弃 2 和 4 是同一族问题。现在全表命中 0 行，所以暂时无害；但一旦出现命中，表现就是”点了没有反应”。复现：读 core/bz-rpc-server.js 里 exchangeItem 的 eRet 4 分支，再到客户端 exchangeItem 的回调里 grep eRet，看有没有处理 4 的分支。

8. 对 C2 与 note.eco.potential 的判断
C2：一条断言只有在指向已知的错误版本时会变红，它的”通过”才算证据。所以每一个新检查器都要附带一次”对改前代码的红灯运行”，并把退出码 1 记录进 CI，第 5 节 C1b 就是这种写法。没有做过红灯运行的绿灯，在第 2 节里一律当作 A=0 计算。
note.eco.potential：它属于”字段落进客户端没有的分支”这一族，ECONOMY_CHNG 只认 ptt，所以 note.eco.potential 必然被丢弃。它是不是一个正在发生的缺陷，只取决于 upgradeSkill 的回调有没有读顶层的 potential 并写进模型：
回调读了顶层 potential：note.eco 那一项只是死字段，没有实际危害，把键改成 ptt 即可。
回调没读：客户端显示的潜能不会减少，比账本里的多。之后客户端会允许玩家继续升级，但服务端会拒绝，或者导致账本与客户端分叉。
这条应该排在②之前：判别只需要读一个回调。
9. 假设
H1：R05 的 6 次形状故障全部是在真机上发现、CI 没有抓到的（第 2 节里 A₂=0 的依据）。如果其中有些是 CI 抓到的，A₂ 会变大，但只要 E₂ 不小于 184，排序依然不变；只有当 A₂ 接近 1 时，第 1 节第 1 条才失效。

H3：三包是 ES5，没有 =>，也没有 with。不成立时，第 4 节对相应文件失效，3(a) 的规则 2 也会随之失效。

H6：每个动作都有可以用来跑 C2 第二遍的录制请求样本。不成立时，C2 对这些动作只覆盖空产出那一遍，第 7 节 (a) 第 4 条就是后果。
