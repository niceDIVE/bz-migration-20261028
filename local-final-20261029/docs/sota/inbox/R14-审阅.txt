1. 结论
§2 的七条处置都成立，第 4 条按 D 修正后的前提也成立。但设备实测里，拒绝应答是 {"eRet":4,"beginTime":0,"skillID":0}：fillShape 在拒绝路径上照样补了字段。T4 只禁止带”请求时刻”的 beginTime，并不禁止 0。拒绝应答的键应当收窄到 {eRet} 加上逐项登记的白名单（见反例 1）。
订正 A 成立。 我 R13 的第 1 档规则漏了一个限定：提示文本必须与拒绝原因语义相符，而且在拒绝时刻的字段下不会解引用失败。不满足时就降到第 2 档，并写上 tierWhy。这个三态设计我接受。
订正 B 对 4 成立；但你改选的 5 同样犯了 A 的错。 1333 你已经学会此配方了 只有在拒绝原因真的是”秘籍已学会”时才对；用它拒绝一个”效果未建模”的 buff 物品，同样是误导。所以 chosen 要按”动作 × 原因”来选，不能按动作选。
订正 C 成立：washAdditionalArr 的 4 是流程码。这也说明 R5b 的规则”eRet 的字面量只要不等于 1 就算拒绝点”太粗，表必须能把流程码表达出来（见 Q4）。
订正 D 成立。 我当时担心的是一种有条件的风险，实测表明它当前没有发生；改成 missingRequired 之后，真正的问题（live 里看不见缺了哪一条）也补上了。
本批暴露出的最严重的事实，不在四处订正之内，而是 dispatch:2605 的 catch 会把异常换成成功 ACK。 所有还直接写 s 的 handler，在抛出异常时都会留下”应答说成功、内存半写、下一次 persist 就把半写的值落实”的三方不一致。useItem 原子化只修了其中一处。catch 里应当做两件事：先 _save = null，丢掉内存缓存、改从盘上重读；再回这个动作登记的拒绝码，并写 REJECT 日志（见反例 2）。
2. Q1 答
先后：先产表，再去问用户
只读统计不需要用户裁定，条件是满足下面三条可判定的要求：
不写存档：产表前后，设备存档和沙箱存档的 md5 都不变。
不进入运行路径：impl 的产物里，对 obtainable 这个字符串的命中数为 0（CI 用 grep 断言）。
产物只放在 tools/facts/，与 lookup-keys.json 同级，性质同样是事实表。
先产表的理由：用户裁定需要知道代价有多大，也就是到底会影响几种物品、分别是哪些。没有这张表就去问，只能问一个空泛的问题。
关于”缩小可用范围”这个说法
这个说法要先校正。(b′) 拒绝的只是”需要服务端落地、而我们没有产出”的那一类物品。这类物品现在的状态本来就是：点了，物品没了，效果没有。它们不是”可用”的，而是”可被消耗掉”。真正由客户端在本地生效的那一类，不在拒绝范围之内。问用户时要把这一点讲清楚，否则用户会以为自己在放弃能用的东西。
裁定问法（一句话模板）
useItem 目前对以下 N 种物品”扣掉但无任何效果”（清单附后，每项写明来源和 Effect 码）；改为”拒绝、不扣、弹提示或无反应”以后，这 N 种物品会留在背包里、暂时不能使用，其余物品不受影响。是否同意？
N 和清单由脚本按”需要服务端落地 ∧ 可获得”算出来，不手填。
3. Q2 答
根因先修：ver 拆成两个字段
ver 应该拆成 ver（内容）和 built（时间）。今天就能落地的做法：
// build-handlers.js
var META_RE = /^(.*\bbuilt=|.*IMPL_VERSION\s*=|.*生成于 |.*"gen"\s*:)/;   // 只匹配这 4 类元数据行
var lines = product.split(&#39;\n&#39;), kept = [], stripped = 0;
lines.forEach(function (l) { if (META_RE.test(l)) stripped++; else kept.push(l); });
if (stripped !== 4) fail(&#39;META 剥离行数=&#39; + stripped + &#39;（必须正好 4 行；防止正则吞掉代码行）&#39;);
var contentHash = sha1(kept.join(&#39;\n&#39;)).slice(0, 8);      // 对外的 ver 用它
var built = new Date().toISOString();                      // 单独字段，不参与任何哈希

4. Q3 答
这个边界不够。 R5b 是对字面量的静态扫描，它看不到下面这些写法：
eRet: code、eRet: ok ? 1 : 4；
r.eRet = 4 这样的赋值；
从共享辅助函数里返回的码，比如 return reject(a, reason)；
还有最关键的一种：异常进入 dispatch:2605 的 catch 之后变成的成功 ACK。这种情况下，handler 体里根本没有任何拒绝点。
覆盖要分三层：
层
范围
断言

R5
表内 15 个动作，每个”动作 × 原因”至少一个夹具
实际返回的 eRet 等于登记的 chosen；磁盘哈希和业务哈希都不变；应答的键 ⊆ {eRet} ∪ 登记的白名单；有 REJECT 日志

R5b+
全部 87 个 handler 的源码
字面量扫描之外再加两条：eRet: 后面跟的不是数字字面量 1，或者出现了 .eRet = 赋值，都必须在表里登记成”动态码”，并带 ev；否则 FAIL

R5c
全部 87 个 handler 的冒烟测试
在沙箱里各发一次空请求 {}，再各发一次字段全部类型错误的请求：不抛异常（catch 计数器不能增加）；eRet ∈ {1} ∪ 登记码；只要 eRet 不等于 1，磁盘哈希就不变

R5c 的成本只有 174 次沙箱调用，却是唯一能抓到”catch 把异常吞成成功 ACK”的一层。为此，dispatch:2605 的 catch 里要先加一个计数器，比如 __bzCatchCount++。
5. Q4 答
同意保留在同一份文件里，不另建 flow-codes.json。 但表的结构要从”一个动作一条”改成”一个动作一组码”：
"washAdditionalArr": [ { "code":4, "role":"flow",   "reads":["attrList"], "ev":"index.js:144071#<sha8>" } ],
"useItem":           [ { "code":5, "role":"reject", "reasons":["recipeLearned"], "tier":1, "ev":"index.js:64906#<sha8>" },
                       { "code":<第2档码>, "role":"reject", "reasons":["effectUnmodeled"], "tier":2, "tierWhy":"提示文本均不符", "ev":"…" } ]
不拆文件的理由有三条：
同一个动作可能同时有流程码和拒绝码。拆开就要跨文件拼出一个动作的全部码，R5b 必须同时查两份文件，而且两份之间还会漂移。
R5b 回答的问题是”这个非 1 的码有没有被登记”，它需要一个统一的命名空间。
按”动作 × 原因”来选码（第 1 节第 3 条）本身就需要每个动作对应一组码。
flow 角色的码不适用 R1 到 R3，改用自己的 F1 到 F3：
F1：这个码必须在 handled 里，并且 ev 指向的那一行是一个非提示分支（加载界面、打开列表等）；
F2：应答里必须带有该分支会读取的全部字段（reads），而且类型正确，比如 attrList 是 4 段字符串；
F3：同一个动作里，flow 角色的码不能同时出现在任何 reject 条目的 code 中。
T7（washAdditionalArr 的 4 必须保持是 4）由 F1 加 F3 覆盖，可以保留作为回归。
6. 反例
拒绝应答里夹带了零值字段：BeginTraining 拒绝时发出 beginTime:0, skillID:0。如果日后有人按 tierWhy 的变化把 chosen 改成 3（比如 3 的文本被换成了更合适的版本），客户端就会执行 :120570 的 getItem(0, "skill")，得到 null，读 .Name 时抛出 TypeError。如果从一开始就不发 skillID，这条路径上至少不会多出一个必崩的值。
异常被吞成成功 ACK：某个仍然直接写 s 的 handler（比如出售、兑换），先改了 s.gold，再在读取模板时抛出异常。catch 回了一个成功 ACK，内存缓存里已经是改过的金币；下一个动作 persist 时，这个半写的值被写进盘。验收全绿，因为没有任何一条测试会让 handler 中途抛出异常。
用 5 拒绝未建模物品：玩家使用一个 Effect 23 的 buff 药，看到”你已经学会此配方了”，以为物品坏了或者被误判，于是反复尝试。
已知红项掩盖新的红项：core-test-server.js 本来就红。如果这个文件里又新增了一处失败，整套验收仍然是”32 绿 1 红，红项是那条遗留的”，看不出变化。已知红项必须细化到”文件 + 断言行 + 消息哈希”这个粒度来登记，同一个文件里出现任何其他失败都要判 FAIL。这张登记表同样受 G 规则约束。
META 剥离的正则过宽：日后某一行代码里出现了 rebuilt= 或者 "gen":，被当作元数据剥掉，contentHash 就看不见这次代码变更。“正好剥 N 行”这条断言能把它抓出来，前提是这条断言不被删掉，所以它也要进 required-checks。
T5 静态断言能被别名绕过：var sk = s.skills; sk[id] = [1,0,1]; 写在效果阶段，T5 匹配的是 s.skills[…]=，抓不到。R5c 的”异常时磁盘哈希和业务哈希都不变”才能从行为上把它兜住。
端到端仍未验证：协议层回声了 isCollective:0，但如果在门派练功界面里，e.isSchoolLiang 当时其实是 1 而不是 2（scripts2.js:38080 置 1），那么 :120523 会走 else if (1 != e.isSchoolLiang) 之外的路径，界面行为仍可能不符合预期。这只能靠人在 UI 上实际点一次来验证。
7. 假设
A1：除了 :120516 开始的回调之外，没有别的监听者会无条件读取 BeginTraining 应答里的 beginTime 或 skillID（材料未提供全局监听的取证）。如果有，第 1 节第 1 条从”应当收窄”升级为”正在发生的缺陷”，反例 1 也不再需要”日后改码”这个前提。
A2：dispatch:2605 的 catch 确实会把所有 handler 的异常换成成功 ACK，而不只是部分动作这样（你给的是一处证据）。如果只是部分动作，第 1 节第 6 条和第 4 节 R5c 的覆盖面要按实际范围缩小。
A3：_save = null 之后，下一次 loadSave() 会从盘上重读，而且盘上的内容就是上一次成功 persist 的结果。如果 persist 本身可能写到一半（单槽存档、没有 fsync），第 1 节第 6 条的回滚就要依赖 A03 的 A/B 双槽，否则重读到的可能是一份损坏的存档。
A4：useItem 的回调里，没有处理的码（比如 7 或 9）不会落进一个有副作用的 else 兜底分支。你在 R2(b) 里提到过 "else" 兜底分支；如果它存在并且会修改模型，第 1 节第 3 条里”effectUnmodeled 走第 2 档”就没有可用的码，只能在 1333 这类不贴切的提示和”回 1 但不扣、不产出”之间重新取舍。
A5：META 元数据正好是那 4 类行，并且每次构建都存在。如果某次构建缺了其中一类（比如 gen 改成固定时钟之后），第 3 节的行数断言就要同步修改，否则会误报。
A6：test/ 下的文件不会进入产物。如果会进入，第 3 节”挡不住”的第一项就已经被 contentHash 覆盖了。
