3. Q2 答
三条都不选。先对这 71 个动作分类，再分别定 catchCode。 理由是”没有 MessageCenter.on 注册行”并不等于”没有回调”：sendRequest(USE_ITEM, f) 这种写法说明，回调完全可以是在发送点内联传入的闭包。
可以写成脚本的分类方法：对每个动作常量，grep 它在三包中所有的引用点。
类
判据
catchCode

(i) 内联回调
存在 sendRequest 或 sendReqWithMask(<常量>, data, function…) 这样带第三个参数的调用
从这个闭包里抽 handled 集合，按原规则推导；同时还要抽出按真假判断和不等号判断，以及 if 链末尾的 else

(ii) 只发不收
有发送点，但没有回调参数，也没有注册行
不回 eRet。客户端不读应答，任何码都没有风险，唯一要确认的是遮罩会不会被清除

(iii) 从不发送
这个常量在全库里只有定义那一行
不回 eRet，登记为 role:"unreachable"，带上 grep 计数作为证据。客户端不会发，catch 就不可能被触发

现在的 (b) 恰好在 (ii) 和 (iii) 这两类上是对的。真正有风险的只有 (i)，你点名的三个动作都属于 (iii)。
“客户端收到一个它没有分支的应答”，实际风险是什么。 只有一种情况下是零风险：回调里只有 X == eRet 这种等值分支，而且没有末尾的 else。只要回调里有 1 != e.eRet、!e.eRet 或者末尾的 else，不带 eRet 和带 0 都会走进错误分支。如果这个错误分支还会解引用应答里的字段，就会崩溃。
(c)“任取一个非 1 的码”被否决，原因相同：它碰上末尾 else 的概率，和”不回码”是一样的，而且还多出了一种撞上流程码的可能。
4. Q3 答
门控中的原因也必须有夹具，而且两态都要
用户的裁定是”一行就能回退”，这是一个承诺。两态都有夹具，这个承诺才是可验证的。
// 夹具读取当前常量，决定哪一态是"现行行为"；另一态在沙箱里临时翻转常量后验证
var cur = impl._internal.REJECT_UNMODELED_ITEMS;            // 现在是 false

function openState(){   // 门控打开：拒绝、不扣

(cur ? openState : closedState)();  withFlag(!cur, cur ? closedState : openState);
withFlag 只在沙箱实例里翻转常量，跑完立刻恢复，并断言恢复后的值等于 cur。这样，一旦有人把常量改了，“现行行为”和”另一态”会自动对调，而两态依然都被测到。
数组顺序要计入
在 R5 里，数组顺序要计入，而且不需要任何例外。R5 只测拒绝路径，拒绝路径上账本的任何变化都是缺陷，包括数组重排。canon 只对对象的键名排序，不对数组排序。
只有到将来，如果业务哈希被用在成功路径上，才需要逐路径声明哪些数组是”集合语义”（这是 B01 的规则：按接口和字段判定，判不出来的按 replace 处理，也就是顺序要计入）。
最小集
表内每个”动作 × 原因”至少一个夹具：16 个动作、17 个原因，其中门控中的那一个原因要两态都测，合计 18 个夹具；
flow 码不在 R5 的范围内（F2 已经实际跑过 handler）；
catch 路径单独一个夹具（用你现有的注入式用例），加上断言”repushLive 抛异常时，仍然有应答发出”。
5. 对”39 件 / 6 个家族”收敛结果的判断
方向对，数字不能用来排期，顺序要调整。 下面四件事都排在实现任何一个家族之前：
在全表上重算可获得性：用 item.full.json（6525 行）作为定义域，重新跑 gen_obtainable.js，把域外那 2251 个 id 也纳入。39 很可能会变大。
追查 1792572970629 的来源：如果配置里的活动时间其实是泄漏进来的构建时钟，那么”可获得性”里由活动货架、活动掉落贡献的那一部分本身就是错的。这一项排在第 1 条之前，或者至少与它同时做。
按损失的紧迫度排序，而不是按家族大小：先做当前账本里就已经有的物品，也就是 Ledger(i) 为真的那些。这些物品现在每用一次就丢一个，是正在发生的损失；只是”可获得”的物品，只是潜在的损失。
先跑一遍查表归属探测（第 2 节第 1 步）：只需要一次 live 调用，就能确定 5、13、28 各自读哪张表，然后再去写 handler。
家族的实现顺序，按确定性和可复用性来排：
Effect 5：29 件。如果被证实是学技能，就能复用 ITEMSCH 的逻辑，以及 recipeLearned 这个拒绝码 5，确定性最高；
Effect 28：2 件，按 id 发放坐骑或特效，已经拥有的情况用拒绝码 15 或 16；
Effect 6、8、24：各 1 件，按探测结果逐个处理；
Effect 13：最后做。礼包会给出别的物品，这会扩大 Grant* 的不动点，做完之后还要重新计算可获得性；如果它是抽奖，还要先解决随机源的问题。
6. 反例
catchCode 0 命中按真假做的判断：某个已登记动作的回调写的是 if (!n.eRet) { show(getText(n.msgId)) }，handled 的抽取只认 X == eRet，没有抽到这一句，于是推导出 0。这个 handler 一旦抛出异常，catch 回了 0，客户端就会执行 getText(undefined)，得到一条空提示，或者直接抛出 TypeError。
内联回调被当成没有回调：71 个动作里，有一个是用 sendReqWithMask(X, d, function(e){ if (1 != e.eRet) { c.show(e.note.tip) } … }) 发出的。catch 不回 eRet，1 != undefined 为真，于是执行 e.note.tip，而 e.note 是 undefined，抛出 TypeError，遮罩也可能清不掉。
repushLive 在 catch 里再次抛异常：handler 因为某个技能 id 在客户端技能表里不存在而抛出异常；进入 catch 后，repushLive 对同一个技能执行 pushSkillToClient，又抛了一次。如果 catch 没有对 repushLive 再包一层 try，就不会有任何应答发出，sendReqWithMask 的遮罩会一直挡在屏幕上。
构建时钟泄漏进了配置：某个活动的起止时间是 1792572970629（2026-10-21 01:56:10 PDT，也就是 R11 里那个旧的构建时钟），只扫元数据行的断言放过了它。结果是这个活动被永远判定为”刚刚开始”，或者按这个时间开放货架，可获得性也跟着被污染。
可获得性的定义域偏小：某个 Effect 13 的礼包，id 落在原来 522 条定义域之外，实际上会从某个 npc 掉落。它不在 39 件之内，没有被排期，玩家每开一次，物品就被扣掉，只留下一条 CONSUME_UNMODELED 日志。
测试固化了无效请求的成功 ACK：日后客户端某个版本在技能已满级时发出不带 skillArr 的 upgradeSkill，服务端回 eRet:1，客户端进入成功分支，播放升级动画，然而什么都没有改变。改写后的测试要求的正是 eRet===1，会阻止有人把它修成拒绝。
guardHash 没有纳入 test/，可以借此登记 known-red：有人削弱或改坏了 test/x.js 里的一条断言，让它变红，guardHash 不变（因为不含 test/）。于是 G5 判定为”什么都没改”，允许扩容，这条红被登记成了”已知”。
Data1 的语义被同族的个例误导：Effect 13 里有一件物品的 Data1 是 4567，不等于它自身的 ID。如果统一按”自身 id 查礼包表”来实现，这一件会查不到，或者查到另一份奖励。第 2 节第 1 步的命中率统计必须按每一个 Data1 值去算，不能只看大多数。
7. 假设
A1：handled 的抽取目前只认 X == eRet 这种等值比较（这是从你 R14 的描述推断出来的）。如果它已经覆盖了按真假的判断、不等号判断和末尾的 else，第 1 节第 1 条的缺口和反例 1 都不成立。
A2：ConfigMgr 能列出它全部的表名。如果不能，第 2 节第 1 步就要靠 grep getTable(&#39; 和 getItem(…, " 的字面量，自己拼出一份候选表名清单。
A3：Effect 5 的 Data1 是技能 id【推断】。如果不是，第 5 节”Effect 5 复用 ITEMSCH 和码 5”的排序依据就不成立，要按探测出来的实际表重新排序。
A4：1792572970629 不在原始的配置导出里。如果原始配置里本来就有这个值（巧合），第 1 节第 2 条的”泄漏”判断和反例 4 都作废，第 5 节的第 2 项可以删掉。
A5：71 个动作里存在内联回调。如果 grep 之后发现全部都属于 (ii) 或 (iii)，第 3 节就退化为”现状即正确”，只需要补上 unreachable 的登记和证据即可。
A6：env 里没有确定性的随机源（材料未提供）。如果有，第 2 节和第 5 节里 Effect 13 “要先解决随机源”这个前置条件就可以去掉。
A7：只有 Ledger(i) 为真的物品才会真正发生损失（依据是 Math.min(n, have)）。如果客户端可以对不在背包里的物品发出 useItem，并且我们的 handler 在别的路径上还会扣除其他资源，第 5 节第 3 项的排序依据就要修正。
