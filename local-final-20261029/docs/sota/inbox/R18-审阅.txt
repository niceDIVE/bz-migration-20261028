1. 结论
§2 的十项处置里，2、3、5、7、8、9、10 成立；1 和 6 如实标为”未做”，判断正确；第 4 项（时间平移）成立，但有一个副作用。
平移的写法是”每次 LoadGame 都用 now - 抓包时刻 来平移”，这会让活动永远显示还剩 7 天：活动永不结束，抓包时尚未开始的活动也永不开始（见反例 1）。
用户已经裁定同意平移，所以这一项可以接受，但要把”活动永续”写进行为登记。
§3.2（Effect 28 是称号）的判断成立。 名字、表归属、titleID 回调三方证据一致。但它还缺一个落地点：LoadGame 必须把 s.titles 投射进 AchieveModel 的数据源，否则重启之后称号就丢了（见反例 2）。
§3.3 的判断成立，附带一个条件。 “dic 非空等价于已学会”只在任何路径都不会推送 lv=0 的 skch时才成立：119832 的 setSkill(n, e[o][0]) 不过滤 0（见反例 3）。
§3.4 里”原版允许对已学会的技能继续用”成立。 但从同一段证据还能推出一个更强的结论：Effect 11 无论学没学会，都走 ConsultUI。所以升级请求多半根本不是 useItem【推断】，不应该在 useItem 里补（见 Q2）。
2. Q1 答
① 不需要先知道表名，但不能只靠”以这 5 个 id 为主键”来筛
稠密 id 的问题还在：5 个 id 同时命中的表一定很多。改用下面三条特征的交集，每条都可以在 442 张 dump 上直接执行：
特征
可执行判据

F1 键集吻合
表的键集 K 要满足两条：Effect 13 全部物品的 Data1 都在 K 里；并且 Effect 8 和 13 两族物品的 id 与 Data1 合起来，占 K 的比例 ≥ 0.5。65268 里 8 和 13 共用”背包上限”检查，说明这两族都会发物品【推断】

F2 行内有奖励
行里有一个数组或对象字段，其中 ≥ 80% 的元素能在 item 表的 id 里找到

三条交集如果只剩一张表，就可以定表。如果剩不止一张，或者一张都不剩，再去客户端里找礼包内容预览：物品 tips 或者”可能获得”之类的界面，会用 e.ID 或 e.Data1 调 getItem(…, "<表名>")。grep 那段 tips 的代码，表名就是第二个参数。
templates.json 里如果有 useItem 的抓包能对上，就以抓包为准，优先于上面这些判据。
② 应答形态：方向对，但有三个前提
字段
规则

rewardArray
格式必须和现有 handler 已经在产的 rewardArray 逐字相同，直接复用任务奖励的构造函数。如果奖励里含有装备，还必须同时给 equipObj，否则 addShowRewardUI1 的第三个参数为空，可能出错（材料未提供它的空值处理）

写绝对值，包含净额：ivch[礼包id] = 原数量 - 1，ivch[奖励id] = 原数量 + 获得数量；如果奖励 id 和礼包 id 相同，就合成一项写净值

守恒断言
对每个奖励 id：rewardArray[id] === ivch[id] - before[id]；对礼包 id：ivch[id] === before[id] - 1 + rewardArray[id]（没有这一项时按 0 算）

前提一：先查 REWARD_ITEM 的监听者（64774 处触发）。 如果有监听者会对 PackageModel 做加法，那它和绝对值 ivch 叠在一起，结果取决于两者的处理顺序：ivch 先处理、REWARD_ITEM 后处理，物品就会加两遍（见反例 5）。只有确认 REWARD_ITEM 只用于展示或统计，上面的形态才成立。
前提二：礼包如果是随机的（表里有概率或权重列），抽取必须在服务端完成，而且要在同一次 persist() 之前定下来。catch 回滚之后，重试必须允许重新抽取；这一点不需要断言为”结果相同”。
前提三：已有的形状契约。 useItem 成功时形状表要求的其他字段（比如 getKnackIds、gemId）如果是开关字段，就保持不发。

3. Q2 答
不要直接在 useItem 里做 +1 级。 先闭合请求，而且闭合的成本很低。
理由： 64401-64417 的证据显示，Effect 11 在已学会（列表带当前等级）和未学会（lv:0）两种情况下，都会加载 ConsultUI 并调用 studyData。如果 64417 后面是 return !0（材料只给到 64417，这一点需要核实），那么 Effect 11 从来不会经过 65333 发出 USE_ITEM。请求是 ConsultUI 发的，它可能是 User.upgradeSkill，可能是带了额外字段的 useItem，也可能是别的动作。在 useItem 里加的逻辑，可能永远不会被执行到。
闭合方法，按成本从低到高：
在服务端直接观察，最有决定性。 我们就是网络层，ConsultUI 发出的任何请求都会进到 dispatch。在 dispatch 的入口记录”动作名加请求体”，然后在端上用一本 Effect 11 的书走一遍 ConsultUI：
只要看到请求到达，就闭合了；
在确认按钮之前取消，不会消耗任何东西；
如果非要点确认才能看到请求，那就要消耗一本书，需要用户同意。
运行时读源码，不消耗任何东西。 prefab 加载之后执行 cc.js.getClassByName("ConsultUI").prototype.studyData.toString()，以及它的确认回调（材料未提供方法名，可以枚举 prototype 上的函数）。Cocos Creator 2.x 里，skillsUI 很可能是单独的 asset bundle 或分包，它的脚本在 assets/<bundle>/index.js（或 .jsc）里，所以主包的 index.js 里 grep 不到【推断】。
在 APK 里 grep。 在 assets/ 下所有 index.js 和 project.js 里搜 ConsultUI。如果是 .jsc，需要先解密，密钥材料未提供，所以这一步成本最高。
闭合之后再分情况：
如果发的是 User.upgradeSkill，现有的 upgradeSkill handler 已经存在，要核对它是否扣书、是否读 level 表做封顶。这时 useItem 里的 ITEMSCH”已学会”分支，应当登记为 role:"unreachable"，而不是改成升级；
如果发的是 useItem，再按”+1 级、扣 1 件、note.skch“在 useItem 里实现。
level 表：要 dump。 原因是 64401 用 getItem(T.lv, "level") 计算升级进度 pgr，这张表的键是等级。封顶的判据应当是 max(Object.keys(level))，再叠加 skill 表或品质系数中可能存在的单技能上限。具体字段名材料未提供，dump 之后先抄出列名再定。dump 沿用 item 表的流程（写设备文件，pull，删除，留痕），只要 level 和 skill 两张表。
4. Q3 答
① Effect 15 的语义：减少死亡计数（“伤痕”）【推断】
case 15 的拦截条件是 numDeaths == 0，提示文本是”没有伤痕”。这说明伤痕就是 numDeaths 的外在表现，Effect 15 的作用是让它减少，Data1 = 0 可能表示”清零”，也可能表示”减 Data2”（材料未提供 Data2..5 的值）。要定性，读以下两处：
全表里 Effect 15 的所有物品，看它们的名字和 Data1..5 的分布：如果美肤露这类物品 Data1 > 0、月饼 Data1 = 0，那 Data1 就是数量，0 有特殊含义；
grep 读 numDeaths 的代码：哪里会显示伤痕，哪里会扣属性，以及回包里哪个字段会写回 numDeaths。这就是应答契约。
② 名字不符：Effect 列被复用，这个解释成立
Effect 是行为编号，不是品类编号。节日道具套用已有的行为，并且共用同一条通用提示文本（4374 写死了”美肤露”），是很常见的配置复用方式【推断】。可以用 3020 自己的描述文本来验证：如果它的 tips 里写着”消除伤痕”之类的意思，复用就坐实了（材料未提供 tips 列名，可以去看 Property1..5 里是不是有文本 id）。
③ 3020 先不要做效果，先判断”在当前模型下可不可达”
关键问题：我们的存档和 LoadGame 有没有建模 numDeaths？ 依据约束（不能让客户端上报服务端才有的数据），死亡次数只能由服务端维护。
实测结果
处置

LoadGame 总是给出 numDeaths = 0（或者干脆不发），也没有任何 handler 会增加它
客户端 case 15 会永远在本地拦截，3020 永远发不出请求，也不会有损失。登记为 role:"unreachable"，证据写”numDeaths 恒为 0 且无增加路径”，加一条断言来锁住这个条件

某个 handler（比如战斗结算）会增加 numDeaths
那 3020 是可达的，就按 ① 的语义实现，并且要在同一处把新的 numDeaths 推送回去

只需要 grep 一次服务端代码里的 numDeaths，就能知道是哪种情况。
5. 对”下一批顺序”的意见
要换。 我的顺序如下：
Effect 11 的闭合观察（第 3 节方法 1 或 2）：这是当前就确定错误的行为，而闭合成本最低，只需要一次观察，不需要扫 71 个调用点。它还会告诉你，useItem 里的 ITEMSCH 分支到底会不会被执行到。
3020 的可达性裁决（第 4 节 ③）：grep 一次 numDeaths 就够。如果结论是 unreachable，账本里现存的两件物品就都处理完了。
87 个动作的 catchCode 加 handled 抽取扩展：catch 只在出现异常时才会触发，频率低，但它影响所有动作，放在两项便宜的事情之后。
Effect 13：先按第 2 节的 F1–F3 定表，再查 REWARD_ITEM 的监听者。
R5：但不要把它整块推到最后。每改动一个 useItem 家族，就要同时补上这个家族在 R5 中的”拒绝与业务哈希不变”夹具：Effect 28 的 T2 已经是半个夹具，补上 bizHash 和 pushCount 就是完整的。
6. 反例
活动永续或永不开始：活动 67 的结束时间在每次 LoadGame 时都被平移到 now + 7 天，所以玩家永远看到”还剩 7 天”。如果这个活动有按期结算的奖励（比如活动结束时发排行奖励，或者按期重置进度），永远不会结算。另一种情况：抓包时尚未开始的活动，start 被平移到 now + Δ，永远差 Δ 才开始。还有一点：用 10 位秒级时间戳表示的窗口不在 >1.6e12 的范围里，不会被平移。
称号重启即丢：玩家使用 7027 获得称号 2045，当场弹出了称号奖励；重启后 LoadGame 没有把 s.titles 投射到 AchieveModel 的数据源，客户端认为没有这个称号，穿戴界面里也看不到。如果背包里还有第二件 7027，客户端就不会弹 3187 号提示，而是再发一次；服务端再扣一件、再写一次相同的称号，又白白消耗了一件。另外，“已经拥有还继续用”在原版里是”拒绝、不扣”还是”照扣”，材料未提供。
lv=0 的 skch 推送破坏等价性：某个 handler（比如废功、重置，或者 catch 之后的 repushLive 推送了 lv=0 的项）经由 119832 写进 dic[X].lv = 0。getSkillItem(X) 不为空，于是 Effect 5 的书在本地被拦截，提示”已学会”；Effect 11 的书则拿 ConditionUp 和 lv 0 去走升级。这个技能就再也学不会了。需要断言：服务端产出的任何 skch 值的第 0 个元素都大于 0，删除技能只能通过 abolish 通道。
在 useItem 里实现的升级成了死代码：按 Q2 的原方案，在 useItem 里实现了 +1 级，但端上的 ConsultUI 实际发的是 User.upgradeSkill，带着 skillArr。升级落到了现有的 upgradeSkill handler 上，那里不扣书，或者不封顶，于是书被无限使用。
REWARD_ITEM 让物品加两遍：一个礼包里有 10 个铜钱袋。note.ivch 先把铜钱袋写成”原数量 + 10”，随后 REWARD_ITEM 的监听者又执行一次 PackageModel.add(铜钱袋, 10)，客户端就显示”原数量 + 20”，与服务端不一致。直到下一次 ivch 或者重启之前，玩家都可以按 +20 的数量去卖。
礼包里的装备没有 equipObj：礼包产出一件装备，rewardArray 里有它，但 equipObj 是空对象。addShowRewardUI1 去读装备属性时可能出错（材料未提供它的空值处理），回调中断，遮罩没有清掉，物品却已经扣了。
把 3020 判为 unreachable 后被未来的改动打破：日后实现了战斗死亡计数，numDeaths 开始增加，3020 变得可达，但它的登记仍然是 unreachable，于是走”照扣、无效果”的路径。所以 unreachable 的登记必须附带一条可执行的 exitCheck：“服务端代码里没有任何写 numDeaths 的位点”，一旦出现就判红（G4）。
7. 假设
A1：64417 之后，case 11 是 return !0，即在本地结束，不经过 65333 发 USE_ITEM。如果不是这样（ConsultUI 只是展示，之后仍会 break 并发出 useItem），第 3 节”不要在 useItem 里做”就退化为”可以在 useItem 里做，但仍要先确认 ConsultUI 是否另发了请求”，反例 4 也作废。
A2：REWARD_ITEM 的监听者里有对背包做加法的。如果它只用于展示或统计，第 2 节 ② 的前提一自动满足，反例 5 作废。
A3：服务端没有 numDeaths 的增加路径。如果有，第 4 节 ③ 和第 5 节第 2 项的”可以快速结案”作废，3020 要按 ① 实现。
A4：礼包表在客户端配置里有对应的数据。如果礼包内容只存在于服务端（客户端 442 张表里都没有），第 2 节 ① 的 F1–F3 会筛出空集。这时只能靠抓包，没有抓包就登记为”待判”，不要凭空构造礼包内容。
A5：活动的开放状态完全由结束时间与 serverTime 比较决定，并且不存在按期结算的逻辑。如果有按期结算，第 1 节第 1 条的”可以接受”要降级为”必须和用户再确认一次”。
A6：LoadGame 现在没有投射 s.titles。如果已经投射了，第 1 节第 2 条和反例 2 的前半部分作废。
