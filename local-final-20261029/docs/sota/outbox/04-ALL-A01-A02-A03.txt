===== 第四部分：材料 A02（权威状态机分层）=====

===== 第五部分：材料 A03（存档版本演进）=====

【场景】玩家进度全部存在一个 JSON 文件里（当前约 700 字节，预期 20–100 KB）。没有数据库，只有文件读写：
读 = 读整个文件反序列化；写 = 序列化整个对象覆盖原文件。进程随时可能被杀、也可能断电。

【已经发生过的 4 次结构调整（一周内）】
v1  { roleId, questAccepted: [qid], questDone: [qid], abilities: { aid: levelNumber }, inventory: { itemId: count }, xp }
v2  + equipInstances: { uid: [kind, itemId, attrs, gemIds, skinId] }, equipSlots: { slotIndex: uid }
v3  abilities: { aid: [level, progressRaw, tier] }
v4  + rewardedQuestIds: [qid]

目前做法很原始：读档后逐字段补默认值（if (!save.abilities) save.abilities = {}），没有版本号、没有迁移函数。
两次事故：① 改动后旧档读出来少了字段，程序按"空"处理并把空值写回 → 玩家背包被清空；
② 同名字段在"全量快照"和"增量同步"两个接口里格式不同（数组 vs 对象），改错一处静默失效两周。

【补充事实（上一轮回答里缺失、由我补上的）】
- 当前存档里 abilities 的值是**混形态**：既有 [level, progress, tier] 数组，也有裸 number。所以"值全是数组 ⇒ v3"这类形态指纹不成立。
- v2→v3 的初值取 progress = 0、tier = 1。
- v3→v4 的 rewardedQuestIds **空着、不回填 questDone**（回填等于宣称"老档都发过"，会永久丢奖励；另有幂等补偿手段）。
- 现网只发布过 v1–v4 四种形态。

【约束】
1. 只有一个逻辑存档，不能引入数据库/多进程锁（允许有辅助文件）。
2. 写文件必须在任何时候都是"要么旧内容、要么新内容"。
3. 迁移函数必须幂等，且能跳版本直升最新。
4. 有些集合是增量语义、有些是全量语义，混在同一个文件里。
5. 玩家可能从备份恢复到旧版本再升级。

【我要你回答（A03）】
1. 版本化方案：saveVersion + 顺序迁移 vs 读时补默认值 vs 混用？给迁移函数签名与最小骨架（注意：环境是 ES5）。
2. 原子写：在没有 fsync、但有 renameFile 的前提下怎么做？（给可移植做法 + 失败场景；如果必须彻底不依赖 rename，给替代方案）
3. CI 断言 3–5 条，每条写成"给定某版本存档输入，断言输出满足 X"。

【A03 输出格式】
