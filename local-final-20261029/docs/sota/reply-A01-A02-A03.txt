A01 契约测试体系
A01-0 矛盾与信息不足
303 个动作平均各读 2–3 个字段，合计约 606–909 个字段位，但形状表有 1105 个字段位。两种可能：表里含有客户端不读的字段，或者”平均 2–3 个”这个数不准。材料未提供是哪一种。
1103 条断言要覆盖”动作存在、成功标志、字段齐全、类型正确”四类，可 1105 个字段位光是”齐全+类型”就至少需要 1105 条。所以要么有字段没断言，要么一条断言覆盖多个字段。断言和字段的对应关系材料未提供。
509 个 ACK 动作只是”客户端不读应答”，有多少会改状态材料未提供。D 说明动作是有副作用的。
“类型正确”用什么判定（typeof、Array.isArray 还是元素类型），材料未提供。B 能不能被拦住取决于这一点。
拦截层代码能不能脱离游戏在 Node 里跑，材料未提供。这决定测试放在哪一层。
A01-1 结论
最大的结构性漏洞：形状表只验证应答的语法，不验证值的语义，也不验证状态转换。A–E 五起事故全是”形状对、语义错”：空数组是合法数组，下标 0 和 1 都是 number，全集和增量是同一个类型。
期望和实现出自同一个人的理解。形状表是按你对协议的理解写的，没有以客户端代码的实际读取路径作真值，所以理解错的地方，测试会和实现一起错，C 就是这样【推断：材料未说形状表来源】。
509 个 ACK 动作没有任何关于”写了什么进存档”的断言。
进程内自检和生产共享运行态，本身就是污染源。沙箱开关加字节比对只能事后发现问题，不能从结构上禁止。
自检的状态覆盖面取决于启动时那份存档。空背包的玩家身上，“回空”这类错误永远是绿的。
A01-2 三类测试
类别 1：哨兵值位置契约（拦 B、C） - 目的：把”类型对、位置或语义错”变成可失败的断言。 - 断言示例：
var s = fixture({ abilities: { a1: [7, 13, 2] } }); // 三个位置填互不相等的值
var snap = project(s, &#39;fullSnapshot&#39;);
assert(snap.abilities.a1[0] === 7 && snap.abilities.a1[1] === 13); // 进度必须在下标 1
var r = handle(s, { action: &#39;abilityUpgrade&#39;, aid: &#39;a1&#39; });
assert(r.state.abilities.a1[0] === 8 && r.state.abilities.a1[2] === 2); // 只加一级，tier 不动
// 拦 B：同名字段在所有接口里必须走同一个 codec
forEachSharedField(function (f, eps) { assert(allEqual(map(eps, function (e) { return CODEC[e][f]; }))); });
放哪一层：CI（Node，文件 API 打桩）。如果 A01-0 第 5 条不成立，就在模拟器里跑，但只能在克隆的状态上跑。
类别 2：集合语义契约（拦 A、E） - 目的：每个集合字段标注 MODE ∈ {snapshot, delta, replace}，按语义断言内容，而不是按类型。 - 断言示例：
if (MODE[f] === &#39;replace&#39;)  assert(count(get(resp, f)) === count(get(after, f)));
if (MODE[f] === &#39;delta&#39;)    assert(isSubset(keys(get(resp, f)), changedKeys(before, after, f)));
if (MODE[f] === &#39;snapshot&#39;) assert(deepEqual(decode(f, get(resp, f)), get(after, f)));
fixture 必须覆盖空、1 条、≥2 条三档，否则 A 在空档上永远是绿的。 - 放哪一层：CI 跑全矩阵；replace 这一条同时作为运行时守卫放在投射层，失败就拒绝回空，改用状态投射。
类别 3：副作用隔离与幂等契约（拦 D、重复发奖） - 目的：只读动作和自检零写入；同一请求重放不改变资源。 - 断言示例：
var b = hash(JSON.stringify(model)), w = fileStub.writeCount;
selfCheck(clone(model));
assert(hash(JSON.stringify(model)) === b && fileStub.writeCount === w);
var s1 = handle(s0, claimReq).state, s2 = handle(s1, claimReq).state;
assert(deepEqual(resources(s2), resources(s1)));
放哪一层：CI。生产环境里，自检期间把文件 API 换成调用即抛错的代理。
A01-3 20 条断言
写档前，如果旧档背包总量 >0 而新档为 0，且本次动作不在清空白名单里，就拒绝写入。
背包、任务、好友三个整份替换接口返回的条目数，必须等于状态里对应集合的条目数。
未实现动作的降级应答里，任何 replace 或 snapshot 语义的集合都不能是字面量空值，必须取自状态投射。
加载时迁移或校验失败，本次进程的写文件计数必须为 0。
写后回读：读回文件并解析后，必须和内存模型 deepEqual。
全量快照经 decode 后还原出的状态，必须 deepEqual 当前状态。
任一技能等级在一次动作后不能下降，声明了降级的动作除外。
questDone 单调不减，并且 questDone 和 questAccepted 交集为空。
xp 单调不减，声明了消耗 xp 的动作除外。
迁移前后，每个技能的等级（裸 number 或数组下标 0）必须相等。
哨兵 [7,13,2] 经快照投射后，下标 1 必须仍是 13。
增量应答里的进度值，必须等于应用变更后状态里的进度值。
同一个领奖请求连续处理两次，第二次的状态差异必须为空。
qid 已在 rewardedQuestIds 里时再次领奖，资源总量不变。
每次动作的资源变化量，必须等于结算层本次产生的事件里声明的增减之和。
每个发奖事件的内容，必须 deepEqual 配置表里对应 ID 的奖励定义。
迁移不增加资源：背包总量和 equipInstances 数量在迁移前后相等。
同一请求在同一个 now 下处理两次，产出相同的状态，结算没有隐式随机或时间依赖。
自检全程写文件计数为 0。
自检前后，hash(JSON.stringify(model)) 相等。
A01-4 最可能冗余或无效的那一类
【推断】最可能是”字段齐全/类型正确”这一类：当应答骨架和断言出自同一张形状表或同一个模板时，这类断言只有代码崩溃才会失败，等于重言式。“成功标志值”如果是写死的常量，也一样。另外，如果”平均读 2–3 个”属实，1105 − 909 = 196 个以上的字段位保护的是客户端根本不读的字段。验证方法：对投射层做变异，逐个删字段、换类型、交换下标；从来没被任何变异杀死过的断言就是冗余。if (!anyMutantKills(a)) markRedundant(a)
A01-5 边界清单
[] 能通过任何”X 的数组”检查，空集合下元素类型根本没被检查。
typeof [] === &#39;object&#39;、typeof null === &#39;object&#39;：如果用 typeof 判类型，B 和 null 都会漏掉。
客户端读字段时带默认值（resp.x || 0），缺字段不会崩但值是错的。
数字字符串 “5” 和数字 5：客户端做加法时会变成字符串拼接。
路径越界（a.b[3]）返回 undefined，不报错。
整数样式的键会被重排，依赖键顺序的字节比对会误报或漏报。
启动自检所用存档的进度阶段决定覆盖面，新档下大部分集合是空的。
客户端会不会超时重发同一请求，材料未提供；如果会，13、14 两条必须在 CI 里覆盖。
A01-6 反例：测试全绿但线上炸
好友整份替换接口回 []：类型是 array，自检在空好友档上跑，全绿；老玩家的好友列表被清空。这是 A 在第 4 个接口上重演。
应答返回累计值，客户端却当增量去加：两者都是 number，测试全绿；线上每次领取都翻倍，数值凭空增加。
[level, progress, tier] 写成了 [progress, level, tier]：三个都是 number，全绿，线上等级和进度错乱。
降级应答”字段齐全但为空”本来就是为了让形状断言通过而设计的，所以未实现的动作在测试里永远是绿的。
509 个 ACK 动作中，有一个把客户端给的目标等级直接写进存档，造成跳级；没有任何断言检查存档，全绿。
A01-7 假设
H1：客户端 JS bundle 可读，能静态提取每个动作的应答读取路径。不成立时（混淆或 jsc 加密），真值只能靠抓包加人工整理，A01-1 第 2 条的修正方案失效，只剩哨兵测试。
H2：拦截层能在 Node 里运行，文件 API 能打桩。不成立时，三类测试都只能在模拟器内跑，而且必须用克隆状态加只读文件代理。
H3：能拿到多个进度阶段的真实存档作为 fixture。不成立时，类别 2 覆盖不到非空集合。
H4：每个集合字段的 MODE 能从客户端代码确定。不成立时，MODE 是猜出来的，类别 2 的断言本身就可能是错的。
H5：客户端对同名字段在各场景下的处理一致。不成立时，按字段名共享 codec 会误报，要改成按（动作, 字段）分 codec。
A01-8 落地步骤
给 1105 个字段位逐个标注读取来源（客户端代码位置或抓包记录），没有来源的标记出来待删。
给每个集合字段打 MODE 标签，建统一的 codec 表，所有接口都经过 codec 序列化。
把拦截层抽成能在 Node 里跑的模块，CI 跑三类测试加 20 条断言，fixture 覆盖空、单条、多条三档。
进程内自检改为只读：只跑纯函数和克隆状态，自检期间把文件 API 换成抛错代理。
用变异测试筛出从来没失败过的形状断言，删掉或降级。
A02 权威状态机分层
A02-0 矛盾与信息不足
约束 2 写的是”迁移 → 校验 → 写后回读”，但迁移一般发生在加载时。我按”加载时迁移；写入时校验 → 原子写 → 回读”来理解。
商店的价格、限购，挂机的收益率、离线上限，配置表里有没有这些列，材料未提供。全局约束只列了物品、任务、掉落、常量四类表。
战斗领奖请求里带不带击杀数和掉落明细，材料未提供。
时间来源只有设备时钟吗？客户端请求里带不带时间戳？材料未提供。
客户端会不会重发请求、带不带请求序号，材料未提供。
“学技能把等级改成客户端要求的目标等级”很可能就是 A03 里 abilities 混形态的来源【推断】。
A02-1 分层图与职责
HTTP 请求
  │
[L0 拦截/路由]  解码，注入 now，按 ROUTE[action] 选路径 ──(replay 或异常)──► [F 降级：回放+ACK]
  │
[L1 动作适配]   请求 → Command（意图）
  │
[L2 领域决策]   decide(state, cmd, cfg, now) → Event[] | Reject
  │
[L3 结算/应用]  apply(state, events) → state&#39;
  │
[L4 持久化]     校验 → 原子写 → 写后回读
  │
[L5 投射]       project(state&#39;, events, MODE) → 快照 / 增量 / 整份替换
  │
HTTP 应答                        [CFG 配置表：只读，供 L2、L5 使用]
L0：唯一接触 HTTP 和时钟的一层，把 now 作为参数往下传。
L1：把客户端给的值翻译成意图，例如”升一级”，而不是”设为 5 级”；不读写状态。
L2 领域状态：纯函数，依据状态、配置和 now 校验前置条件，产出事件或拒绝。
事件：请求内不可变的事实，例如 RewardGranted{key, items}；只在本次请求里存在，不持久化成日志【推断：单文件下不保存事件流】。
L3 结算：全系统唯一修改状态的地方，负责去重账本、计数器、离线补算和守恒检查。
L4：一个请求对应一次原子写，失败就丢弃 state’。
L5 快照/增量投射：增量由事件投射，快照由状态投射，整份替换由状态的完整集合投射；所有字段都经 codec。
F 未实现动作降级：现有的回放+ACK 层，但 replace 集合取状态投射，不回空。
A02-2 层间调用规则
允许 L3 修改状态；禁止 L1、L2、L5 修改（测试里传 deepFreeze 过的状态）。
禁止 L2 调用文件 API 或 Date.now，now 只能来自 L0 注入。
禁止 L5 读取请求体，只能读 state’ 和事件，防止把客户端的值原样回显。
L4 成功后才能调用 L5 生成应答；写失败时回滚到请求前的克隆状态，走 F 的应答【推断：客户端对失败标志怎么处理，材料未提供】。
F 只能通过 L0 的路由进入，禁止权威路径中途跳进 F 再回来。
自检和测试只能调用 L1–L3 和 L5，禁止调用 L4。
A02-3 防歧义规则
客户端发来的值只当意图或校验依据，结果以服务端状态计算。反例：服务端是 3 级，客户端发”目标 5 级”，直接记账就跳过了 4 级的消耗。
结算按语义键去重（领奖用 qid，限购用 shopId+日期），不按请求去重。反例：连点两次领奖，两次请求各不相同，按请求去重会发两份。
计数类字段回绝对值，除非客户端代码证明这个字段是增量语义。反例：回”+10 金币”，客户端本地已经预演加过 10，结果变成加 20。
整份替换集合只有在状态里确实为空时才回空，“不知道”就从状态投射。反例：未实现动作回空背包，客户端清空本地缓存。
时间只认 L0 注入的 now，存 lastSettledAt；now 早于 lastSettledAt 时按 0 处理。反例：模拟器时钟回拨后再拨回，离线收益被补算两次。
一个请求等于一次原子状态转换，扣费和发货在同一个 state’ 里完成。反例：先写扣金币、再写加物品，进程在两次写之间被杀，金币没了、物品没到。
实例 ID 只由一方分配；客户端分配时，服务端检查唯一性。反例：两件装备用了同一个 uid，后一件覆盖前一件。
客户端算出的战斗结果，按配置表掉落上限截断。反例：客户端上报 1000 次击杀，任务直接完成，奖励全额发放。
A02-4 状态机边界判别标准
不能从其他已存值、配置和 now 重算出来的，进状态：questDone、背包计数、击杀计数、lastSettledAt。
能从状态加配置纯函数算出来的，只做派生、不存：战力、“任务可完成”标志、当前售价。存下来，配置一改就漂移。
防重复的凭据进状态：rewardedQuestIds、限购计数加日期戳。
随时间累积的收益，存锚点（lastSettledAt 和计算输入），不存”待领收益”；只有收益率中途变化时，才在变化点结算并落盘。
配置改动不应追溯的（已发奖励）存结果；应该追溯的（价格、属性公式）做派生。
A02-5 降级路径
L0 维护一张路由表 ROUTE[action] ∈ {auth, replay}，默认值是 replay，另有一个全局开关能一键把所有动作切回 replay。权威路径抛错或校验失败时，丢弃克隆出来的 state’，用请求前的原状态走 F 处理同一请求。两条路径读写同一份存档 schema，F 必须原样保留自己不认识的字段（计数器、lastSettledAt、去重账本）。F 运行期间，权威层独有的字段会过期，所以从 replay 切回 auth 时，离线补算要按配置表上限截断。F 自身保留写前语义守卫：清空或回退类的写入直接拒绝。
A02-6 5 条断言
断言：deepEqual(applyDelta(snap_n, delta_n1), snap_n1)。触发场景：增量投射漏掉了某个被事件改动的字段（状态漂移）。
断言：deepEqual(resources(settle(settle(s, claim(q)), claim(q))), resources(settle(s, claim(q))))。触发场景：客户端连点或重发领奖（重复结算）。
断言：对不在 DECREASE_ALLOWED 里的动作，level/xp/questDone/killCount 处理后 ≥ 处理前。触发场景：客户端带着过期的目标等级发请求（进度回退）。
断言：sum(diff(before, after)) === sum(eventAmounts(events))，并且每个 RewardGranted.key 处理前都不在账本里。触发场景：投射层或降级层绕过 L3 直接加资源。
断言：deepEqual(settleTime(settleTime(s, t), t), settleTime(s, t))，并且 settleTime(settleTime(s, t2), t1) === settleTime(s, t2)（t1 < t2）。触发场景：两个请求拿到同一个 now，或者时钟回拨。
A02-7 边界清单
设备时钟向前大跳，离线补算产出巨额收益；截断上限材料未提供。
每日刷新按哪个时区跨日，材料未提供。
请求涉及的任务还没接取或已经完成。
存档引用的配置 ID 已经从配置表里删掉了。
奖励超出背包或堆叠上限；上限字段材料未提供。
会话中途从 replay 切到 auth，或反过来切换。
509 个 ACK 动作被服务端拒绝或修正后，客户端看不到，要到下次全量快照才同步。
应答生成失败但存档已经写入，客户端重发时被去重挡下，状态和客户端视图不一致，要到下次登录才恢复。
A02-8 反例：不可逆的状态损坏
A 链条：降级应答回空背包 → 客户端清空本地缓存 → 客户端之后基于空视图发出的动作（比如整理背包时带上全量列表）被回放层照单记账 → 存档里的背包真的被清空。回放层信任客户端的值，所以无法恢复。
replay 期间写入目标值：客户端要求 10 级，回放层直接写成 10 级，但消耗没扣。切回 auth 后，已经没法区分哪些等级是合法获得的。
去重键和发奖分两次写：键已经写入、奖励没写进去，玩家这份奖励永久领不到。只要违反 A02-3 第 6 条就会发生。
时钟前跳：离线补算的巨额收益落盘后，和合法收益无法区分。
配置表 ID 重编号：存档里存的 ID 指向了另一件物品，原物品丢失。
老档领奖：rewardedQuestIds 为空的老档里，已完成的任务如果允许再领，就会重复发奖，事后无法识别（见跨批影响）。
A02-9 假设
H1：客户端会用应答覆盖本地预演的结果。对 303 个读应答的动作，这一点必须成立；对 509 个 ACK 动作，它天然不成立，服务端的修正要到下次全量快照才可见。如果连 303 个也不覆盖，权威状态机只在重新登录时生效。
H2：请求里有足够信息推出意图。不成立时，L1 只能退回到记录目标值，A02-3 第 1 条失效。
H3：配置表里有价格、限购、收益率、掉落上限。不成立时，商店和挂机只能保持 replay，权威化范围缩小。
H4：单线程，一个请求处理完才开始下一个。不成立时（异步回调交错），state’ 的克隆和提交需要加串行队列。
H5：设备时钟是唯一的时间源。不成立时（请求里带客户端时间），要定义两者冲突时以谁为准。
A02-10 落地步骤
先完成 A03 的持久化链和 codec 表，让 L4 和 L5 有统一的基础。
把现有回放层改造成 F：replace 集合取状态投射、保留未知字段、加写前语义守卫，并补上 A01 的 20 条断言作为基线。

A03 存档版本演进（修订）
A03-0 矛盾与信息不足
“现网只发布过 v1–v4 四种形态”和”abilities 混形态”矛盾：数组和裸 number 并存，不属于 v1–v4 里任何一种，实际上是第五种物理形态。结论：不能用形态指纹判断版本，只能逐值归一；而且代码里很可能还有一个写裸 number 的写入方【推断：就是 A02 回放层”把等级改成目标等级”】，迁移一次之后还会再被写坏。
“另有幂等补偿手段”具体是什么，材料未提供。它和 A02 约束 3 冲突，见跨批影响。
renameFile 在目标文件已存在时怎么表现、底层是不是 POSIX rename(2)，材料未提供【推断：Cocos 的 Android 实现调用 rename(2)，需要真机验证】。
writeStringToFile 的返回值语义，材料未提供【推断：返回 bool】。
约束 2 和平台能力冲突：没有 fsync 时，断电或模拟器宿主崩溃无法保证”要么旧、要么新”，最多只能做到”要么新、要么某一份较旧的有效版本”。
A03-1 结论
推荐 saveVersion 加顺序迁移，“补默认值”只出现在迁移步骤内部，并且只补该步新增的字段。
所有现有步骤都写成可重入的，所以加载时不论有没有版本号都从 v1 跑起，这样就绕开了混形态导致指纹失效的问题；saveVersion 只用来挡住比当前程序更新的存档（> LATEST）。
v2→v3 逐值转换：裸 number n 转成 [n, 0, 1]，数组原样保留；v3→v4 的 rewardedQuestIds 只在缺失时补成 []，绝不回填。
校验同时挂在加载后和每次写入前，只要发现裸 number 就拒写，用来拦住还没修掉的写入方。
纯”读时补默认值”区分不了”缺失”和”本来就空”，也处理不了值形态的变化，见 A03-7。
A03-2 迁移签名与骨架代码（ES5）
var LATEST = 4;
function has(o, k) { return o != null && Object.prototype.hasOwnProperty.call(o, k); }
function clone(o) { return JSON.parse(JSON.stringify(o)); }

// 规则：每一步都可重入，已迁移的数据再跑一遍结果不变
var STEPS = [null,
  function (s) { // 1 -> 2
    if (!has(s, &#39;equipInstances&#39;)) s.equipInstances = {};
    if (!has(s, &#39;equipSlots&#39;)) s.equipSlots = {};
  },
  function (s) { // 2 -> 3：逐值归一，兼容混形态
    var k, ab = s.abilities;
    for (k in ab) if (has(ab, k) && typeof ab[k] === &#39;number&#39;) ab[k] = [ab[k], 0, 1];
  },
  function (s) { // 3 -> 4：只在缺失时补 []，不回填 questDone
    if (!has(s, &#39;rewardedQuestIds&#39;)) s.rewardedQuestIds = [];
  }
];

// migrate(raw: Object) -> Object；抛错时调用方禁止写回
function migrate(raw) {
  var v = +raw.saveVersion; // 字符串 "5" 也能挡住；缺失时得到 NaN
  if (v > LATEST) throw new Error(&#39;NEWER_SAVE:&#39; + v);
  var s = clone(raw), i;
  for (i = 1; i < LATEST; i++) STEPS[i](s); // 全部可重入，所以总是从 1 跑起
  s.saveVersion = LATEST;
  validateLatest(s);
  return s;
}

function validateLatest(s) { // 加载后和每次写入前都调用
  var req = [&#39;roleId&#39;, &#39;questAccepted&#39;, &#39;questDone&#39;, &#39;abilities&#39;, &#39;inventory&#39;, &#39;xp&#39;], i, k, a;
  for (i = 0; i < req.length; i++) if (!has(s, req[i])) throw new Error(&#39;MISSING:&#39; + req[i]);
  for (k in s.abilities) if (has(s.abilities, k)) {
    a = s.abilities[k];
    if (!Array.isArray(a) || a.length !== 3 || typeof a[0] !== &#39;number&#39;) throw new Error(&#39;ABILITY:&#39; + k);
  }
  if (!Array.isArray(s.rewardedQuestIds)) throw new Error(&#39;REWARDED&#39;);
}
A03-3 原子写做法
文件格式：第一行是头部 JSON {"v":4,"gen":N,"len":L,"crc":C}，换行后是 payload 原文。crc 用 ES5 自己实现 CRC32 或 FNV-1a，crc 和 len 都按读到的原始 payload 字符串计算，不能先 parse 再 stringify，因为 itemId、slotIndex 这类整数样式的键在 parse 之后会被重排。
rename 方案的步骤：先 writeStringToFile(content, tmp)，返回 false 就放弃；然后检查 getStringFromFile(tmp) === content，并且 getFileSize(tmp) === unescape(encodeURIComponent(content)).length（UTF-8 字节数）；两项都通过才执行 renameFile(tmp, main)，最后对 main 再做一次同样的回读。
如果 renameFile 在目标已存在时会失败，就改成 renameFile(main, prev) 再 renameFile(tmp, main)。启动时如果 main 不存在，按 tmp、prev 的顺序取第一个 crc 通过的文件。
失败场景①进程被杀：在任何一步被杀，main 都是旧内容或新内容之一。前提是 renameFile 映射到 rename(2)，并且进程死后内核仍会把页缓存落盘。
失败场景②断电或宿主崩溃：没有 fsync 时，rename 的元数据可能先于数据落盘，留下 0 字节或残缺的 main。这时回读只读到页缓存，检测不到问题，只能等下次启动时靠 crc 发现、靠备份恢复。
失败场景③磁盘满：写 tmp 失败或回读不一致时不执行 rename，旧 main 保持原样。
不依赖 rename 的替代方案：用两个固定的槽文件 save.a 和 save.b，头部都带 gen；每次写入覆盖 gen 较小或校验失败的那个槽，写完回读；加载时取 crc 通过且 gen 最大的槽。
A/B 方案的关键在于写入过程中从不碰最新的有效副本，所以断电最坏只丢最后一次保存，而不是丢整个存档。在没有 fsync 的前提下，它比 rename 方案更稳，代价是占两份存储空间。
选择条件：如果只需要防进程被杀，rename 方案就够了；材料写了会断电，所以主路径用 A/B。

A03-6 边界清单
整数样式的键在 parse/stringify 之后会被重排，crc 必须按原始字符串计算。
getFileSize 返回字节数，JS 的字符串长度是 UTF-16 单元数，含非 ASCII 字符时两者不相等。
不检查 writeStringToFile 的返回值，就可能把一个空 tmp 改名成主档。
混形态的写入方如果还在，迁移之后又会写出裸 number；靠写前的 validateLatest 拦住。
saveVersion 被写成了字符串 “4”：现在因为步骤可重入所以无害，将来一旦出现不可重入的步骤就会出错。
备份如果按设备时间命名，时钟回拨后会选错”最新”的那份；所以用存在头部里的 gen。
合法的空 abilities: {} 不能被当成缺失。
从备份恢复出一份更新的存档，却在旧版程序上运行：被 NEWER_SAVE 挡住，并且不会写回。
A03-7 反例：什么场景会写坏玩家数据
现有做法加混形态：if (!save.abilities) 不检查值的形态。读代码遇到裸 number 时，ab[k][0] 返回 undefined，被当成 0 级，写回后技能清零；另一处代码对数组做 ab[k] + 1，得到字符串 “5,7,21”。
现有做法加截断文件：断电后得到 0 字节文件，JSON.parse 抛错；如果 catch 分支是”新建档、补默认值、保存”，整个进度就被覆盖了。
现有做法加整份替换接口：读档时把缺失的 inventory 补成 {}，投射给背包整份替换接口，客户端随之清空本地背包；之后客户端基于空视图发出的动作被回放层记账，存档也跟着被清空。
我的方案的反例 1：“总是从 v1 跑起”依赖每一步都可重入。将来如果出现不可重入的步骤（比如把 progress 换算成新单位、乘以 10），无版本号或版本号写坏了的存档就会被重复换算。那一步必须按 saveVersion 门控。
我的方案的反例 2：如果写入方的 bug 写出的数据”校验合法但内容错误”，crc、validate 和回读全都能通过，几次保存之后两个槽和轮转备份全被污染。
A03-8 假设
H1：序列化时总会写出 v1 就有的全部字段（包括 xp=0、空集合）。不成立时，MISSING 校验会误杀合法存档，要改成白名单字段缺失时按空处理。
H2：writeStringToFile 的返回值和 getStringFromFile 的回读可信（至少在页缓存层面）。不成立时，回读校验失效，只剩下次启动时的 crc。
H3：rename 方案需要 renameFile 等价于 rename(2)。不成立时，只能用 A/B 方案。
H4：现有的三个迁移步骤可重入。将来新增步骤不可重入时，“从 1 跑起”对那一步失效。
H5：同一时刻只有一个写入方。不成立时（比如 Android 进程重建期间旧实例还在写），gen 可能重复，A/B 槽的选择可能出错。
H6：补偿手段是幂等的，并且有独立的证据来源。不成立时，见跨批影响第 1 条冲突。

跨批影响
1. 必须一起改的决定
降级应答回空 ↔ 事故 A/E ↔ A01-3 第 2、3 条：A02 的 F 层改成”replace 集合取状态投射”，和对应的断言在同一次提交里落地。只改其中一边，要么断言红着没法合，要么改动没有保护。
A02 分层 ↔ A01 断言挂在哪一层：单调和守恒类断言挂在 L3 的 apply 边界；形状和集合语义类挂在 L5；自检只调用 L1–L3 和 L5，不调用 L4。这样事故 D 的沙箱开关从结构上就不需要了。
一个字段一个 codec：A03 的 abilities 元组 [level, progress, tier]、A02 的 L5 快照和增量投射、A01 的事故 B/C 和哨兵测试，三处共用同一个 codec 模块。迁移校验、快照、增量各写各的，就会重演 B。
混形态的写入方：A03 校验里拒绝裸 number，要求 A02 回放层”学技能写目标等级”必须同时改成写 [level, progress, tier]【推断：写入方就是它】，否则写前校验会让这个动作的每次保存都被拒。
持久化链：A03 的 A/B 双槽、回读和守卫就是 A02 的 L4，A01 的存档安全回归要改成对 L4 断言。
新增状态字段：A02 的计数器、lastSettledAt、限购账本都要走 A03 的 v5 迁移和 fixture；F 层必须保留自己不认识的字段，否则一降级就会把它们删掉。
2. 建议执行顺序
A03 → A01 第一阶段（黑盒：哨兵、集合语义、20 条断言，针对现有回放层）→ A02（逐个动作切换）→ A01 第二阶段（按层挂断言，把自检改成纯函数） - 先做 A03：之后每一步改动都要写存档，没有版本化和备份，任何一个 bug 都可能造成不可逆的丢档。 - A01 第一阶段放在 A02 前面：20 条断言是每个动作切到 auth 时的验收门槛。 - 如果先做 A02 再做 A03：状态机的新字段只能靠”读时补默认值”引入，事故 ① 会重演，而且会多出没有版本号的形态，迁移分支随之增多。 - 如果先做 A02 再做 A01：要改写 303 个动作，却没有任何语义回归保护，进度回退和重复发奖只能靠用户反馈发现，C 已经证明过这一点。 - 如果 A01 全部放到最前面：其中依赖 L2/L3 纯函数的那部分（自检隔离）没有可挂载的层，只能先用沙箱开关凑合，做完 A02 后再返工。
3. 我无法调和的冲突
rewardedQuestIds 不回填 vs 不能重复发奖（A02 约束 3）：迁移时丢掉了”老档已完成的任务是否发过奖”这个信息。如果补偿手段靠客户端再次领取来触发，已经领过奖的老玩家会被重复发奖，违反 A02-3；如果不允许领，没领过的老玩家就永久丢奖励。除非补偿手段有独立的证据来源（比如能从背包或其他字段推断出”已经发过”），否则两者只能选一个。补偿手段的细节材料未提供。
随时能降级回 replay vs 状态机不变量：replay 期间写入的目标值会绕过单调和守恒检查，切回 auth 后，存档里可能已经存在违反不变量的状态。要么断言接受历史违规（以切换时刻为基线），要么在 F 层也执行完整的不变量检查，而后者会拒绝客户端认为已经成功的动作，造成可见的分叉。我的折中是：F 层只拦清空和回退类写入，不保证数值正确。这个冲突只能缓解，不能消除。
509 个 ACK 动作 vs 权威状态机：客户端不读这些动作的应答，服务端拒绝或修正之后，客户端要到下次全量快照才能看到；客户端又不能改，所以这段分叉窗口无法消除【推断：拦截层没有办法让客户端主动重新拉快照】。
