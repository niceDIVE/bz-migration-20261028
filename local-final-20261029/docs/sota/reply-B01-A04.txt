B01 任务进度状态机
B01-0 矛盾与信息不足
计数目标在哪里定义，材料未提供。 列出的配置字段只有 TaskID、Type、Require、SpRequire、Reward，里面没有”杀哪种怪、杀几只”或”到达哪里”的字段。Require 被称为”前置”，格式却是 “flag,taskID,param”，带了 param。它到底只是前置条件，还是也包含完成条件，材料没说清。B01-2/3/4 默认计数目标可以从 Type 加 Require 的 flag/param 解析出来【推断】。如果解析不出来，事件推断计数就没有目标可以比对。
是否存在打怪结算请求、请求里带哪些参数，材料未提供。 约束 2 原文是”可能有”。B01-2/3 全部依赖它；有没有怪物 id、数量、战斗实例 id、开战请求，会直接决定能不能去重。
现有做法与约束 3 冲突。 “接任务时按 SpRequire 自动补齐物品”就是数值凭空增加。交任务时会不会扣掉 SpRequire 物品，材料未提供；如果不扣，每接一个任务背包就净增一次。
客户端自己算显示状态，但它依据什么算，材料未提供。 如果客户端在本地维护击杀计数（存在哪里也没说），服务端的计数会和客户端的计数分叉。
“同一次打怪不能同时推进两个任务”可能和客户端的显示逻辑相反。 很多客户端会让一次击杀同时计入所有匹配的任务【推断】，材料没有给出客户端的实际行为。
任务进度的”离线补算”指什么，材料未提供。 不清楚挂机是否产生击杀或采集。4842 个任务按 Type 的分布同样材料未提供，所以没法给出每种建模方式能覆盖多少比例。
重复任务、放弃任务是否存在，材料未提供。 包括配置里有没有”可重复”字段、有没有放弃任务的请求。
B01-1 结论
不存在一种能覆盖所有任务的建模，只能按任务类型分桶：采集类用真实背包校验（进度由背包派生，不落盘）；击杀类在存在可去重的战斗结算请求时用事件推断计数；到达、对话类服务端拿不到任何信号，只能在交任务时放行。
推断（“这次击杀算给哪个任务”）放在 L2，做成纯函数产出 TaskProgressed 事件；去重键的登记与检查放在 L3，因为已消费键集合属于状态，而 L3 是唯一写状态的地方。
去重的前提是每次战斗能拿到唯一身份：请求里带战斗实例 id 时直接用它；没带但存在 1:1 的开战请求时，用服务端在开战时分配的单调序号；两者都没有时，“重复提交”和”相同参数的真实第二场”在信息上无法区分，这时宁可不推进进度。
任务进度单独存在 taskProg 字段里，不改动 questAccepted 的类型，吸取 abilities 改类型的教训；计数器挂在”本次接取序号 acc”之下，只有重新接取才会清零。
关闭自动补齐和开启真实计数都必须通过 v5 迁移给已接任务打上 legacy 标记，否则老存档里进行中的任务会突然卡住，被当成误拒。

B01-3 推断逻辑归属与去重键
归属
L2 decide：输入状态、请求、配置；把战斗结算解析成击杀单元，按归属规则映射成 TaskProgressed{taskId, idx, unitKey} 事件。已消费的键直接拒绝，不产出事件。这一步是纯函数，可以单测。
L3 apply：再查一次 unitKey 是否已消费，已消费就断言失败并拒绝整笔，属于纵深防御。同时更新计数，登记已消费键或推进水位线。
为什么不全放 L3：归属规则（算给哪个任务）是业务决策，放进 L3 会让”唯一写状态处”夹带策略，无法单测。为什么不全放 L2：去重集合是状态，只能由 L3 推进。
去重键构造
// battleKey：一次战斗的唯一身份
function battleKey(req, st) {
  if (req.battleId != null) return &#39;B:&#39; + req.battleId;               // 客户端自带实例 id（是否存在：材料未提供）
  var p = st.taskProg.pendingStart;                                    // 开战请求时由服务端分配的序号
  if (p != null && p > st.taskProg.battleWatermark) return &#39;S:&#39; + p;
  return null;                                                         // 无法去重：不推进进度
}
// unitKey：一次战斗里的第 i 个击杀单元，只能归属一个任务
unitKey = battleKey + &#39;:&#39; + monsterId + &#39;:&#39; + i          // i = 0 .. n-1
// 归属规则（同一单元不推进两个任务）：
// 在 acc < 开战序号、目标包含 monsterId、计数未满的任务里，取 acc 最小的那一个
用服务端单调序号时，去重只需要一个水位线：seq <= battleWatermark 就拒绝，存储为 O(1)。
用客户端 battleId 时需要有界集合 seenBattleIds，容量按存档预算定（结算频率材料未提供），并且要接受超出窗口的重放无法识别。
采集类走方式②，进度由背包派生，天然幂等，不需要去重键。
B01-4 存档字段设计
{
  "questAccepted": ["t101", "t205"],
  "questDone": ["t001"],
  "rewardedQuestIds": ["t001"],
  "taskProg": {
    "seq": 1287,
    "pendingStart": 1286,
    "battleWatermark": 1285,
    "seenBattleIds": [],
    "active": {
      "t101": { "acc": 1203, "c": [3, 0], "legacy": false },
      "t205": { "acc": 0,    "c": [],     "legacy": true }
    }
  }
}
seq：服务端单调计数器，接任务和开战都从这里取号。
acc：本次接取的序号，计数器只在同一个 acc 内有效，重新接取时 acc 变化、c 清零。
c：按配置目标顺序排列的计数数组。只有方式③的任务才有 c；方式②的进度不存，按背包计算。
legacy：迁移前就已接取的任务，按旧规则放行。
不变量：keys(active) 等于 set(questAccepted)；active 与 questDone 不相交；c[i] 不超过 target[i]。
离线补算：沿用 A02 的 lastSettledAt。挂机产出击杀时（材料未提供是否产出），把 [上次结算时间, now) 区间转成事件，键为 idle:<from>-<to>；区间由 lastSettledAt 推进，保证不重叠。
v5 迁移（可重入，接在现有 STEPS 后面）
function (s) { // 4 -> 5
  if (!has(s, &#39;taskProg&#39;)) s.taskProg = { seq: 0, pendingStart: null, battleWatermark: 0, seenBattleIds: [], active: {} };
  var a = s.taskProg.active, i, q;
  for (i = 0; i < s.questAccepted.length; i++) {
    q = s.questAccepted[i];
    if (!has(a, q)) a[q] = { acc: 0, c: [], legacy: true };   // 老的进行中任务不清零、不卡住
  }
}
validateLatest 要追加检查上面三条不变量。
B01-5 5 条断言
重复计数。 断言：var s1 = run(s0, settle), s2 = run(s1, settle); assert(eq(s2.taskProg, s1.taskProg) && eq(s2.inventory, s1.inventory))。触发场景：客户端重发同一个战斗结算请求。
跨任务串味。 断言：assert(sumAllC(after) - sumAllC(before) <= killsIn(settle))，并且每个 unitKey 在本次产出的事件里只出现一次：assert(uniq(map(events, &#39;unitKey&#39;)).length === events.length)。触发场景：两个任务都要求同一种怪，一次击杀同时推进两个。
进度回退。 断言：for (q in before.active) if (q in after.active && after.active[q].acc === before.active[q].acc) for (i...) assert(after.active[q].c[i] >= before.active[q].c[i])。触发场景：F 层或调试动作把计数写回 0。
已完成任务被重开。 断言：for (q of before.questDone) assert(contains(after.questDone, q) && !has(after.taskProg.active, q))。可重复任务只有在出现显式 TaskReaccepted 事件时才豁免（可重复字段材料未提供）。触发场景：客户端再次对已完成任务发 acceptTask。
完成门槛与计数上限。 断言：if (has(events, &#39;TaskFinished&#39;, q)) assert(a.legacy || model(q) !== &#39;count&#39; || all(a.c[i] >= target(q, i)))，并且 all(c[i] <= target(q, i))。触发场景：计数未满就交任务，或计数溢出导致后续再接取时提前完成。
B01-6 边界清单
开战之后、结算之前才接的任务，不应吃到这场战斗的击杀；规则是只算 acc 小于开战序号的任务。
客户端重发开战请求会产生两个待结算序号；只保留最新的 pendingStart，旧的作废，否则会残留可以被重放的序号。
配置表调整目标数量后，已存的 c 可能超过新目标；读时按 min 截断，但不要写回截断后的值，以免配置回滚时丢失进度。
Require 里出现未知 flag 时，应该拒绝接取，而不是忽略后放行【推断】。
放弃任务的请求如果存在（材料未提供），必须同时删除 active[q]，否则会残留僵尸计数。
SpRequire 物品交任务时扣不扣，必须和客户端一致；不一致时，一边显示还有物品，一边已经扣掉。
一次结算里击杀数大于所有匹配任务剩余需求之和时，多出的单元直接丢弃，不能挪给其他类型的任务。
legacy 任务交付后，要从 active 里移除，不能继续留着 legacy 标记。
B01-7 反例：进度算错且事后无法修正
既没有战斗实例 id，也没有开战请求。 玩家连续打了两场参数完全相同的战斗，和一次重发在请求层面无法区分。去重会少算一场，不去重会在重发时多算；计数一旦落盘，事后找不到证据纠正。
归属规则和玩家意图或客户端不一致。 击杀被算给了 acc 最小的任务，客户端却显示另一个任务进度 +1。存档只存计数、不存每个单元的归属，事后无法重新分配；要存归属，就得付出存储代价。
保留自动补齐，同时又开启计数。 补齐出来的物品和合法获得的物品在背包里混成同一个数量，无法区分，凭空增加的数值永久留下。
迁移时把老的进行中任务计数置 0 却不打 legacy 标记。 玩家在旧版本里实际打过的进度没有任何记录，无法恢复。
客户端按”一次击杀计入所有任务”来显示。 服务端只计一个，玩家看到任务已完成却交不了；如果为了顺从客户端改成计入全部，又违反了材料的要求。
B01-8 假设
H1：存在战斗结算请求，并且带怪物 id 和数量。不成立时，击杀类只能退回方式①或④，B01-3 失效。
H2：存在战斗实例 id，或者存在 1:1 的开战请求。不成立时，去重退化为”不推进”或”可能重复”，只能二选一。
H3：计数目标能从 Type 加 Require 解析出来。不成立时，方式③没有比对目标。
H4：采集物品有合法来源。不成立时，关闭自动补齐会让采集任务无法完成，方式②失效，只能用①并接受数值问题。
H5：客户端对交任务失败的应答会做合理处理。不成立时，服务端每次拒绝都是一次误拒，见 A04。
H6：单线程、请求串行处理。不成立时，水位线的推进需要串行化。
B01-9 落地步骤
抓一局真实流量（打怪、采集、交任务），确认结算请求和开战请求是否存在、带什么参数；这一步只读，没有风险。
解析 4842 个任务的 (Type, Require flag)，生成分桶表，并统计每个桶的数量。
写 v5 迁移，引入 taskProg 和 legacy 标记，补 fixture 和 B01-5 的 5 条断言。
采集桶：新接取的任务停止自动补齐，改按背包校验；交任务时是否扣物品按客户端行为对齐。
击杀桶：L2 做推断、L3 做去重，按动作挂在 ROUTE 路由后面，默认仍走 replay。
到达、对话桶保持方式①，并在 A04 的守卫白名单里登记所有新增写入点。
A04 写入守卫策略
A04-0 矛盾与信息不足
“49 个赋值点”与分项之和不符。 9+6+5+4+4+3+2+2+2+2+1+1 = 41，差 8 处，这 8 处是什么材料未提供。如果这 8 处在 L3 之外，守卫对它们完全看不见。
豁免动作不在写入方名单里。 背包守卫豁免了”使用物品、卖物品”，但”会写这些字段的动作”名单里没有这两个动作。要么写入方名单不全，要么这条豁免是死规则。
潜能有两份。 baseValueAy 包含潜能，另外还有一个独立的 potential 字段。两者是不是同一个量、以哪个为准，材料未提供；如果是同一个量，就存在漂移风险。
potential 只减不增。 照此运行下去，潜能最终会耗尽、无法再学技能。这是不是有意为之，材料未提供。
存档里的”增量语义变更表”具体是哪些字段，材料未提供。 存档存的是状态，增量通常只是传输格式；如果存档里确实存着变更表，需要单独列出来。
现有守卫只拦”减少”，而事故 C、D 都是”增加”型损坏。 现有规则从结构上就拦不住这两类事故。
穿装备是否会把物品从 inventory 移到 equipInstances，材料未提供。 如果会，背包会在穿装备时缩水，而穿装备不在豁免名单里，就会被误拒。
A04-1 结论
守卫的判据应该从”字段朝哪个方向变”换成”变化必须被本次请求的事件解释”：要求 diff(before, after) 与 L2 事件声明的效果完全相等，多出来的或缺少的都拒绝。这样既能拦缩水（A、E），也能拦凭空增加（C、D）。
白名单不靠手写，而是从”动作 → 事件 → 字段效果”目录推导出来；某个字段允许在哪些动作里缩水，是这张目录的派生结果。
在单机离线、存档就是全部进度的前提下，漏拦是不可逆的，误拒是可以补救的。所以默认拒绝，但误拒必须做到可回放：回滚内存、按回滚后的状态投射应答，把请求写入隔离区，事后重新走一遍完整管线。
调试通道走独立路由，产出显式的 Maintenance 事件，写入前强制备份并留下审计记录；它只放宽该事件声明的字段，不绕过 validateLatest，也不绕过结构不变量。
集合语义按 (接口, 字段路径) 判定，不按字段名判定；判别不出来的一律按”整份替换”处理，因为这是最严格的守卫。
A04-2 白名单推导原则与建议初稿
推导原则
某个字段只有在本次请求的 L2 事件声明了相应效果时，才允许缩水，例如消耗物品、花费货币、卸下装备。判据来源是事件目录，不是直觉。
缩水的量必须等于事件声明的量（守恒），只验证”允许方向”是不够的。
语义上单调的字段（questDone、rewarded、技能等级、突破等级）没有任何正常动作可以缩水，只有 Maintenance 可以，而且写前必须有备份。
实例表里的条目只有在出现”销毁”事件并指名 uid 时才可以删除；在槽位和实例表之间移动不算删除，uid 必须仍然存在于某个地方。
身份类字段（name、faction、roleId）只能由各自的专属动作修改。置空必须有显式事件，例如退出门派。
增加同样需要解释：增量必须等于奖励或授予事件的总和。这一条专门用来拦 C 和 D。

A04-3 误拒 vs 漏拦的取舍与误拒自愈路径
取舍条件：当一次损坏不可逆、而误拒的那次操作能够被保存下来并在事后重放时，默认拒绝的总代价严格更低，所以选择默认拒绝。反过来，如果误拒的操作无法保存（比如结果依赖随机数，而种子没有记录），对那一类动作改用”放行 + 写入前备份”。
误拒自愈路径
守卫拒绝时一个字节都不写，并把内存状态回滚到请求前的克隆。不回滚的话，下一次写入会把这次被拒的变化一起带进去。
应答从回滚后的状态投射出来，客户端会处理失败标志时带上失败标志。ACK 类动作的客户端看不到应答，要到下一次全量快照才会纠正（见跨批影响）。
把 {请求, before 的哈希, diff, 命中的规则} 追加写入辅助文件 save.quarantine.json，条数上限按存储预算定，具体数值材料未提供。
下次启动时（或通过调试通道），把隔离区里的请求用当前状态重新走一遍完整的 L1→L5 管线：这次能通过守卫就应用，仍然不通过就继续保留。永远不直接套用旧的 diff。
按 (规则, 动作) 统计拒绝次数；正常动作一旦出现拒绝，就当作事件目录的缺陷来处理：先修正目录，再执行第 4 步回放。
A04-4 集合语义判别流程
输入：字段路径、客户端的读取代码、服务端的读写代码。输出：MODE[(接口, 字段路径)] ∈ {snapshot, delta, replace, instance}，并附上证据。
找到客户端消费这个应答字段的代码；如果本地集合被整体赋值为应答值（local.x = resp.x），记为 replace 候选。反例：local.x = merge(local.x, resp.x) 形式上也是整体赋值，但实际是 delta，所以必须看右侧表达式。
如果客户端按键遍历应答、逐个写入（for k in resp.x: local.x[k] = resp.x[k]），并且事先没有清空，记为 delta。反例：遍历之前有一句 local.x = {}，那实际上是 replace。
对 delta 继续查删除是怎么表达的（值为 0、null 还是特殊标志）；如果找不到删除路径，标为”只增改不删”。反例：数量为 0 的键仍然保留，界面上出现”0 个”的幽灵物品。
只出现在登录全量快照里、只读一次的字段，记为 snapshot。反例：同名字段在增量接口里也出现，而且格式不同（事故 B），所以必须按 (接口, 字段) 分别判定。
如果键是服务端生成的唯一 id，值是引用配置 id 的元组，记为 instance：身份有意义，删除即销毁。反例：uid 删除后被重用，新装备被当成了旧装备。
对照服务端：存档里这个字段如果是”整体计算后写入”，就是全量状态；投射到 delta 接口时发送全集通常无害，但发往 replace 接口的值必须是全集。反例：把 delta 发给了 replace 接口，这正是事故 A 和 E。
读不到代码时做黑盒实验：在模拟器里回一个”修改一个键、省略一个键”的应答，观察本地状态，被省略的键还在就是 delta，没了就是 replace。反例：客户端只在切换场景时重绘，过早观察会得出错误结论，所以必须在切换场景之后再看。
判定结果连同证据（代码位置或实验编号）写入 MODE 表；判定不出来的按 replace 处理（永不回空、没有事件不许缩水）。反例：把未判定的字段当成 delta 放行，结果它其实是 replace，一次回空就清空了玩家数据。

A04-6 边界清单
建角时没有 before，守卫必须把”before 不存在”当作专门的情形处理，否则第一次写入就会被误拒。
背包”总量不变”会漏掉互换型损失（A 少了 5 个、B 多了 5 个），所以必须逐键与事件对账。
数量如果被存成字符串，求和会变成字符串拼接，守卫的比较会失真。
退出门派时 faction 合法地被置空，必须有专属事件才能通过。
调试通道从备份恢复时，几乎所有字段都会”缩水”，必须走”整份替换”类型的 Maintenance 事件，并在写前备份。
守卫在请求边界上比较，不在每个赋值点比较；只要有任何代码路径在请求中途写盘（不经过 L4），守卫就被绕过。
交任务必须在同一次写入里同时更新 questAccepted、questDone 和 rewarded，分成两次写会被”rewarded ⊆ questDone”误拒。
将来如果新增潜能的获得途径，“潜能只减不增”的规则必须和事件目录同步修改，否则会误拒。
A04-7 反例：静默放行一次不可逆损坏
背包从 100 个变成 1 个。 现有规则只拦”大于 0 变成 0”，部分缩水完全放行，玩家的物品就这样被吃掉。
装备实例被结构 bug 改坏。 比如 attrs、gemIds 被重置为默认值，uid 和条目数都没变，所有基于数量的规则都放行；这是 B 类事故在装备上重演。
渐进流失。 每次写入少一个物品，单次写入都不会触发任何阈值。
增加型损坏。 事故 C 和 D 在现有只看”减少”的规则下必定放行。
守卫只保护磁盘，不保护应答。 内存里的状态已经被写坏，写盘虽然被拒绝了，但整份替换接口的应答仍然从坏掉的内存投射出去，客户端清空了本地缓存；之后客户端基于空视图发来的请求被 F 层照单记账，最终被合法写入磁盘。所以 A04-3 第 1 步的内存回滚是必需的。
F 层的动作无法用事件解释。 如果为了不误拒而给 F 层开粗粒度豁免，就等于对 F 层所有动作关闭了守卫。
A04-8 假设
H1：所有写入都发生在 L3，并且事件目录是完整的。不成立时（比如那 8 处没有说明的赋值点在 L3 之外），守恒守卫看不见这些写入，A04-1 第 1 条失效。
H2：每个正常动作的效果都能用事件表达。不成立时（F 层的回放动作），这些动作只能用粗粒度的结构规则（不为负、不删除、单调字段不降），守恒检查对它们失效。
H3：客户端代码可读。不成立时，A04-4 只能使用第 7 步的黑盒实验，判定的成本和误判率都会上升。
H4：允许使用辅助文件。不成立时，隔离区只能放进主存档里，会和主存档一起损坏。
H5：误拒的操作在重放时是确定性的。不成立时（依赖未记录的随机种子），A04-3 第 4 步的重放结果会和玩家当时看到的不一致。

跨批影响
1. 必须一起改的决定
自动补齐 ↔ 守恒守卫。 B01 的自动补齐是一次没有奖励事件的背包增加。A04 的守恒守卫上线后，要么给它声明一个 TaskItemGrant 事件（等于把凭空增加合法化，违反两份材料共同的约束），要么关闭补齐（采集任务改为真实校验）。这两件事必须同时决定。
taskProg 新字段 ↔ v5 迁移 ↔ 守卫白名单。 白名单要新增 taskProg 这一行（同一 acc 下计数单调，只有重新接取才清零，水位线只进不退），迁移与 validateLatest 的不变量要在同一次提交里落地。
交任务扣 SpRequire ↔ 背包缩水白名单。 交任务允许背包缩水的量，必须恰好等于 SpRequire 解析出来的数量。两边各自解析一遍，就会重演事故 B，所以要共用同一个解析函数。
交任务的原子写入。 questAccepted 移除、questDone 增加、rewarded 增加、删除 taskProg.active 条目，必须在同一个 state’ 里完成，否则 A04-5 的 E 条断言和”accepted 移除必须伴随 done 增加”的规则会误拒。
legacy 任务。 守卫的完成门槛必须放行 legacy 任务，否则迁移后玩家手上的老任务全部交不了。
新增写入方。 战斗结算和采集类请求会成为新的写入方，必须进入事件目录和白名单，否则一上线就被守卫全部拒绝。
2. 建议执行顺序
B01 第 1 步（抓流量）和 A04 第 1 步（对齐写入点），两者都是只读的，可以并行 → A04 第 2–4 步（事件目录、守恒守卫、隔离区）→ B01 第 3 步（v5 迁移）→ B01 第 4–6 步（分桶实现）。
先做守卫：B01 会引入新字段和新写入方，在守卫保护下上线时，计数 bug 会被隔离、可以重放；没有守卫的话，重复计数一旦落盘就无法区分真假。
如果顺序反过来（先做 B01 再做 A04）：重复计数、串味、错误归属会不可逆地写进存档；等守卫上线后，B01 的写入又会因为事件目录不全被大面积误拒，需要返工两次。
先做 A04 的代价：A04 第 2 步必须临时为现有的自动补齐声明事件，并标记为”待移除”，否则第 3 步上线当天，接任务就会被全部拒绝。
3. 无法调和的冲突
自动补齐 vs “不允许数值凭空增加”。 如果离线版本里采集物品没有其他合法来源（材料未提供），那么关闭补齐会让部分任务永远无法完成，保留补齐又违反约束。“任务能一路点下去”和”不凭空增加”只能二选一，除非能找到物品的合法来源。
“一次击杀只推进一个任务” vs 客户端显示。 如果客户端按”计入所有匹配任务”显示进度【推断】，服务端就会拒绝客户端认为已完成的交任务请求，这正是 A04 所说代价很高的误拒。客户端不能改，冲突无法消除，只能先抓流量确认客户端的实际行为。
“重复提交必须幂等” vs 没有战斗唯一身份。 如果结算请求既没有实例 id，也没有 1:1 的开战请求，这两个要求在信息上无法同时满足：要么可能重复计数，要么会漏掉合法的重复战斗。
ACK 动作的误拒对客户端不可见。 509 个 ACK 动作被守卫拒绝后，客户端要到下一次全量快照才会纠正，在此之前玩家会以为操作成功了。A04-3 的自愈只能修复存档，修复不了玩家这段时间看到的界面。
