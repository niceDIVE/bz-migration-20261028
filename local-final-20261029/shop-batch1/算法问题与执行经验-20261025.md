## 一、实测数据（本轮真跑，可复现）

**环境**：Python 3.13.2 / networkx 3.5 / Windows / r3 包 `_incoming/relate-pack-r3-20261024/bz-oracle`

**输入**（当前生产源码三件）：

| 文件 | 大小 |
|---|---|
| `hotfix-patch/core/bz-rpc-server.js` | 230,994 B |
| `hotfix-patch/core/bz-handler-impl.js` | 35,579 B |
| `hotfix-patch/patch/live/flow.js` | 17,862 B |

**命令**：
```
PYTHONHASHSEED=<0|1|2|3> python forge/analysis/extract_rw.py <上面三个文件> > rw.s<seed>.json
```

**结果 1 — 复现性（通过）**：

| seed | 输出字节 | md5 |
|---|---|---|
| 0 | 40,554 | `39B9B57A595A12904015B583A31E833C` |
| 1 | 40,554 | `39B9B57A595A12904015B583A31E833C` |
| 2 | 40,554 | `39B9B57A595A12904015B583A31E833C` |
| 3 | 40,554 | `39B9B57A595A12904015B583A31E833C` |

→ **四档逐字节一致**，v2.1 的「与 PYTHONHASHSEED 无关」成立。

**结果 2 — 覆盖率（分派表层零遗漏，但读写层只有一半）**：

stderr 原文：
```
# 53 个动作抽到存档读写（共扫到 108 个 handler，分派表成员 108）
```

| 指标 | 值 | 说明 |
|---|---|---|
| 扫描到 handler | **108** | 与我们实际实现的 108 个**完全一致** → 分派表切段无遗漏 ✅ |
| 分派表成员 | **108** | 同上 |
| 抽到存档读写 | **53** | 占 **49%** |
| **不写存档的动作** | **55** | 占 **51%** |

**这 55 个就是聚类算法的盲区**：它们不碰 `s.*`，在「共享存档读写字段」这一维度上权重为零，
只能靠名字 token / family 配置归类。而恰恰是这类读动作决定了「界面能不能打开」——
`GetMarketList`（南北奇货货架）、`GetMountsList`（坐骑商店货架）都在其中，
C01 名单没有它们，结果 27 个动作全做完，两个面板还是点不开。
→ 这是 §二.1 那条意见的**直接数据支撑**。

**结果 3 — `relate.py` 无法独立运行（交付缺陷，建议修）**：

```
FileNotFoundError: .../out/registry.json
```

`relate.py` 依赖 `out/registry.json` 与 `out/contracts.json`（L77-L78），但 r3 包只带了
`config/` + `forge/analysis/`，**没有带这两个 ~1.4 MB 的依赖文件**。
上游能跑是因为手上还有完整 bz-oracle 目录；换台机器/换个人拿这个包**必然跑不起来**。
建议：要么把 `out/{registry,contracts}.json` 一起打进包，要么在 README 里写明「需自备」。

## 二、【本轮暴露】算法级问题（建议改良，按影响排序）

### 问题 1：聚类维度缺少「同一 UI 面板」，导致漏掉真正的根因动作 ★影响最大

**现象**：C01〔商店交易〕列了 27 个动作，我们照单全做完，结果「南北奇货」和「坐骑商店」**仍然点不开**。
根因是两个**不在 C01 名单里**的动作：

| 动作 | 客户端消费点 | 不做的后果 |
|---|---|---|
| `GetMarketList` | `index.js:130760-130773` → `scripts2.js:8507-8524` | 货架全空，「南北奇货」点了没反应 |
| `GetMountsList` | `index.js:32137` → `scripts2.js:18485` | 坐骑商店空列表 |

**原因分析**：聚类按「共享存档读写字段 / 名字 token / family 配置」聚合，而这两个动作**不写存档**（纯读配置表下发），既不进 `rw:` 字段集合，名字里也不带 `BUY/SELL/SHOP` 这类交易词，于是被漏掉。

**建议**：增加一条「**面板同一性**」维度 —— 用客户端的
`prefabName`、`MessageCenter.on(常量)` 注册点、`STORE_SHOW_UI.type` / `dispatch(EVENT, …)`，
反查「打开某面板会发出一组什么动作」，把 **GET 货架 / POST 购买** 配成对。
一个面板 = 1 个写动作 + N 个读动作，只做写动作必然出现「能买但看不到货架」。

---

### 问题 2：字段类型误判 —— 分类器对「经事件派发 / 转手一层」的字段是盲区 ★

**实例 A**：`GetMarketList.market`
- 形状表判定：`number`，默认 `0`
- 实际类型：**数组的数组**（`scripts2.js:8508` `for (var l in a)`，`8511-8521` 按位置取 `u[0]`…`u[10]`）
- 后果：兜底发 `0` → `for..in 数字` 零次迭代 → `listData` 空 → 面板「点了没反应」
- 成因：值的传递链是 `index.js:130767 dispatch(STORE_SHOW_UI, {market: o.market})` → 另一文件 `scripts2.js:8507` 消费。**判类型的那一层只看到 dispatch 语句，没看到最终消费方式**

**实例 B**：`getChangeShop.shopObj`
- 形状表判定：开关字段（switch）
- 实际：客户端按 key 遍历的对象
- 工程内已有注释记录（`bz-rpc-server.js` 的 `noteBadSwitches` 说明里）

**建议**：
1. 对 `dispatch(EVENT, {字段})` → `on(EVENT)` 的字段做**跨文件追踪**，判类型以**最终消费点**的取值方式为准（`for..in` / 下标 `[n]` / `.length` / `.toString()`）；
2. 形状表增加一列 `consumedAt`（`文件:行号`），便于人工复核；
3. 对「被 `for..in` 遍历」的字段强制标成 `array|object`，**禁止**用 `0` 兜底。

---

### 问题 3：「有形状条目」≠「可安全兜底」

**现象**：`passCardData` 有形状条目，兜底返回 `eRet:1` 但缺 `passObj` / `etime` →
客户端 `PassCardUI` 每帧抛 `TypeError`（`scripts2.js:35088` 读 `this.data[1]`），
实测 **2 秒内 110 次**，面板卡死。

更极端的反例：`getBigGrowupData` 若返回**空** `growObj`，客户端
`changePage()` 会 `else 1 == t && reqBigGrowUpData()`（`scripts2.js:46175`）**无限重请求**，
14~15ms 一次，把 `lockScreen` 锁死 —— **给空数据比不给 handler 更糟**。

**建议**：形状表增加 `safeDefault` 布尔列，标记「缺字段会不会崩 / 会不会触发重试」。
对这类动作，兜底时**宁可不发 `eRet:1`**（让客户端走「未开启」分支），也不要发半截数据。

---

### 问题 4：配置表目录没纳入证据链 —— 导致误判「数据源不存在」

**现象**：我们一度认为「侠客令的奖励档位表不存在，只能由服务端动态下发」，据此决定不回 `eRet:1`。
后来在 `tools/cfg/dump/`（**444 张配置表**）里找到了：

| 表 | 内容 |
|---|---|
| `pass_level.json` | 4 档价目 `0/288/600/1000` |
| `pass_award.json` | 12 阶 × 4 档奖励 |
| `anniversary_pass_award.json` | **22 阶**双轨（`award1`=侠客令 / `award2`=大侠令） |
| `anniversary_pass_gift.json` / `active_store.json` / `gift_permanent.json` | 礼包，且**同时含人民币价与游戏币价** |

前 4 轮算法只读 handler 源码 + 客户端 bundle，**没读 dump 表**，于是把「客户端不读表」误判为「数据不存在」。

**建议**：把 `tools/cfg/dump/*.json` 纳入证据链。做法：
1. 对每个 handler，用回执字段名与表列名做相似度匹配，给出「这个货架/档位数据可能来自哪张表」；
2. 反向：按表名/列名找「哪些动作应该消费这张表」，用来发现**漏实现**的动作（问题 1 的自动版）。

---

### 问题 5：孤立动作 370 个缺少「值不值得做」的判据

**现象**：图里 76 簇 / 孤立 370 / 成对 21。孤立动作没有优先级信号，
而离线单机环境下大量动作**玩家永远触发不到**（跨服、活动、付费）。

**建议**：给每个动作附「**玩家可达性**」标记：
- 能否从某个 UI 入口触发（`MessageCenter.on` 有注册 + 有 prefab 入口）
- 是否属于付费 / 跨服 / 已下线活动（可按配置表 `begintime/endtime` 判过期）

把不可达的沉底，可达的按「入口被点到的频次」排序。

---

### 问题 6：动作名与 do 名不是一对一，核对时容易误判「缺失」

**实例**：C01 名单 27 个，其中 3 个名字与客户端常量指向的 do 名不同：

| C01 名单 | `HttpConst` 实际指向 | 位置 |
|---|---|---|
| `WEAR_EQUIPMENT_ALL` | `User.PutOnEquipment` | `index.js:59594` |
| `SPECIAL_SHOP` | `User.GetSpecialShopData` | `index.js:59618` |
| `ACTIVITE_SHOP` | `User.BuyAcitivityShop` | `index.js:59619` |

我们一度按名字核对，误报「缺 3 个」。

**建议**：产物里同时给出 **`动作名` + `do 名` + `HttpConst 常量行号`** 三列，
并在文档里明确「核对以实现侧的 do 名为准」。

## 三、执行经验（与算法无关，但同类离线补丁工程可直接复用）

1. **「空数据占位」不是万能的**
   某些面板在数据为空时会**每帧重请求**（`scripts2.js:46175`），形成死循环并锁死输入。
   给数据前先确认：空表会不会触发重试？有守卫才敢给空。

2. **给数据表挂统计属性会污染遍历**
   我们给生成的数据表挂了 `__meta`（可枚举），`for...in` 把它当数据行 →
   `BZ_MALL` 真实 39 行却下发了 40 行，客户端多出一张空白商品卡。
   **凡整表下发，必须显式跳过 `__meta`。**

3. **货币与物品必须分流**
   `1`=金条 / `4001`=银两 / `4003`=潜能 / `8888`=元宝 都是**货币**。
   一律走「发放物品」会把货币塞进背包（客户端只认钱包），玩家看起来"拿到了"，实际钱包没涨。

4. **判币种看客户端的比价语句，别信注释**
   `BuyMount` 我们按注释实现成「扣铜钱」，实际客户端 `scripts2.js:18754` 用
   `RoleBaseInfo.gold`（金条）比价 → 扣错钱包 = 变相打折。
   搜 `RoleBaseInfo.xxx <` 这类语句比读注释可靠。

5. **客户端没有空表 / 缺字段守卫的三处典型崩法**（下发数据时要保证「下标存在 + 查表 id 合法」）
   - `scripts2.js:35088` `this.data[1]` —— 元素是 `undefined` 就崩（列表里塞了空值）
   - `scripts2.js:45855` `getSkillLvData(t).SkillEvaluate` —— `t` 查表返回 `null` 就崩
     （`level` 表 id 是 1..999，**给 0 必崩**）
   - `scripts2.js:46151` `this.priceNum.toString()` —— 字段缺失就崩

## 四、给算法改进的最小可交付建议（按性价比排序）

| 优先级 | 改进项 | 预期收益 |
|---|---|---|
| P0 | 面板同一性聚类（问题 1） | 直接消除「只做写动作 → 界面点不开」这一整类返工 |
| P0 | 跨文件追踪后判字段类型（问题 2） | 消除「数组判成数字」导致的空货架 |
| P1 | 形状表加 `safeDefault`（问题 3） | 减少「兜底反而弄崩客户端」 |
| P1 | dump 配置表纳入证据链（问题 4） | 自动给出数据源，减少人工翻 444 张表 |
| P2 | 动作可达性标记（问题 5） | 孤立动作排序，避免做永远触发不到的 |
| P2 | 产物加 do 名与常量行号（问题 6） | 减少核对口径误判 |
